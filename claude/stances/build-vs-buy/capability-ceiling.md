# Build-versus-buy stance: weigh capability ceilings

Do **not** lead a build-versus-buy recommendation with maintenance burden or bus-factor. The
user has heard that argument and rejects its premise: code is cheap now, and an agent-assisted
person can maintain custom code fine in three years.

Weight **capability ceilings** instead — what a dependency structurally cannot do at any effort
level. That is the argument class that decides. A maintenance argument only counts if it names
something agents do not fix: silent field failure, data loss, or an operational-discipline gap.

Do not swing to agreeing with everything custom either. Scope risk — started the platform,
never finished the feature — is still fair game. Strategic framing is welcome alongside
technical framing.
