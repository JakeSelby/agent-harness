# The 0.13 adoption release: an instrument package, parity packaging, a repositioned front door

> Turn 0.13 from the Jev judgment layer into the adoption release: publish the field scan as a public
> doc, extract the rule-measurement engine as a standalone package that runs on anyone's transcripts,
> close the three packaging gaps that stop people trying the harness, and lead with measurement
> instead of stances. Mechanism: `bmad-deep-recon` for logged research, `bmad_issue_sync.py new` for a
> traceable epic tree on milestone 4, `product.json` as the one copy source.
> **Effort:** 3 epics, ~18 issues · **Risk:** medium · **Blast radius:** public positioning, milestone scope, one new repository

## At a glance

- **Outcome** — Someone who has never heard of agent-harness runs one command, learns which of their own rules never fire, and finds a front door that installs like everything else in the field.
- **Approach** — Log the field scan through BMad, publish it as credit rather than teardown, then ship the one capability nothing else has as its own package and import it back.
- **Touches** — `product.json`, README, `docs/field-scan.md`, `claude/hooks/rule-detectors.py`, `bin/harness`, milestones 3 and 4, a new MIT repository, and this repository's `_bmad-output/`.
- **New deps** — One vendored wheel alongside `tomlkit`; no new runtime service, no network call.
- **Not in scope** — List submissions (another session owns those), chasing rulesync's 52 targets, the v1.0.0 stable contract, Jev itself.
- **Exit test** — `uvx ruleprobe report` works on a machine with no agent-harness; `ProductCopyTests` and `bmad_issue_sync.py audit --live` both pass; v0.13.0 holds only adoption issues.
- **Open question** — Whether the listings session has submission copy in flight that the new positioning would contradict; my coordination message expired undelivered.

## System design

```text
  bmad-deep-recon ──▶ *docs/field-scan.md ──▶ *product.json ──┬──▶ README
     (logged, public)     (credits the field)                 ├──▶ site
                                                              └──▶ GitHub About
  *AH epic tree ──▶ v0.13.0 (milestone 4)
        │
        ├──▶ *ruleprobe repo ── vendored wheel ──▶ agent-harness
        │     (uvx; no harness needed)                  ▲
        └──▶ *parity: plugin manifest · packaged install · import ─┘
```

`*` marks what is new. The field scan sets the copy, the copy sets every public surface, and the
epic tree is what makes 0.13 an adoption release instead of a capability release.

## Steps

1. **[Run and publish the field scan](#step-1--run-and-publish-the-field-scan)** — `bmad-deep-recon`, competitive type, from the shared checkout; synthesize into `docs/field-scan.md` and retire `docs/comparison.md`.
   *Exit:* the doc names at least ten projects and what each does better; `harness lint` and `tests/test_doc_links.py` pass.
2. **[Re-scope the milestones](#step-2--re-scope-the-milestones)** — move the Jev tree (#135 and 15 children) to a new v0.14.0; v0.13.0 takes the adoption epics.
   *Exit:* `gh api …/milestones` shows v0.13.0 holding only adoption issues and v0.14.0 holding Jev.
3. **[File the epic tree](#step-3--file-the-epic-tree)** — three `type::epic` issues parented to #212 via `bmad_issue_sync.py new --milestone 4`, then their stories.
   *Exit:* `bmad_issue_sync.py audit --live --grace-days 2` is clean and every new issue resolves in `issue-map.json`.
4. **[Reposition the front door](#step-4--reposition-the-front-door)** — rewrite `product.json`, the README opening and `hero.*`; amend #230's acceptance rather than closing it.
   *Exit:* `ProductCopyTests`, `.github/scripts/check_landing_copy.py` and `scripts/sync_about.py --check` all pass.
5. **[Carve out the measurement engine](#step-5--carve-out-the-measurement-engine)** — lift `analyse()` and the shell tokenizer into a new `ruleprobe` repo, plus a declarative detector format so a stranger can measure their own rules without writing Python.
   *Exit:* someone with no agent-harness, no Python written and their own CLAUDE.md gets hits against **their** rules, not only the six generic ones.
6. **[Import it back](#step-6--import-it-back)** — `rule-detectors.py` shrinks to the harness's own rule pack and imports the vendored wheel; `check_detectors` keeps gating.
   *Exit:* `unittest discover -s tests` green, `harness lint` green, and an existing home runs a session end to end with no re-install.
7. **[Close the packaging gap](#step-7--close-the-packaging-gap)** — add `.claude-plugin/marketplace.json` and a packaged install path; keep `git clone` working unchanged.
   *Exit:* a fresh home installs from the plugin marketplace and from the packaged command, and `harness uninstall` restores both.
8. **[Ship `harness import`](#step-8--ship-harness-import)** — read an existing CLAUDE.md, AGENTS.md or `.cursorrules` into primitives behind a dry-run diff.
   *Exit:* importing a third-party CLAUDE.md produces primitives whose `harness sync --dry-run` the user can read before adopting.
9. **Persist the design record** — this plan and the [roadmap arc](roadmap-arc-2026-09-21.md) land under `_bmad-output/planning-artifacts/`; the field scan lands under `research/`.
   *Exit:* both files are committed on the release branch and every relative link resolves.

## Decisions for the reviewer

None — all five taken as recommended on 2026-09-21: Jev splits (#136 to #139 stay), measurement before grading, Python on PyPI, amend #230, a separate MIT repository. Reply `build`.

## Risks

- Extraction destabilises the shipped detector path; publication gates on a full suite run plus one real home upgrade. Hooks execute from the checkout by absolute path and `lib/vendor` is always reachable, so vendoring cannot break an installed home.
- The listings session never received the coordination message, so positioning could contradict an in-flight submission; forward the handoff text below before running `sync_about.py --apply`.
- 0.13 absorbs both Jev and adoption and neither ships; the release policy cuts when a milestone empties, so a split milestone releases half-done.
- The whole repositioning rests on the standalone tool being useful to a stranger in sixty seconds, and the first draft of step 5 was not: generic detectors only, with Python required before it says anything about their own rules. Declarative detectors are the fix; if they do not land, the package ships as a narrower cost-and-hygiene reader and the positioning has to follow it down.

# Addendum

## Why now: the delta, in the backlog's own terms

The field scan found three clusters in this category, each with an owner. Breadth belongs to
**rulesync** — 52 targets, derived from per-feature tuples rather than a hand-kept list, on npm.
Content belongs to **superpowers**, **gstack** and **addyosmani/agent-skills**, and those positions
track audience size, not engineering. Static validation belongs to **ctxlint** (90 rules in four
catalogs) and **agnix** (Rust, with an LSP).

Nobody owns evidence in the bound-to-your-rules sense. The nearest neighbour is Burnd, which reads
the same transcripts and even proposes a CLAUDE.md line per cost leak (`claudeMdPatch`), but runs
the other way: leak → suggested rule, never rule → did it fire. No project in the set binds a
detector to each rule file, fails its own lint when a rule has neither a detector nor a written
opt-out, and reports per-rule hit rate grouped by which preference variant was active. The sharpest illustration: six projects enforce an always-loaded size cap and no
two numbers agree — 200 lines (agnix, cc-audit), 150 (wshobson), 150 soft with 300 heavy plus a
32,768-byte hard cap (agents-md-cookbook), 400 lines or 2,000 tokens depending which file you read
(caliber), 8,000 tokens with a 4,000 tier aggregate (ctxlint), 200 here. Only the 32 KiB figure
cites a mechanism. Everyone is guessing, because measurement does not exist.

agent-harness already has the instrument. `bin/harness:1628 check_detectors` fails lint when a rule
file has neither a transcript detector nor an explicit `OPT_OUT` giving "the one-line reason nothing
in a transcript can decide it". `bin/harness:2480 rule_report` reports hit rate per detector grouped
by repository **and by stance variant**, excluding legacy and errored rows from the denominator.
Nineteen detectors ship today. That is a category — agent instrumentation — and it is currently one
line in a 34-line doc behind a CLI flag that `harness --help` does not list.

**The instrument has already earned its keep, twice, and both receipts are in this repo's own
backlog.** #429: "The delegation stance never fires: zero subagent spawns in 19 headless runs" — a
shipped stance measured as having no effect. #324, closed: "brief-without-cap rate did not move after
brief-guard shipped" — a shipped hook measured as not moving its own metric. No other project in the
field can produce a finding of that shape about itself, because no other project can see it. Those
two issues are the strongest marketing this project has and they are currently filed as bugs. They
belong in the field scan and in the launch narrative, stated exactly as they are: the measurement
caught the author's own features not working.

**The backlog delta.** v0.12.0 is 38 issues of internal plumbing. v0.13.0 is 16 issues, all of them
the Jev epic. #212, the adoption epic, says in its own body: "This program is post-v1 and does not
block the stable CLI release." So the plan of record is stable release → v1.0.0 → adoption, while
the field's window is open now. The nuance that makes inverting it defensible rather than impatient:
adoption work that depends on the stable CLI contract *should* wait for v1, but a new package in a
new repository and an additive plugin manifest depend on neither.

## Step 1 — Run and publish the field scan

Run from the shared checkout, not a worktree (BMad resolves `{project-root}` against the working
directory; a worktree has no `_bmad/scripts/` and halts by design).

Invoke `bmad-deep-recon`, research type **competitive**, decision framed as *"where should 0.13 spend
its effort to make the harness usable by people who are not its author?"* — not "how do we beat X".
The session's own adversarial reading of the field is **input, not output**: `.agent-harness/` is untracked, `_bmad-output/` is tracked and public
(267 files), and `docs/bmad-governance.md` forbids redirecting artifacts to a private repo. Everything
BMad writes here is published, so the run's framing has to survive being read by the maintainers of
the projects it names.

The research firewall applies: subagents get briefs, not project files. Feed the assessment in as a
named granted document or re-derive; do not let it leak as ambient context.

Then synthesize `docs/field-scan.md`. Nine sections, and the order matters — the generous ones come
before the self-interested ones:

1. **Why this page exists** — one person's reading on one date; comparisons age, so the date and the
   method are stated before any claim.
2. **How the field was read** — four public lists, repos pulled with `gh api`, every claim traced to
   a file path a reader can open.
3. **What to use instead of this** — rulesync for anyone on more than two runtimes (52 targets,
   bidirectional import, npm); ctxlint alongside whatever you pick (90 catalog rules). Putting this
   third, above our own strengths, is the whole tone of the document.
4. **What the field got right, by name** — planning-with-files' floor-not-override `.mode`
   precedence, gsd-core's `MODEL_PROFILES` and review-depth auto-downgrade, gstack's
   declared-versus-inferred profile, wshobson's capability matrix, LynxPrompt's `--boundaries`,
   agents-md-cookbook's 32 KiB cap and its actual source.
5. **What this harness took from it** — credits each borrowing and says what changed; names the floor
   semantics as a better idea we have not adopted.
6. **What is here that I did not find elsewhere** — measured rules, the ownership journal, graded
   shell commands, the normalized policy engine, each with a file path.
7. **What this deliberately does not do** — no model routing, no agent loop, no 52 targets, no
   always-on runtime.
8. **Honest gaps** — empty `constraints.json`, six advisory axes, no macOS CI, no plugin manifest,
   the unsourced 200-line cap, and the `qualified` versus all-stances-`unqualified` contradiction.
9. **Corrections welcome** — an Idea issue; the page is dated and versioned.

Section 8 is not decoration. A field scan that lists only other people's gaps reads as marketing; one
that leads with its own reads as an engineering document, and it is the second kind that gets linked.

Retire `docs/comparison.md` by replacing its body with a pointer; `tests/test_doc_links.py` resolves
every relative link, so update the referrers in the same change. The closing invitation ("Send a
comparison, or a counter-example, as an Idea issue") is worth keeping — it is the best line in it.

**Flag for licensing:** `anthropics/skills` is not open source. Repo-level `license: null`, and each
`skills/<name>/LICENSE.txt` forbids retaining copies outside the Services, reproduction and

## Step 5 — Carve out the measurement engine

`claude/hooks/rule-detectors.py:539 analyse()` and the tokenizer above it are roughly 55% of the file
and entirely rule-agnostic — that is the library. The 17 `Detector(...)` entries at `:886-903` are
this repo's own rules and stay. Around six are generic enough to ship as `ruleprobe.detectors.common`:
whole-file-cat, unfiltered-find, no-verify, secret-in-write, compact, model-switch. Event construction
is already isolated — `usage-log.py:610-659` (Claude) and `:960-968` (Codex) emit the same dict
schema, so both readers move without reshaping.

```
ruleprobe/
  events.py  shell.py  registry.py  report.py  cli.py
  readers/claude_code.py  readers/codex.py
  detectors/common.py
```

```python
run(events, stances=None, *, registry=DEFAULT, strict=False, errors=None) -> dict[str, list[Hit]]
iter_sessions(root=None, runtime="auto", since=None) -> Iterator[Session]   # .id .repo .runtime .events
Registry.add(Detector(id, rule, event, fn, gate=None))
Registry.from_entry_points("ruleprobe.detectors")
report(rows, by="rule", min_sessions=20, promote_share=0.30) -> str
```

**The first draft of this step did not work, and the fix is the most important change in this
round.** A stranger running `uvx ruleprobe report` would have got hits for the six generic detectors
only. Their own rules have no detectors, and `Registry.from_entry_points` asks a first-time user to
write Python before the tool says anything about their configuration. The entire repositioning rests
on that sixty seconds, so the wedge has to work before anything else in the plan matters.

**Declarative detectors are the fix.** Ship a rule-side format — front-matter or a sidecar, matching
on tool name, command shape, argument pattern, message role and ordering — so someone writes a
detector for "never `cat` a whole file" in five lines of YAML, not five lines of Python. The Python
`Registry` stays as the escape hatch for anything the format cannot express. This needs no model,
which is what keeps it in 0.13.

Detector *generation* from rule prose is the next step up and is genuinely LLM-shaped, which puts it
in Jev territory (#136 to #139). That is the coupling the first draft missed: the plan extracts the
instrument and defers the only mechanism that lets the instrument grow detectors for rules it has
never seen. Hence the split in decision 1 rather than a wholesale move.

Sequence for 0.1.0: generic pack → declarative format → the six generic detectors re-expressed in it
as proof the format is sufficient. Generation is 0.2.0 and depends on the Jev apparatus.

Name is provisional. Check availability on PyPI and GitHub before the epic is filed.

## Step 6 — Import it back

`bin/harness:126 load_detectors` and `usage-log.py:68 detectors()` both load the module **by file
path**, and `check_detectors` only reads `module.DETECTORS` and `module.OPT_OUT`. So
`rule-detectors.py` stays exactly where it is, shrinks to roughly 350 lines, and imports `ruleprobe`;
both loaders and the lint gate are untouched.

Distribution back into the harness is a vendored wheel beside `tomlkit`, not a PyPI dependency.
Verified: hooks run from the checkout by absolute path — `~/.claude/settings.json` invokes
`python3 <checkout>/adapters/claude-code/hook.py`, and
`~/.claude/hooks/harness` is a symlink to `claude/hooks` in the checkout. `lib/vendor` is therefore
always reachable at runtime, and an existing installed home needs no re-install. `reconcile.py:10` is
the precedent for the sys.path insert.

## Step 7 — Close the packaging gap

Today a new user runs 8–12 commands with decisions about branch, which runtimes to manage, VS Code,
Homebrew opt-outs and hook trust before seeing anything. Every high-star neighbour ships
`.claude-plugin/marketplace.json`; rulesync and ctxlint are one `npx` away. The plugin manifest is
additive and does not touch the v1 stable CLI contract, which is why it does not have to wait.

`harness uninstall` restoring cleanly is the acceptance bar for both new paths, not an afterthought —
it is currently in `hero.proof` and is one of the more credible things the project says.

## Step 8 — Ship `harness import`

rulesync's `import` and `convert` are the reason it is adoptable: you are not asked to throw away the
CLAUDE.md you already have. Today agent-harness can *adopt* a file — take ownership with a conflict
record — but cannot read `.cursorrules` or a third-party CLAUDE.md into primitives. The dry-run diff
is the trust-building half; ship it with the importer, not after.
