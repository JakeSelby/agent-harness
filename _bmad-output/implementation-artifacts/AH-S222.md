# AH-S222 — Carry GitHub's stateReason into the issue map so not-planned items stop reading as completed

## Story

As a maintainer reading the planning corpus, I want an issue closed as not planned to read as not
planned in its story file and the map, so that abandoned work stops looking delivered.

## Context and value

`bmad_issue_sync.py` maps every closed issue to the lifecycle `completed`. An issue closed as not planned
therefore reads `completed` in its story file's frontmatter and managed block, and `done` in
`sprint-status.yaml`. `epics.md` now says "not planned" for those items, but the tool that owns the map
does not ([#698](https://github.com/JakeSelby/agent-harness/issues/698)). AH-S054 is one example: #142
was closed as not planned on 2026-09-21, and the map records its lifecycle as `completed`
[Source: _bmad-output/implementation-artifacts/AH-S054.md]. `epics.md` marks it "(not planned)"
[Source: _bmad-output/planning-artifacts/epics.md].

**Current behaviour at HEAD** [Source: scripts/bmad_issue_sync.py]:
- `live_lifecycle` returns `active` for an open issue and `completed` for any closed one. The same
  expression sets the lifecycle when an item is reserved or bootstrapped.
- `refresh` copies `live_lifecycle` into the map, and `audit --live` compares the two.
- The sprint status renders `done` for an item whose lifecycle is `completed`.
- The REST issue payload the tool already fetches carries `state_reason`. The tool reads it in one place
  only, `accepted_for_delivery`, which treats `not_planned` and `duplicate` as not accepted.

## Acceptance criteria

From the issue's Acceptance section ([#698](https://github.com/JakeSelby/agent-harness/issues/698)):

1. **Given** an issue closed as not planned, **when** `refresh` runs, **then** its story file's
   frontmatter and managed block render it as not planned.
2. **Given** the map, **when** `audit` runs, **then** it checks the new value, including against GitHub
   under `audit --live`.
3. **Given** an item closed as not planned, **when** the sprint status is derived, **then** it is still
   treated as closed.

## Design

### Approach

From the issue's scope: carry GitHub's `stateReason` into the map, as a new lifecycle value or a field
beside it; render it in the managed block; and let `refresh` keep it current. No new API call is needed,
because the fetched issues already carry `state_reason` [Source: scripts/bmad_issue_sync.py#fetch_issues].

### Decisions and alternatives

The issue records two shapes and does not choose:
- **A new lifecycle value**, such as `not-planned`, beside `active` and `completed`. Every comparison with
  `completed`, in `sprint-status` and in the epic's done rule, must then treat it as closed.
- **A field beside `lifecycle`**, keeping `completed` for every closed issue and adding the reason. Closed
  handling is unchanged, and only rendering and the audit read the new field.

[ASSUMPTION: the second shape changes fewer call sites, since two places compare lifecycle with
`completed`; the issue does not weigh the two.] Whether `duplicate` renders the same way as not planned
is not recorded; `accepted_for_delivery` already groups the two.

### Do not implement

- Any change to how an open issue's lifecycle is derived.
- Any edit to story bodies: the sync tool owns only the frontmatter, the H1 and the managed block (AD-5).
- A hand edit of `epics.md`; its "not planned" wording is separate from this tool.

## Tasks

- [ ] Choose the shape: a lifecycle value or a field beside it (AC: 1)
- [ ] Carry `state_reason` into the map on `reserve`, `bootstrap` and `refresh` (AC: 1)
- [ ] Render it in the frontmatter and managed block (AC: 1)
- [ ] Check it in `audit` and `audit --live` (AC: 2)
- [ ] Keep the sprint status and the epic done rule treating it as closed (AC: 3)
- [ ] Run `refresh` once to bring existing not-planned items up to date, and record the command in the
      pull request (AC: 1)
