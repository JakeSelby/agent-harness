# AH-B079 — A hook you add beside the harness's hooks makes sync report a conflict

## Reproduction

1. Run `harness sync` in a clean home, which registers the harness's coordinator on `PostToolUse`
   and the other events in `~/.claude/settings.json`.
2. Add your own entry to `hooks.PostToolUse`, for example `{"matcher": "Bash", "hooks": [{"type":
   "command", "command": "python3 ~/.claude/hooks/mine.py"}]}`.
3. Run `harness sync` again. It prints "Needs your attention: owned field changed:
   hooks.PostToolUse" and exits 2. `harness doctor` reports a modified owned field, and
   `harness uninstall` keeps the whole field, so the harness's own entry stays behind.

`NativeInstallTests.test_a_personal_hook_survives_sync_doctor_and_uninstall` scripts these steps
in a temporary home.

## Root cause

The settings merge keeps entries the harness does not recognise as its own
[Source: bin/harness#merge_claude_settings]. The ownership journal, however, records each
`["hooks", <event>]` path as a whole value. `Store.json` flags a conflict whenever the live list
differs from the applied one, and so do `Store.drift` and `Store.uninstall`
[Source: lib/harness_core/reconcile.py#Store.json]. A user's entry in the same list therefore
looks like an edit to the harness's field. After the first such sync, the record is never
updated again.

## Acceptance criteria

1. **Given** a synced home, **when** you add your own hook to an event the harness registers and
   sync again, **then** sync reports no conflict. It keeps your entry and still writes its own.
2. **Given** the same home, **when** `harness doctor` reads the journal, **then** it reports no
   drift for that event.
3. **Given** the same home, **when** `harness uninstall` runs, **then** the harness's entries are
   removed and yours remain. An event list that ends up empty goes back to its prior presence; a
   parent `hooks` object the harness created is left in place, as it is for every other owned
   field.
4. **Given** an edit to one of the harness's own entries, **when** sync or doctor runs, **then** it
   is still a conflict or drift.
5. **Given** a journal written before this fix, **when** sync, doctor or uninstall reads it,
   **then** its hook event lists are treated as shared, and the next sync records them as such.
6. **Given** a malformed entry, or a command that only resembles a legacy script name, **when** the
   harness decides ownership, **then** it is the user's.

## Design

- **Mechanism:**
  - `Store.json` takes `hook_lists`, the owned paths whose list the harness shares entry by entry.
  - Their records carry `"entries": "harness-hooks"`.
  - Conflict, drift and uninstall compare only `owned_part` of a value: the entries
    `is_harness_hook_entry` recognises. An absent list owns nothing, the same as a list of only
    user entries.
  - A record written before this fix names no owner. `entries_of` reads a `["hooks", <event>]`
    key as shared all the same, so doctor and uninstall are right before the next sync.
  - `is_harness_hook_entry` treats anything malformed as the user's. It matches a legacy script
    name only as a whole path component, because uninstall now deletes what it matches.
  - Uninstall's `restored` keeps the user's entries instead of restoring the prior value.
- **Shared predicate:** it moves from `bin/harness` into `harness_core.reconcile`, so the journal
  can apply it at uninstall without the caller. `bin/harness` keeps its old names as aliases.
- **Rejected:**
  - Dropping hook events from the owned paths would give up conflict detection for the harness's
    own entries.
  - Adopting the live value on each sync would hide a real edit to them.
- **Must not change:** the whole-value comparison for every other owned field, and the Codex
  `hooks.json` merge order.

## Review findings

A fresh-context blind review returned twelve findings. The patched ones:

- Journals written before the fix still took the old path at doctor and uninstall. `entries_of`
  now reads a `["hooks", <event>]` key as shared. (medium)
- A malformed user entry could crash uninstall partway through. `is_harness_hook_entry` now treats
  it as the user's. (medium)
- An absent list and a list of only user entries compared unequal. `owned_part` now treats them
  alike. (low, latent)
- A legacy script name matched as a substring now decides what uninstall deletes, so it matches
  only as a whole path component. (low)
- There was no Codex `hooks.json` coverage, the end-to-end test skipped doctor's drift report, and
  uninstall was untested after an edit or a removal. Tests now cover all three. (medium)
- The docs did not say how the harness recognises its entries, or that a command added inside one
  of them counts as an edit. (low)
- The owner name was repeated rather than a constant, and the Claude Code hook paths were built
  twice. (low)
- The story claimed the pre-fix failure without evidence. The regression section now records it.
  (low)

Rejected: the leftover empty `hooks` object after uninstall, which is how every owned field's
parent is treated and predates this change. AC 3 now says so.
