## Story

As a maintainer landing many pull requests before a release, I want a merge queue and one changelog
fragment per change, so that pull requests stop waiting on sequential rebase-and-rerun rounds and stop
conflicting on the same changelog section.

## Context and value

From the release-cost analysis tracked in #340. The up-to-date requirement forced a rebase-and-rerun
round trip per pull request, which the issue puts at 36–70 minutes for 12 pull requests per release,
and every fix branch edited the same section of the same changelog file. The issue notes that the
queue takes over the up-to-date check, a branch-protection change worth reviewing on its own terms.
[Source: https://github.com/JakeSelby/agent-harness/issues/337]

## Acceptance criteria

The issue has no acceptance section; these are taken from its mechanism and the PR:
1. **Given** every check workflow that reports on a pull request (`lint`, `test`, `issue-ownership`,
   `landing-copy`), **when** a merge group runs, **then** it runs too, and the PR-number checks read
   the number from the merge-group head ref or refuse rather than guess.
2. **Given** a change under the governed roots, **when** `bin/harness lint` runs on its branch,
   **then** it requires a fragment under `changelog.d/`, or a `changelog.d/<n>.none.md` waiver with a
   reason.
3. **Given** the fragments, **when** `scripts/release_notes.py --changelog VERSION` assembles them,
   **then** the version section renders in a stable order, and an empty set, a malformed name, an
   existing version section or hand-written Unreleased entries are refused.
4. **Given** the `main` ruleset, **when** the queue is enabled, **then** merges go through it — not
   delivered; see Completion notes.

## Design

### Approach

`merge_group` triggers on the three workflows with a shared `.github/scripts/pull_number.py`;
`lib/harness_core/changelog.py` parses and assembles fragments; `changelog.d/README.md` and
`CONTRIBUTING.md` describe the convention.
[Source: https://github.com/JakeSelby/agent-harness/pull/610]

### Decisions and alternatives

- The triggers land before the queue, because a queued PR whose checks never report stalls the queue.
- The waiver is a file, because the squash message is the PR body and neither the lint nor the test
  job can see it.
- Transition: a branch stays exempt while its `CHANGELOG.md` diff lands in Unreleased and `main` has
  no 0.13.0 section; the 0.13.0 release PR is the cut-over.
- **After review:** only a visible `.md` other than the README is a fragment candidate; only fragments
  the branch creates count; a waiver needs a reason of at least three words; every workflow step that
  reads a pull-request field is checked for its merge-group guard.
