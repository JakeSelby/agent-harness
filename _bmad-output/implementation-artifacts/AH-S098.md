## Story

As a developer who works in VS Code or the Codex desktop app, I want written graduation gates and an
independent evaluation of each editor and desktop client, so that a client is called stable only when its
own evidence and a support promise back it.

## Context and value

The only story under epic #216, which gives editor and desktop integrations an evidence-based path from
preview to stable without expanding the v1.0.0 floor; the epic is post-v1 and does not block the stable CLI
release. Existing evidence authority is #187 and #188, the 0.9.0 qualification of these clients.
[Source: https://github.com/JakeSelby/agent-harness/issues/217]
[Source: https://github.com/JakeSelby/agent-harness/issues/216]

## Acceptance criteria

1. **Given** the graduation criteria, **when** they are written, **then** they cover install, update,
   runtime discovery, hooks or equivalent lifecycle behaviour, conflict handling, recovery and support
   ownership.
2. **Given** a client, **when** it is evaluated, **then** it has independent immutable evidence on every
   operating system claimed for it.
3. **Given** a native capability a client lacks, **when** it is evaluated, **then** the gap is named rather
   than simulated.
4. **Given** one client's passing evidence, **when** another client is evaluated, **then** it cannot stand in
   for it; each graduates only on its own evidence and support promise.
5. **Given** compatibility docs and release notes, **when** a client is evaluated, **then** its status
   changes only after acceptance.

## Design

### Approach

Define the extra evidence and maintenance promise stable support requires, then evaluate Claude Code
VS Code, Codex VS Code and Codex desktop one at a time against it.
[Source: https://github.com/JakeSelby/agent-harness/issues/217]

### Decisions and alternatives

- **No proxying between clients.**
- **Separate from v1:** the v1 plan keeps this program apart so it cannot silently expand the stable
  contract. [Source: _bmad-output/planning-artifacts/v1-release-plan.md#Post-v1 programs]

### Do not implement

- Any change to the v1.0.0 support floor.
- A status change in docs or release notes before acceptance.
