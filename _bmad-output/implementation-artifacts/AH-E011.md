## Goal

Every unit the harness installs is selectable from one selection document. A mode bundles a selection
under a name. A `superpowers` mode ships out of the box and is measured against superpowers alone, and the
copy says what the harness is when it sits under a skill library. Completion is observable when a
developer can switch any rule, hook, skill, workflow or role by id, select a named mode, and read a
four-arm result for that mode.

The issue gives the reason. Skill libraries such as obra/superpowers tell an agent how to work, but they
cannot enforce, measure, budget or route any of it. This release makes the harness the layer under them.

## Scope and requirement coverage

**In scope:**

- Every rule, hook, skill, workflow and role becomes a dimension with variants. Switch kinds have `on` and
  `off`, and a mode is a named set of selections.
- Users keep their own keys above any mode.
- `delegated` stance variants, and detection of a layered library.
- Replay arms built as profiles, and the first four-arm live set.
- The copy, the docs and the release.

**Constraints,** from the issue's Principles:

- The work is additive to the v1 CLI contract, and `harness uninstall` restores.
- Per-file rule links migrate with both states journaled.
- One selection document shape serves five places: the mode file, user config, the project file, the
  session file and `harness selection --json`. There is one resolver and no second path.
- Nothing is claimed as enforced without a hook id. A mode is `unqualified` until the live set says
  otherwise.

**Out of scope:** PRD FR-16 excludes trimming a layered library's own skills. The harness switches its own
units and cedes whole areas.

## Architecture slice

- **AD-2 One resolver, fixed invariants:** `posture.py` is the only resolver. Core hooks can be switched off
  only behind an explicit acknowledgement. For modes, a developer's explicit choice shadows a mode key,
  while a default written by `harness init` does not; #557 picks the mechanism within that constraint. The
  spine names #554 as carrying the resolver migration.
- **AD-3 Reversible configuration ownership:** record prior and applied values, and restore only while
  they match. That is the issue's rule that per-file rule links migrate with both states journaled.
- **AD-12 Measurement invariants:** arms differ only by environment, each fence is proved before scoring,
  every row records its arm's provenance, and ablations are declared in a manifest (#559, #560).

## Exit criteria

- [ ] One selection document and one resolver serve all five places the issue names (#554).
- [ ] Hooks, rules, skills, workflows and roles are switch kinds. A disabled primitive is absent from every
  projection, and core hooks need `core_switches_acknowledged: true` (#555, #556; FR-15).
- [ ] `HARNESS_MODE` selects a mode for one session, and `harness selection` names every shadowed mode key
  (#557; FR-16).
- [ ] The `superpowers` mode keeps every enforcement hook and cedes process primitives. The `delegated`
  variants keep `plan-ceremony` and `testing` explicit (#558).
- [ ] Arms are declared in `benchmarks/ablations.json`, and the four-arm live set reports each metric
  against control, with n and spread (#559, #560; FR-58).
- [ ] The copy and docs are published, and the release is qualified and tagged (#561, #562, #563).
- [ ] `harness uninstall` restores, and `git clone` plus `bin/harness install` keeps working unchanged.
