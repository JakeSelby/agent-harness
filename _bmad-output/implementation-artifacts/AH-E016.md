# AH-E016 — Harden BMad traceability for many sessions filing at once

<!-- bmad-sync:begin -->
- **GitHub issue:** [#635](https://github.com/JakeSelby/agent-harness/issues/635)
- **Primary parent:** None
- **State:** active

The issue carries the summary, discussion and acceptance evidence; this file carries the design.

This work item was authored as part of the repository's committed BMad planning system.
<!-- bmad-sync:end -->

## Goal

Harden the BMad traceability tooling, so that every issue maps to its story file in both directions and
the sync tool is safe with many sessions filing at once. Completion is observable through the issue's
acceptance: two sessions filing at once never collide on an ID, and the audit stays green without a pull
request after every merge.

## Scope and requirement coverage

**In scope,** from the issue's Scope section:

- Filing and reservation races (#392, #433, #537).
- Reservation against the default branch (#410).
- `issue-ownership` diagnostics (#411).
- Key naming (#412).
- The map lifecycle treadmill (#420).
- The command-grading conflict with `apply` (#421).
- The held backlog reservations (#530).
- Verifying artifact content on `main`, not only its presence (#642).

**Out of scope:** the story-file format and the corpus re-baseline, which AH-E012 carries.

**Requirement coverage.** `epics.md` lists this epic against FR-9 and FR-64. Checked against the 2026-09-23
PRD:

- **FR-9 Traceable work items:** its consequences are that `issue-ownership` fails a pull request whose
  delivery issue is unmapped or shared, and that `reserve` refuses an ID any reachable branch or worktree
  already holds. The races (#392, #433, #537), reservation (#410) and diagnostics (#411) all harden these.
- **FR-64 Story files as design records:** `apply` verifying artifact frontmatter on `main` (#642) keeps
  the story file and the map consistent.

NFR-10 Concurrency safety also names this epic's condition as a tested property: two reservations in
parallel worktrees never take the same ID.

## Children

Mapped to this epic, all open:

- AH-B040 #392: new files an issue the list endpoint does not yet return, so reserve fails
- AH-B042 #410: reserve allocates an ID without checking what the default branch already holds
- AH-B043 #411: issue-ownership does not say which issues it found, so a keyword in prose is invisible
- AH-B044 #412: the issue number is keyed github_number in the map and issue in planned actions
- AH-D005 #420: Decide how map lifecycle stays current without a pull request after every merge
- AH-D006 #421: grade-bash refuses a sub-issue delete that bmad_issue_sync apply performs unattended
- AH-B069 #537: Reserve a BMad ID in the same invocation that files the issue (v0.12.1)
- AH-B065 #642: bmad_issue_sync apply: verify artifact frontmatter on main, not only presence

Named in the issue's scope but not mapped:

- #530: Reserve BMad IDs for the accepted backlog (open, v0.12.1). Held by the unmerged #529.
- #433: `bmad_issue_sync.py new` files an issue then fails to reserve it (open). It has no BMad ID, and
  `epics.md` does not list it among the issues held by #529.

**State at `origin/main`, relevant to #410.** PR #441 (merged 2026-09-23, closing #440) makes `reserve`
survey every issue map the clone can reach before trusting its counter. That covers each linked
worktree's working copy and every local and remote-tracking branch. #410's problem statement says
`reserve` "never consults `origin/main`". After a fetch, the remote-tracking branch is now surveyed.
`[ASSUMPTION: #410 may be partly addressed by #441; the issue has not been updated, and a stale fetch
still leaves a window]`

## Architecture slice

- **AD-5 Public planning with the design in the story file:** the sync tool owns only the frontmatter, the
  H1 and the managed block. `apply` verifying frontmatter on `main` (#642) checks that ownership.
- **AD-18 Shared-machine concurrency and writes:**
  - ID reservation surveys every reachable issue map.
  - The issue map is among the files a whole-file rewrite writes atomically.
  - These are the concurrency rules this epic's races test.

## Sequencing

- #537 (reserve in the same invocation that files) and #530 (the held reservations) carry v0.12.1. The
  rest are unscheduled.
- #392 and #433 are the same failure class as #537: an issue is filed but the reservation fails.
  `[ASSUMPTION: #537 may subsume them; the record does not say so]`
- #420 is a decision, and it gates the second half of the acceptance: the audit stays green without a

- #421 needs a call on whether `grade-bash` or `apply` changes, because the two conflict today.
- **Milestones:** the issue has no milestone field, matching `epics.md` ("unscheduled").

## Exit criteria

- [ ] Two sessions filing at once never collide on an ID. A test proves it for parallel worktrees
  (NFR-10).
- [ ] Filing and reserving happen in one invocation, and a read-after-write miss recovers (#537, #392,
  #433).
- [ ] The audit stays green without a pull request after every merge (#420).
- [ ] `issue-ownership` names the issues it found (#411), and the issue-number key is consistent (#412).
- [ ] `apply` verifies artifact frontmatter on `main` (#642), and `grade-bash` no longer refuses what
  `apply` does unattended (#421).
- [ ] The held backlog has BMad IDs (#530).
