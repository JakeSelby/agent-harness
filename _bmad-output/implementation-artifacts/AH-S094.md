## Story

As a user installing v1.0.0, I want the published release to be exactly the audited candidate, with every
public surface naming the same version and commit, so that what I install is what was audited and a failed
publication can be recovered without rewriting history.

## Context and value

Step 5 of the v1.0.0 release program, under epic #206; existing release authority is #100. It starts only
after #210 records a go verdict.
[Source: https://github.com/JakeSelby/agent-harness/issues/211]
[Source: _bmad-output/planning-artifacts/v1-release-plan.md#Step 5 — Publish the audited bytes]

## Acceptance criteria

1. **Given** the release workflow, **when** it runs, **then** it deterministically rebuilds the candidate
   archive and refuses any mismatch with the audited SHA-256.
2. **Given** the tag, archive, checksum, metadata, changelog, catalog, docs and GitHub release, **when**
   they are published, **then** they identify the same version and commit.
3. **Given** publication, **when** it runs, **then** it goes in order: immutable tag, verified GitHub
   release artifact, reference-site pin, then personal-site metadata.
4. **Given** a failed surface, **when** it fails, **then** publication stops and every publication identity
   so far is recorded.
5. **Given** a failed release, **when** it is repaired, **then** no tag is moved and a corrective release
   follows the SemVer policy.
6. **Given** a rollback, **when** it runs, **then** mutable sites roll back through their prior immutable
   pins and the harness rolls back to the immediately preceding release.
7. **Given** the published archive, **when** post-release smoke checks run, **then** they install and roll
   back that archive, not a local rebuild.

## Design

### Approach

The candidate commit becomes the immutable tag. The release workflow rebuilds the archive
deterministically, refuses a digest mismatch, and publishes the verified archive with checksums; metadata,
changelog, catalog, notes and install and rollback commands must agree with it.
[Source: _bmad-output/planning-artifacts/v1-release-plan.md#Step 5 — Publish the audited bytes]

### Decisions and alternatives

- **Never move a tag:** mark a failed release clearly and ship a corrective release.
- **Stop on the first failed surface** and record identities so a partial release can be resumed or
  reversed without guessing.

### Do not implement

- Any change to the candidate after the audit; a change returns to the affected gate.
