## Goal

Make every capped multi-item read keep the newest items, and prove it, so that a cap trims history
rather than the newest corrections. `remote_control.py` fetched sessions with a fifty-row cap in server
order and asserted nothing, so which rows the cap dropped was undefined, and a session lost minutes ago
is the newest row, the first one an unknown order can hide. Item B7 of the 2026-09-22 enterprise-review
intake, a follow-up to #483.
[Source: https://github.com/JakeSelby/agent-harness/issues/526]
[Source: https://github.com/JakeSelby/agent-harness/pull/564]

**Issue text out of date.** The issue asks that the sessions request name a descending sort and that
the parser check descending `updated_at`. The PR records a live measurement on 2026-09-22 that
`/v1/code/sessions` takes no sort parameter (`sort` and `order` are ignored) and orders newest-first by
`last_event_at`, not `updated_at`. The delivered read asserts that order instead of requesting one.

## Acceptance criteria

1. **Given** a sessions page, **when** it is parsed, **then** the read asserts newest-first order by
   `last_event_at` on parsed timestamps, and refuses a page that is out of order, holds a non-dict row,
   or has an unreadable timestamp.
2. **Given** a refused page, **when** `status` or `doctor` reports, **then** it reads
   `lost sessions: not checked (page order unknown)`, never as nothing lost.
3. **Given** a page that carries `next_cursor`, **when** a count is reported over it, **then** it names
   the page ("none in the newest 50"), not the account.
4. **Given** `docs/runtime-controls.md`, **when** a reader reads it, **then** it records the rule for
   capped reads, and `OPEN_TAIL` in the usage feed records its drop order at its declaration.
5. **Given** a fake page in the wrong order, **when** the tests run, **then** it is refused.
