## Reproduction

1. Start a Claude Code session.
2. While it runs, run `harness sync`, which installs the band workers `worker-a`, `worker-b` and
   `worker-c`.
3. In the running session, spawn a subagent without naming a role.

Observed: the spawn hook rewrites the spawn to a band worker and the runtime rejects it with "Agent type
'worker-b' not found". Every unnamed spawn in every running session fails. Separately, the brief guard
announces the budget sentence on nearly every spawn.
[Source: https://github.com/JakeSelby/agent-harness/issues/257]

## Root cause

Claude Code loads its agent registry when the session process starts and does not reload it. The spawn
hook, added in #251, decided a worker was routable because its definition existed on disk, not because
the running session could resolve it.

## Acceptance criteria

1. **Given** a session start of kind `startup` or `resume`, **when** the session-start policy runs,
   **then** it records which agent definitions exist, and never records on `clear` or `compact`.
2. **Given** that record, **when** an unnamed spawn arrives, **then** the spawn hook routes only to a
   worker in the record, and the brief guard prices through the same decision.
3. **Given** no record, an unreadable one, or one without the worker, **when** an unnamed spawn arrives,
   **then** it is not rerouted, and one notice per session says to restart to get routing.
4. **Given** the budget sentence is appended, **when** it happens, **then** it is silent; the routed
   notice appears once per session; notices for a refused or changed request stay per occurrence.
5. **Given** session records, **when** they are stored, **then** they hold agent names only, are
   owner-only, are pruned after 14 days, and are removed by `harness uninstall`.

## Design

A reroute must never turn a working spawn into a failing one. `policy/hooks/harness-session.py` writes a
per-session registry record at session start; `policy/hooks/posture.py` locates it;
`policy/hooks/tier-agent-spawns.py` and `policy/hooks/brief-guard.py` share one routability decision
that reads it. Without a usable record the hook falls back to the pre-routing behaviour. The fix must
not change routing in a session that can resolve the worker.

At `origin/main` the record's rules have since been refined: `resume` narrows an existing record and
creates none, and #263 lets a long-running session start routing once
it can resolve the band worker.

## Regression test

`tests/test_session_registry.py` (new), with `tests/test_band_workers.py`, `tests/test_brief_budget.py`
and `tests/test_usage_feed.py`: a session whose record lacks the worker is not rerouted.
