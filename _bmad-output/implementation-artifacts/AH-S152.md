## Story

As a first-time user, I want one command that takes me from nothing to a previewable install, so that
I reach first value without choosing a branch or running `config set` by hand.

## Context and value

Before this story, first value took eight to twelve commands and several decisions (branch, managed
runtimes, editor, hook trust), while every neighbour with an audience was one command away. The
field-parity epic (#442) made this one of its five stories and set `harness uninstall` restoring
cleanly as the bar for every new install path.
[Source: https://github.com/JakeSelby/agent-harness/issues/447]
[Source: https://github.com/JakeSelby/agent-harness/issues/442]
[Source: https://github.com/JakeSelby/agent-harness/pull/479]

## Acceptance criteria

1. **Given** a fresh home with git and Python 3.9 or later, **when** the user pipes
   `scripts/install.sh` from the `stable` branch into `sh`, **then** it clones `stable`, writes a
   default configuration with `harness init --yes`, and runs `harness install --dry-run`, changing
   nothing it does not own.
2. **Given** an existing checkout, **when** the script runs again, **then** it fast-forwards in place
   and keeps the configuration.
3. **Given** a missing requirement or an occupied destination that is not a checkout, **when** the
   script runs, **then** it names the failing step and never clobbers the destination.
4. **Given** the checkout the script leaves, **when** the user syncs and uninstalls, **then** both
   work.
5. **Given** the README, **when** a reader reaches the install block, **then** the one-liner leads and
   the clone block stays for contributors.

## Design

### Approach

A POSIX `sh` script checks git and Python 3.9+, clones `stable` (or fast-forwards an existing
checkout; `HARNESS_CHECKOUT` and `HARNESS_BRANCH` override the defaults), runs a new non-interactive
`bin/harness init --yes`, then `bin/harness install --dry-run`, and prints the exact next command and
the uninstall. It never runs a non-dry install. `init --yes` fills what the machine knows and names the
rest.
[Source: scripts/install.sh]
[Source: https://github.com/JakeSelby/agent-harness/pull/479]

### Decisions and alternatives

- **A checked-in script, not a PyPI package:** the harness runs from its checkout, since every hook is
  referenced there by path, so `docs/runtime-installation.md` says no PyPI package is planned. The
  issue had allowed `uvx`, `pipx` or a script.
- **Preview only:** the script stops at the dry run, so the user applies the install themselves.
- **Credit:** pmstack's installer is credited in the PR as the model.
[Source: docs/runtime-installation.md]

### Do not implement

- Any change to the clone path; the epic is additive only. [Source:
  https://github.com/JakeSelby/agent-harness/issues/442]

## Dev notes

### Bound decisions and requirements

- FR-17, Install and update channels: the installer clones `stable`, runs `harness init --yes`, then
  `harness install --dry-run`, and applies nothing until the developer installs for real.
- FR-69, Initialize and configure: a first configuration in one scripted command. The PRD dates
  FR-69 to 0.8, while #479 describes `init --yes` as new; the record does not reconcile the two.
- AD-19, Distribution channels carry no second authority: the installer installs from `stable`, which
  only fast-forwards to release tags.
- AD-21, Dependencies: standard library and a Python 3.9 floor.

### Files to touch

- `tests/test_installer_script.py`, `tests/test_init_defaults.py`: tests.

### Testing

Ten new tests. `tests/test_installer_script.py` runs the script against a local bare clone in a
disposable HOME with no network: fresh home, second run, sync and uninstall afterwards, a missing
requirement, and an occupied destination. `tests/test_init_defaults.py` pins the `init --yes` defaults
and checks that an existing config is not replaced without `--force`.
