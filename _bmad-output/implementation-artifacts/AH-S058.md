## Story

As a developer considering the optional decision provider, I want documentation and release notes that
say exactly what each decision point sends, what stays local, which points reached `advise` and which
stayed in `shadow`, with numbers from the harness's own ledger, so that I can opt in knowing what I get
and what leaves my machine.

## Context and value

A provider adapter needs a reproducible demonstration and accurate setup and support documentation
before it can be announced as usable. The 2026-09-21 re-scope aligned this story with the re-aimed epic:
the documented consumers are stop-claim verification (#141) and the ask-band gate (#372), with band
routing (#145) and skill shortlists (#143) described as shadow-only measurements. It is the last step of
the epic's critical path.
[Source: https://github.com/JakeSelby/agent-harness/issues/147]

## Acceptance criteria

1. **Given** the release notes, **when** they are read, **then** they carry numbers from the harness's
   own ledger and decision log and state plainly which points missed their criterion and shipped in
   `shadow`.
2. **Given** the documentation, **when** it is read, **then** it lists exactly which fields leave the
   machine per decision point, and the vendor's terms as they stand: no training on input, zero retention
   for enterprise accounts only, and no stated retention window.
3. **Given** a clean installation, **when** a user supplies their own API key, **then** the documented
   demo reproduces; a disabled or unconfigured installation keeps existing behaviour.
4. **Given** the documentation, **when** it is read, **then** it explains what is transmitted, what stays
   local, what is advisory, and which native combinations are actually qualified.
5. **Given** licensing, **when** the release ships, **then** the vendor's hosted service is kept separate
   from the adapter's MIT licence, and dependency licences are reviewed with required notices included.
6. **Given** compatibility wording, **when** it is published, **then** it is factual, with no logos or
   partnership or endorsement claims, and no restricted benchmark or performance results without
   permission.
7. **Given** the release, **when** it links its work, **then** it links the tracking issue and the
   implemented children, and does not present follow-on experiments as shipped.

## Design

### Approach

Onboarding, payload examples per point, question-pack authoring, troubleshooting and an architecture
diagram in the repository docs, with the "Decision providers" section of `docs/runtime-controls.md` as
the existing anchor. Original adapter code, reviewed packs and permitted sanitized fixtures ship under
the project licence.
[ASSUMPTION: the docs extend `docs/runtime-controls.md#Decision providers`, where #486 to #597 documented
the contract; the issue does not name a file.]

### Decisions and alternatives

- **Re-scoped consumers:** stop claims and the ask band are the documented value; the original
  skill-selection and response-style demos are superseded, and response-style checks (#142) were closed
  as not planned.
- **Harness-owned numbers only:** figures that measure the third-party provider's model stay local
  unless its terms permit publication (FR-49).
- **General completion auditing is not the first-release value proposition.**

### Do not implement

- Expansion of the existing platform matrix.
- Publication of restricted benchmark or performance results.
- Presenting follow-on experiments (#156, #157, #374) as shipped.
