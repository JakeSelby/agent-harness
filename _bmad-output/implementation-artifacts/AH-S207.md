## Story

As an agent or contributor working in this repository, I want one rule that routes every SDLC step through its
BMad skill and keeps the planning corpus current. Then the brief, PRD, spine, UX specification and story files
never drift from the code again, and nobody has to explain the process in each session.

## Context and value

BMad was installed and its corpus reconstructed on 2026-09-19, but no rule told an agent to use it:
- Design went into issue bodies and uncommitted plan files.
- The brief, PRD and spine sat unchanged for four releases.
- The maintainer does not want to give linking and upkeep instructions every session, and asked that
  enforcement not come from a brittle hook.

This rule is the instruction half. The depth check from AH-S206 (#620) is the enforcement half.

## Acceptance criteria

1. **Given** any BMad workflow in this repository, **when** it activates, **then** it loads the governance
   text. That text states the authority split between issue and story, the skill routing map, and the currency
   rule.
2. **Given** an agent starting from `AGENTS.md`, **when** it reads the BMad section, **then** it is pointed at
   that governance text.
3. **Given** `bmad-build` on a work item with a BMad ID, **when** it activates, **then** it reads the story file
   as its spec. It upgrades a legacy stub before implementing, and writes the design back into the story.
4. **Given** the lint and context-budget checks, **when** they run, **then** they stay green, with no new
   always-loaded lines.

## Design

### Approach

- The rule lives in `docs/bmad-governance.md`, which every `_bmad/custom/*.toml` already loads as a persistent
  fact. It reaches every BMad workflow without new wiring.
- `AGENTS.md` gets a three-line pointer instead of the rule text. That keeps the always-loaded budget
  untouched.
- `bmad-build` gets an activation step that binds the story file as its spec.

### Decisions and alternatives

- **Repository-level, not a harness primitive.** The maintainer decided on 2026-09-23 that this is a
  BMad-specific, open-source pattern for this repository, modelled on the BMad-usage rule other BMad
  repositories carry. A harness-wide rule, plan and build workflows that consult an integration's design
  record, was considered and not chosen.
- **Enforcement in CI, not a hook.** The story-depth check in `issue-ownership` does the enforcing. A hook on
  issue creation was rejected as brittle.
- **The Review Card stays.** It remains the approval surface. Its addendum is distilled into the story at
  build, so the story is the durable record. Making the plan itself the story was rejected, because long
  stories would collide with the plan card's cap and its hook.

### Do not implement

- No changes to `primitives/workflows/`, which ship to every harness user (#349 decouples the product from
  BMad).
- No new always-loaded lines.
