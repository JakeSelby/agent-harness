## Story

As the maintainer, I want a small, bounded provider-backed end-to-end suite that runs the native runtimes
on inexpensive pinned models, so that integration failures deterministic tests cannot see are caught
without depending on anyone's personal credentials or letting spend grow unbounded.

## Context and value

The issue opened as a deferred follow-up to #98 and #93. Its record of the evidence at the time: CI ran lint,
deterministic Python tests and an isolated installation dry run; authenticated native checks were local
probes, and a personal subscription quota had blocked some of them; release preflight validates saved
evidence but does not execute native qualification.
[Source: https://github.com/JakeSelby/agent-harness/issues/134]

Current state at `origin/main`: CI also runs a `smoke` job, `scripts/smoke_tier.py --skip credentials`,
which is deterministic and explicitly "never native client qualification". No provider-backed suite
exists. [Source: .github/workflows/ci.yml] [Source: scripts/smoke_tier.py]

**Recorded contradiction:** the issue says this is "not new implementation or a new release prerequisite
today" and "Backlog only", but it now carries milestone v1.0.0, sits under epic #206, and the 2026-09-23 PRD
lists it under §9.1, the v1.0.0 stable contract, as its automation item. The issue text is left unchanged.

## Acceptance criteria

1. **Given** the suite, **when** it runs, **then** it uses no developer's personal credentials or
   subscription quota.
2. **Given** each fixture, **when** it runs, **then** it uses an explicitly pinned inexpensive model and
   the measured token, request and cost totals are published.
3. **Given** a run, **when** it approaches a limit, **then** request, timeout and spend bounds are enforced
   with no silent premium-model fallback.
4. **Given** a permitted and a forbidden operation, **when** the fixture runs, **then** the permitted one
   is proven to execute and the forbidden one is rejected; a runner that blocks every command is
   unverified, not passed.
5. **Given** the native adapters, **when** they are tested, **then** they use the same shared primitive
   sources, with no provider-specific stance or skill catalog.
6. **Given** a failed, skipped or unavailable provider case, **when** results are read, **then** it cannot
   produce a passing qualification claim.
7. **Given** the suite, **when** it is documented, **then** credential ownership, trigger policy, limits
   and the exact scope of evidence are stated.

## Design

### Approach

As proposed in the issue:
- Reuse the shared primitives and native adapters: Claude Code through Bedrock, Codex through its supported
  test-provider configuration. A direct model API success alone is not native acceptance.
- Dedicated project or CI identities, preferably short-lived cloud credentials; provisioning belongs to
  this work.
- Pin the cheapest models that support each fixture's tools and protocol, and measure per-run usage before
  enabling recurrence.
- Tiny fixtures: instruction and stance loading, one permitted tool operation, one prohibited operation
  with a verified boundary, a validated output artifact, and one minimal shared-task continuation where
  supported, in isolated homes and repositories.
- Small prompt and output limits, deadlines, concurrency, and per-run request and spend ceilings, with
  bounded retries and explicit classification of quota, auth, outage and runner limitations.
- Start opt-in and manual on trusted code, and record runtime, provider, model, client, platform and
  source versions with redacted observations.

### Decisions and alternatives

- **Integration checks, not quality reviews:** no automatic upgrade to expensive models.
- **Opt-in first:** whether and how often to schedule is decided only after cost and reliability
  measurements.
- **Never expose credentials to untrusted pull-request code.**

### Do not implement

- Qualification of untested models, subscription login flows, GUI clients or the whole catalog; a passing
  fixture does not qualify them.
- Full native qualification (owned by #98) or stance consistency (owned by #130).
- Per the issue: no CI jobs, cloud provisioning, wider required matrix or release-gate change until the
  issue is explicitly scheduled.
