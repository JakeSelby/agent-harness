## Story

As a developer, I want the stop gate's blocking mode, block limit and time budget to be settings, so that I can choose an advisory gate or different bounds while a released turn is never mistaken for a passing gate.

## Context and value

The gate fixes eight consecutive blocks and a 240-second command budget, and a release after a timeout or error is distinct from successful verification ([#129](https://github.com/JakeSelby/agent-harness/issues/129)). The epic's 2026-09-21 assessment rated the story Partial: outcome states are recorded and tested, `MAX_BLOCKS` and `BUDGET_SECONDS` are constants, and there is no advisory mode ([#116 comment](https://github.com/JakeSelby/agent-harness/issues/116)).

That still holds on `main`. `policy/hooks/stop-gate.py` sets `MAX_BLOCKS = 8` and `BUDGET_SECONDS = 240` as module constants. It logs each run with an action (`blocked`, `released`, `skipped`) and an outcome (`passed`, `failed`, `timeout`, `unverified`). A timeout releases the turn as unverified, and a tree that changed during the run releases as unverified [Source: policy/hooks/stop-gate.py]. No advisory mode exists.

## Acceptance criteria

1. **Given** `gates.mode=advisory`, **when** the gate fails, **then** the failure is recorded and the turn is not blocked; **given** `blocking`, **when** the configured bound is reached, **then** the turn is released without any green evidence being manufactured.
2. **Given** both runtime adapters, **when** they apply the gate policy, **then** they apply the same validated values and keep the staged and untracked tree identity and the cancellation semantics of the existing runtime work.
3. **Given** a first failure, the final allowed block, a timeout, a command error, an untrusted repository, invalid bounds and a changed tree, **when** each is tested, **then** each yields its own recorded state and the cache is invalidated on a changed tree.

## Design

### Approach

The issue proposes `gates.mode` (`blocking` or `advisory`), `gates.max_blocks` and `gates.timeout_seconds`, with defaults `blocking`, 8 and 240. Trust checks and the repository's gate authority are kept. Passed, failed, timed-out, errored and released states are recorded separately ([#129](https://github.com/JakeSelby/agent-harness/issues/129)).

The plan adds that advisory and exhausted blocking gates may release a turn, and that neither outcome proves the gate passed [Source: docs/plans/stance-completeness.md#Step 5 — Settings and runtime behavior].

### Decisions and alternatives

- The defaults equal today's constants, so existing behaviour is the migration path ([#129](https://github.com/JakeSelby/agent-harness/issues/129)).
- No other alternative is recorded in the issue or pull request.

### Do not implement

- Do not let a released turn record success.
- Do not bypass the trust check.
- Do not sync an unmerged candidate into the live installation.
