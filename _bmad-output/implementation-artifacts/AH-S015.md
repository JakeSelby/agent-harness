## Story

As a developer who uses a planning framework such as BMad alongside the harness, I want the `delegation` stance to decide the model of subagents the framework launches, and whether they run at all, so that framework-launched spawns do not all run as `general-purpose` agents on the session model with every tool.

## Context and value

The issue records that framework skills spawn subagents with no `subagent_type` and no `model`, so the agent frontmatter carrying the harness's tiers never applied to them. BMad's `bmad-build`, `bmad-build-auto` and `bmad-code-review` mandate subagents and instruct "same model capability as the current session", and `bmad-build-auto` halts when subagents are unavailable, contradicting the `off` stance. The issue also records a verification on Claude Code 2.1.273: a `PreToolUse` hook on `Agent` returning `updatedInput.model` changes the spawned model without a permission decision; the session model is not in the payload or environment, but is in the transcript's newest assistant record. BMad's customization contract (`_bmad/custom/<skill>.user.toml`) exposes each spawn's instruction as text an override can change without patching the framework.

## Acceptance criteria

1. **Given** a bare spawn (no `subagent_type`, or `general-purpose`, and no `model`) under `tiered`, **when** the hook runs, **then** `model` is rewritten to one tier below the session model, with the lowest tier as the floor.
2. **Given** a spawn that names an agent or passes `model`, **when** the hook runs, **then** it is left alone.
3. **Given** `session-model`, **when** a bare spawn runs, **then** it is not rewritten; **given** `off`, **then** the hook asks before every spawn.
4. **Given** no main-line assistant record, a missing transcript or malformed input, **when** the hook runs, **then** the spawn is untouched.
5. **Given** the BMad override templates, **when** tests read them, **then** every layer names a shipped agent, the declared surface is pinned, and the implementation handoff runs on the builder's tier.
6. **Given** `harness bmad check`, **when** an installed skill renamed a layer id or removed a key, **then** it reports the drift; **given** `harness bmad apply`, **then** it installs the templates without overwriting a differing override unless `--force`.
7. **Given** a headless end-to-end run, **when** the hook is installed, **then** the subagent model changes under `tiered` and no spawn happens under `off`.

## Design

### Approach

1. A `PreToolUse` hook, `claude/hooks/tier-agent-spawns.py`, matched on `Agent`, always registered, reading the stance from config or `HARNESS_STANCE_DELEGATION`.
2. Override templates under `templates/bmad/custom/` for the three BMad skills: review layers run as `reviewer`, the acceptance and intent layers as `spec-reviewer`, and the implementation handoff on the builder's tier. Nothing from the framework is redistributed.
3. `harness bmad check|apply [repo]` compares each template with the installed skill's `customize.toml`, and installs the templates.
4. `docs/bmad.md` narrows "no framework extensions" to "no framework copies".

### Decisions and alternatives

- **No settings fallback.** The issue proposed falling back to the `model` key in the user's settings when the transcript has no assistant record. The pull request dropped it, "because that is a default the session may not be running on"; an unknown tier is left untouched.
- **Use the framework's own override contract** rather than patching framework files (from the issue).

### Do not implement

- Routing BMad's implementation handoff to the `builder` agent proper. From the issue: `builder` commits in its own worktree while `bmad-build`'s review step diffs the tree it ran in against `baseline_commit`, so the handoff would also have to bring the branch back. It was tracked separately; #52 records that follow-up as decided won't-do.

### Later change

At `origin/main`, `policy/hooks/tier-agent-spawns.py` routes a bare spawn under `tiered` to the cost variant's default band worker (`worker-a`, `worker-b` or `worker-c`), and uses "one tier below the session model" only when there is no default band. The `harness bmad` command is now an alias for `harness integration check|apply bmad`. This story's criteria 1 and 6 describe the design as delivered in v0.5.0.
