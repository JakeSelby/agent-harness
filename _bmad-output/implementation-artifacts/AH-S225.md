## Story

As the operator running native qualification, I want `role-confinement`, `bidirectional-handoff` and `spawn-confinement` to observe what the client and the harness actually did, so that a success the round produced is not reported `unverified` and an absence that is really unobserved says why.

## Context and value

Round 2 of the 0.13.0 native qualification (`scripts/native_acceptance.py` at 0a7cf94, `claude-code-cli-macos` and `claude-code-cli-linux`, both on genuine hosts) passed 9 of 12 cases on each target with 0 failed and 3 unverified. In each unverified case the driver could not observe the outcome; none showed the product misbehaving.

- `role-confinement` checked for the text `status: completed`, but `harness role run` prints the worker record as JSON (`"mode": "isolated-cli"`, `"status": "completed"`, `"result_path": …`, `"usage": {…}`). The gatherer ran and printed that record, yet the case said it "did not complete as an isolated-cli worker". The record carries `result_path`, not the result, so the next check, for the workspace line, would have read the wrong text too.
- `bidirectional-handoff` saved a codex-written record at revision 2, but its return leg required the reading model to name the writing runtime without being asked.
- `spawn-confinement` found no subagent transcript, no `framework-spawn` deny row and no refusal text, and could not tell a refused spawn from a spawn the model never attempted.

Qualification cannot pass while a working product reads as unverified.

## Acceptance criteria

1. **Given** `harness role run gatherer` prints a worker record with `mode: isolated-cli` and `status: completed` whose `result_path` holds the workspace line, **when** `role-confinement` runs, **then** that step passes. A record with another `mode` fails, a record with another `status` is `Unverified` and names that status, output with no record is `Unverified`, and a result file without the line fails.
2. **Given** a `--runtime codex` save produced revision 2, **when** the return leg runs, **then** the case reads `runtime` from `.agent-harness/task.json` and fails unless it is `codex`. The reading session is asked for the objective and the runtime by name. It must report the objective or the leg is `Unverified`, and whether it named the runtime appears in the verdict without deciding it.
3. **Given** a framework spawn wrote no subagent transcript and neither the decision log nor the client showed the confinement deny, **when** `spawn-confinement` reads the orchestrator transcript, **then** no `Agent` tool call is `Unverified` with "the model never attempted the spawn", a call whose tool result came back without an error fails, a call refused with some other error is `Unverified` and quotes the redacted result, and no readable transcript is `Unverified` as before.
4. **Given** an ordinary spawn wrote no subagent transcript, **when** its transcript holds no `Agent` call, **then** the false-positive check is `Unverified` rather than failing as "the guard refuses everything".
5. **Given** the hook command `lifecycle.registration` registers, run with `Home.env()` while the runner's own `HARNESS_HOME` and `XDG_STATE_HOME` point elsewhere, **when** it refuses a framework spawn, **then** `logged_refusals` finds the row and nothing is written elsewhere.

## Design

### Approach

The driver-side changes are all in `scripts/native_acceptance.py`:

- `last_json_object` decodes the last top-level JSON object in `harness role run`'s output.
- `worker_result` reads the file that `result_path` names.
- `task_runtime` reads the record's `runtime`, which `tasks.save` stamps from `--runtime`, and `RETURN_PROMPT` asks for it by name.
- `agent_calls` parses the orchestrator transcript for `Agent` and `Task` `tool_use` blocks and pairs each call with its `tool_result`.
- `spawn_not_refused` turns what `agent_calls` finds into the three outcomes.

### Decisions and alternatives

- The return leg's primary source is the task record, because the record is what crosses runtimes and its `runtime` field is deterministic. The model's answer is a secondary signal. The reader still has to report the objective, the same bar as the forward leg, so a session that never read the record cannot pass. Rejected: keeping the model's naming as the pass condition, which leaves the leg at the model's discretion.
- Spawn attempts come from the transcript, not the decision log. The log gets a row for an `Agent` call only when a hook judges that call (a `framework-spawn` deny, a `tier-agent-spawns` reroute or a `brief-guard` cap), so a call that none of them touched leaves no row. Neither log gives an "attempted" signal on its own.
- The log path was a suspect and is not the bug. `policy/hooks/decisions.py` resolves `HARNESS_HOME` or `HOME`. `Home.env()` builds the client environment from an allow-list that carries neither `HARNESS_HOME` nor `XDG_STATE_HOME`, and sets `HOME` to the disposable root, so the live hook writes to `root/.local/state/agent-harness/decisions.jsonl`, the path `logged_refusals` reads. A test proves this with the real entry point.
- A worker record whose `status` is not `completed` stays `Unverified`, because a failed or timed-out worker is usually the host's, not the confinement's. A wrong `mode` fails.

### Do not implement

No change to hook behaviour, to what `decisions.py` records, to `harness role run`'s output or to `tasks.save`. No change to other cases.

## Dev notes

### Bound decisions and requirements

Qualification evidence comes from what the harness and the client write, not from the model's say-so. A case reports `unverified` when it cannot observe the thing it checks, and says what it could not observe (`docs/compatibility.md`).

### Files to touch

- `scripts/native_acceptance.py`
- `tests/test_native_acceptance_observation.py` (new)
- `changelog.d/716.fixed.md` (new)

### Testing

`tests/test_native_acceptance_observation.py` launches no client:

- The role tests feed `case_role_confinement` output shaped as `cmd_role` prints it (AC 1).
- The handoff tests save the record with the real `harness task save` and stub only the model's answers (AC 2).
- The spawn tests write orchestrator transcripts with and without `Agent` calls (AC 3, 4).
- The path test runs the registered PreToolUse command in a subprocess with `Home.env()` (AC 5).

16 of the 18 tests fail against the driver at 0a7cf94. The two that pass there are the no-record case, already `Unverified`, and the path test, which shows the path was never the bug.
