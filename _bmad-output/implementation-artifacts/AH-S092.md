## Story

As a developer adopting v1.0.0, I want install, upgrade, repeat sync, rollback and uninstall proven on the
frozen candidate, including after an interruption, so that I can adopt the release and back out of it
without losing unrelated configuration or being stuck in a half-written state.

## Context and value

Step 3 of the v1.0.0 release program, under epic #206; existing authority is #95 and #97. The plan makes a
lifecycle proof that finds user-state loss release-blocking until the recovery defect and its regression
test land. [Source: https://github.com/JakeSelby/agent-harness/issues/209]
[Source: _bmad-output/planning-artifacts/v1-release-plan.md#Step 3 — Prove lifecycle recovery]

## Acceptance criteria

1. **Given** the upgrade and rollback input, **when** the proof runs, **then** it is pinned to an immutable
   tag with its commit and source-archive digest recorded (the issue names `v0.10.0`).
2. **Given** both reference environments and every Python version in the candidate record, **when** clean
   install, upgrade and a second sync run, **then** they pass and the second sync is idempotent.
3. **Given** a conflict or ownership finding, **when** diagnostics report it, **then** they name the
   responsible source.
4. **Given** a rollback, **when** it completes, **then** the prior executable or checkout, managed files,
   generated projections, ownership journal and effective behaviour are restored.
5. **Given** a rollback, **when** it completes, **then** unrelated configuration, adopted backups,
   out-of-scope user edits and visible conflicts are preserved.
6. **Given** an uninstall, **when** it completes, **then** harness-owned output is removed and unrelated
   user files are kept.
7. **Given** a representative mid-write interruption in install, sync, upgrade, rollback or uninstall,
   **when** recovery runs, **then** the result is either the complete prior state or the complete candidate
   state.

## Design

### Approach

A deterministic, headless acceptance runner, `scripts/lifecycle_acceptance.py`, delivered under child
#222 (AH-S099) in PR #223. It pins the baseline by tag, commit and reproducible archive digest in
`compatibility/lifecycle-baseline.json`; exercises clean install, repeated sync, upgrade, rollback,
conflict preservation and uninstall inside disposable homes; and emits a bounded machine-readable record
of platform, Python, baseline identity, candidate commit, results and file-state digests. #209 consumes
that record on the frozen candidate. [Source: https://github.com/JakeSelby/agent-harness/pull/223]

### Decisions and alternatives

- **Harness-owned lifecycle only:** the runner's record is not native client evidence.
- **Repin only after the tag exists:** the issue says the runner intentionally used v0.9.0 and is to be
  repinned to v0.10.0 only after #220 publishes that tag.

### Do not implement

- Native client qualification (#207).
