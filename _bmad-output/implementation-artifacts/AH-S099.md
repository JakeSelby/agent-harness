## Story

As the release maintainer, I want a deterministic headless acceptance runner for install, upgrade,
rollback and uninstall, so that a frozen candidate can be exercised identically on macOS and Linux and
the lifecycle half of the v1 gate rests on a machine-readable record.

## Context and value

The v1 release lifecycle gate (#209) needed proof that harness-owned filesystem and configuration
behaviour survives upgrade and rollback against a pinned prior release. Native client qualification is a
separate question; this runner proves only the harness's own lifecycle. The issue records that the final
run is recorded only after #207 freezes the candidate. The issue carries the v1.0.0 milestone.
[Source: https://github.com/JakeSelby/agent-harness/issues/222]

## Acceptance criteria

1. **Given** a dirty or mismatched candidate or a stale baseline pin, **when** the runner starts,
   **then** it refuses.
2. **Given** any run, **when** it operates, **then** every operation uses a disposable home and the live
   installation is untouched.
3. **Given** the test suite, **when** it runs, **then** it covers record validation, identity checks,
   preservation assertions and failure reporting.
4. **Given** the repository's Python floor and a current Python on macOS and Linux, **when** the same
   command runs, **then** it works under each.
5. **Given** the docs, **when** they describe the record, **then** they say how #209 consumes it without
   treating it as native client evidence.

## Design

### Approach

`scripts/lifecycle_acceptance.py` pins the baseline in `compatibility/lifecycle-baseline.json` by tag,
commit and a reproducible `git archive` tar digest (at `origin/main`: v0.9.0). Inside disposable homes it
exercises clean install, repeated sync, baseline-to-candidate upgrade, candidate-to-baseline rollback,
conflict preservation and uninstall, compares effective configuration state, and emits a bounded record
holding the platform, Python, baseline identity, candidate commit, results and file-state digests.

### Decisions and alternatives

- **Baseline pinned three ways:** tag, commit and archive digest, so a moved tag or a changed archive is
  caught.
- **Lifecycle separate from native qualification:** the record proves harness-owned behaviour only and
  is never read as client evidence.

### Do not implement

- Native client qualification; that stays with the compatibility evidence.
