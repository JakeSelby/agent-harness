## Reproduction

Set `HARNESS_STANCE_<DIM>` to a variant other than the one selected in the configuration file, then run
`harness stances` and `harness sync`. The issue records it natively on `codex-cli-linux` for `commits`,
`cost` and a custom dimension, during the 0.11.0 qualification:

- `harness stances` reports the environment's variant;
- `harness sync` exits 0 and leaves the previously selected variant linked;
- `harness diff` reports no drift.

## Root cause

At `origin/main` the behaviour is deliberate in code, and the doc disagrees with it:

- `_cmd_sync_unlocked` in `bin/harness` collects every `HARNESS_STANCE_*` and `HARNESS_IDENTITY_*`
  variable, plus `HARNESS_PROJECT_CONFIG` and `HARNESS_PERMISSIONS`, and removes them before it loads
  the configuration. When any is set it prints: "sync projects user defaults; project/session overrides
  stay in the session". The drift check filters the same variables.
- `cost_table` in `bin/harness` gives the reason: "a sync projects user defaults and a session's
  `HARNESS_STANCE_*` stays in the session".
- Commit ca5547f, "fix(stances): keep session choices out of global projections (#106)", introduced the filtering.
- `docs/preferences.md` still says: "At sync time the env value is what gets linked."

So the issue's "ignores" describes intended code with a stale doc.

## Acceptance criteria

The issue asks for one of two outcomes, and ties the choice to #276:

1. **Given** a `HARNESS_STANCE_<DIM>` variable, **when** `harness sync` runs, **then** either the
   env-selected variant is linked as `docs/preferences.md` says, or the doc says the variable affects
   resolution only.
2. **Given** the outcome chosen, **when** `harness diff` runs afterwards, **then** it agrees with
   what `harness stances` reports, or the doc explains why not. [ASSUMPTION: the issue names the diff
   observation but does not state a criterion for it.]

## Design

Open, and tied to #276 ("Decide how project and session stance selections reach a native client",
open). The two options are the issue's own: make sync link the env value, or correct the doc.

The 2026-09-23 spine places this under AD-2: "two precedence ladders disagreeing, which #294 records
today", and its rule says "`bin/harness` stops resolving on its own and calls the resolver. #294 and
#554 carry that migration."

`compatibility/catalog.json` records the current contract as a limitation: "harness sync links
user-level stance selections only; a HARNESS_STANCE_ variable or a project selection changes what
harness stances and the hooks resolve, not the linked stance text. Tracked in #276 and #294."

Do not implement: a sync that writes a session's selection into a global projection without a
decision under #276. Commit ca5547f removed exactly that. [ASSUMPTION: the issue does not say this; it
is read from #106's commit title and the code comment.]
