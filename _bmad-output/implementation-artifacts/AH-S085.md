## Story

As a developer landing on the repository for the first time, I want the root README to lead with one
concrete benefit, the current stances, the qualification status and the safest way to try it, so that I
can decide whether to adopt the harness without assembling that picture from several sections.

## Context and value

A child of #99. The issue records the problem: the README already had the provider-agnostic positioning
and compatibility caveats, but a first-time developer still had to assemble the value, the safe path for an
existing runtime, the stance choices, the demonstration evidence and the ownership model from several
sections, and the demonstration used explanatory comments rather than captured output.
[Source: https://github.com/JakeSelby/agent-harness/issues/183]

## Acceptance criteria

1. **Given** a first-time visitor, **when** they read the top of the README, **then** they can identify the
   problem, the current configurable stances, the qualification status and the safest try path.
2. **Given** the commands and captured excerpts, **when** they are checked, **then** they match the current
   CLI run in isolated configuration homes.
3. **Given** the compatibility markers, **when** the README is built, **then** they remain generated from
   `compatibility/catalog.json`.
4. **Given** a claim, **when** it is read, **then** it distinguishes generated configuration, implemented
   hook decisions and native qualification.
5. **Given** the change, **when** the gate runs, **then** lint, unit tests and generation checks pass.

## Design

### Approach

Refocus the README on defining working preferences once and projecting them to Claude Code and Codex.
Lead with a candid candidate-status notice and a compact stance catalog, make a selected-runtime
`sync --dry-run` the primary quick start, and include a real shortened stance-switch transcript from
isolated homes. Clarify shared primitives versus native adapters, cost and measurement limits, and
ownership, conflicts and uninstall, and link the detailed docs. The PR also corrected
implementation-and-documentation mismatches. [Source: https://github.com/JakeSelby/agent-harness/pull/184]

### Decisions and alternatives

- **Dry run as the primary quick start:** the safest try path for a developer with an existing runtime.
- **Captured output over explanatory comments** in the demonstration.
- **Propose, don't apply, GitHub About text:** the PR proposed text and left repository metadata
  unchanged.

### Do not implement

- Runtime semantics, qualification statuses or GitHub repository metadata.
- UML or viewer work, which stays explicitly deferred until implemented.
