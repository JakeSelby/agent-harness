## Goal

Make the v1 release stories, the v1 plan and the lifecycle baseline name the same previous release
([#694](https://github.com/JakeSelby/agent-harness/issues/694)). They were written around v0.10.0 and
have not moved, while 0.12.0 has shipped and 0.13.0 is in qualification. AH-S090 and AH-S092 record the
drift [Source: _bmad-output/implementation-artifacts/AH-S090.md]
[Source: _bmad-output/implementation-artifacts/AH-S092.md].

**Stale references at HEAD:**
- `compatibility/lifecycle-baseline.json` pins `version` 0.9.0, tag `v0.9.0`, commit `8ce2a65`, with a
  `git-archive-tar` digest [Source: compatibility/lifecycle-baseline.json].
- `v1-release-plan.md` Step 3 starts from "immutable tag `v0.9.0`" and says rollback restores "the
  v0.9.0 executable or source checkout"
  [Source: _bmad-output/planning-artifacts/v1-release-plan.md#Step 3 — Prove lifecycle recovery].
- #209 asks to pin upgrade and rollback input to `v0.10.0`, and says the runner "intentionally uses
  v0.9.0 for the v0.10.0 gate; repin it only after #220 publishes the immutable v0.10.0 tag". That tag
  exists, and the repin has not happened (AH-S092).
- #207 opens "After v0.10.0 is published by #220"; #210 reconciles "the v0.10.0-to-v1 lifecycle
  baseline"; #211 says harness rollback "uses immutable v0.10.0 as the immediately preceding release".
- Tags `v0.10.0`, `v0.11.0`, `v0.11.1` and `v0.12.0` exist in the repository.

The scope has two parts: decide which lifecycle baseline v1 should prove upgrade and rollback from, and
repin it; then amend #207, #209, #210, #211 and the plan to name current releases.

## Acceptance criteria

From the issue's Acceptance section ([#694](https://github.com/JakeSelby/agent-harness/issues/694)):

1. **Given** `compatibility/lifecycle-baseline.json`, `v1-release-plan.md`, #207, #209, #210 and #211,

## Dev notes

- **Bound:** FR-66: Upgrade, rollback and migration. Its consequences require the lifecycle runner to
  pass "upgrade from the prior baseline" and rollback
  [Source: _bmad-output/planning-artifacts/prds/prd-agent-harness-2026-09-23/prd.md#FR-66: Upgrade, rollback and migration].
- **Pinned value.** The baseline's `sha256` is a generated value. It must be produced by a command run
  against the tag, never hand-typed. The loader rejects a baseline missing any of `version`, `tag`,
  `commit`, the archive `format`, `prefix` or `sha256` [Source: scripts/lifecycle_acceptance.py].
- **Evidence.** `compatibility/` is outside the evidence source paths, so the repin does not invalidate
  qualification evidence [Source: lib/harness_core/compatibility.py].
- **Files to touch:** `compatibility/lifecycle-baseline.json`,
  `_bmad-output/planning-artifacts/v1-release-plan.md`, and the four story files. Check
  `tests/test_lifecycle_acceptance.py`, which writes its own baseline fixture.
- **Testing:** `python3 -m unittest discover -s tests`.
