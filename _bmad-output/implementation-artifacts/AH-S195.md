# AH-S195 — Let plan mode own the plan review surface, so the native pane and the native approval replace the typed build gate

## Story

As a developer reviewing an agent's plan, I want `/plan` to run inside the runtime's plan mode, so that
the Review Card renders in the native plan pane and the native approval replaces a typed `build` reply
that no tooling can observe.

## Context and value

Follow-up to #436, which fixed the symptom by telling the agent to open the plan file before posting the
review message. The issue gives two reasons that fallback was not enough: the approval stayed a typed
word, so nothing downstream could tell an approved plan from a draft; and opening a file by path is a
best-effort action an agent can forget, while plan mode makes the document the object of the approval.
The issue also records what was already true: `ExitPlanMode` reads the plan from the file rather than
taking content as a parameter, `plansDirectory` and `useAutoModeDuringPlan` were already set, and the
`plan-ceremony` stance already said "before exiting plan mode". Only the workflow never entered it.
[Source: https://github.com/JakeSelby/agent-harness/issues/439]

## Acceptance criteria

1. **Given** a real `plan` run, **when** the card is written, **then** it renders in the native plan
   pane and the native approval is offered.
2. **Given** approval, **when** plan mode exits, **then** the file survives at the same path.
3. **Given** an approved plan, **when** `build` runs, **then** the plan is committed at a topic-named
   path and that path is said in the first message.
4. **Given** the workflow, skill and stance text, **when** it is read, **then** nothing tells the agent
   to name the plan file or to close with a typed build reply, except on the no-plan-mode branch.
5. **Given** entering plan mode needs the user's consent, **when** `plan` starts, **then** it asks before
   doing anything.

**Undelivered or unverified.** Criteria 1 and 2 are recorded as unverified in the pull request: the pane
rendering and the native approval click cannot be proven headlessly, and it names one interactive
`/plan` run after sync as the proof. Whether that run happened is not recorded in the issue or pull
request.

## Design

### Approach

`/plan` asks to enter plan mode, gathers read-only, writes the Review Card into the file plan mode
designates, posts the review message without its closing build line, and calls `ExitPlanMode`. A
runtime with no plan mode keeps #436's behaviour as an explicit branch: a file named for the topic,
opened for the reviewer, closed on the build line.

### Decisions and alternatives

- **Who renames the file changed from the issue's shape.** The issue proposed that `build` locate the
  approved plan and rename it. After review, the PR has `plan` rename the runtime-named file to a topic
  slug in the same directory, never over an existing name, and end by invoking `/build <absolute path>`;
  `build` works only from the path or issue number it is given and asks when it has neither. The builder
  copies the plan into its worktree and commits it there, since a commit on the shared checkout's
  protected branch could never reach the pull request.
- **Open question 1 (other writes in `plansDirectory`):** answered by probe, per the PR: under plan mode
  the runtime states the plan file is the only editable file, and two headless runs refused a sibling
  write into `plansDirectory`. So there is no pointer file.
- **Open question 2 (validator filename sensitivity):** answered from the hook: `validate-plan-card.py`
  keys on a `.md` suffix under a plans directory and is filename-insensitive; a test pins that.
- **Stance length.** The `plan-ceremony` stance carries the change in nine lines, the length it already
  occupied, so the always-loaded budget is unmoved.
- **Consent prompt.** Shipped as the issue asked; the issue says to revisit the whole approach if it
  reads as friction.

### Do not implement

Settings work: the issue records `plansDirectory` and `useAutoModeDuringPlan` as already set.
