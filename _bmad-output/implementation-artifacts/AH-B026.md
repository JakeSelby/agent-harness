# AH-B026 — Read-only roles are refused as native spawns while builder runs natively

## Reproduction

In a Claude Code session under the harness, `Agent(subagent_type: gatherer)` and
`Agent(subagent_type: reviewer)` are refused natively with "This constrained harness role requires an
isolated worker. Use harness role run …", while `Agent(subagent_type: builder)`, the write-capable
role, runs natively. The agent list still advertises `gatherer` and `reviewer`, and the `delegation`
stance says to gather with subagents without waiting to be asked. The issue records this from a
downstream soak of 0.11.0: one coordinator session, 25 subagent spawns and 3 isolated reviewer runs.
The issue also reports that `read_roots` in the worker envelope included the whole harness checkout,
which the brief never asked for.
[Source: https://github.com/JakeSelby/agent-harness/issues/304]

## Root cause

The refusal follows a rule that none of the three texts stated: the stance, the role descriptions and
the refusal message did not say that a read-only role must run isolated, or why `builder` is exempt.
So a session following the stance burned a refused call per attempt, then gathered inline or paid the
four-call isolated path, and clients routed around the refusal with an unnamed spawn (#291, #300).
[Source: https://github.com/JakeSelby/agent-harness/issues/304]
[Source: https://github.com/JakeSelby/agent-harness/pull/600]

## Acceptance criteria

The issue offered three options and asked for one: (a) rewrite the native spawn into the isolated
worker, (b) keep the refusal and make the stance, the agent descriptions and the refusal say the same
thing, including why `builder` is exempt, or (c) a one-call wrapper. PR #600 took (b), so:
1. **Given** a native spawn of any read-only constrained role, **when** it is refused, **then** the
   refusal carries the confinement sentence.
2. **Given** the `delegation` stance, **when** it is read, **then** it carries the same sentence word
   for word.
3. **Given** the shared `gatherer` and `reviewer` role descriptions, **when** they are read, **then**
   each carries the same sentence.
4. **Given** `builder`, **when** it is spawned natively, **then** it is not refused, because writing
   is not what the refusal confines.

## Design

- **Approach:** one sentence, defined once as `CONFINEMENT_SENTENCE` in
  `lib/harness_core/lifecycle.py`: a read-only role runs through `harness role run <role>`, because
  confinement is read roots and return shape, not the absence of write tools, so the workspace-write
  `builder` keeps spawning natively. The stance, both role descriptions and the refusal carry it. The
  stance text was compressed to absorb the sentence with no net new always-loaded lines.
- **Rejected:** (a) hides a different execution model behind a tool call; (c) belongs to #335
  (PR #594).
- **`read_roots`:** no change here; the PR records that #594 already narrows the envelope's declared
  roots and the Claude Code mount to the workspace, the policy-cited skills and `--read-dir`.
- **Must not change:** the refusal itself stays; no capability is added or removed (the PR's
  landing-copy line).
[Source: https://github.com/JakeSelby/agent-harness/pull/600]
