## Story

As a harness developer extending how stances drive model, effort and budgets, I want one module to
decide which stance is selected and what the model ladder is, so that a stance selected through the
user configuration, a project file or a session variable means the same thing in every hook and in the
lifecycle coordinator.

## Context and value

Six places read the selected stance, each with its own precedence and default, and only the coordinator
honoured `HARNESS_HOME` and a project file. The spawn hook carried the model ladder as a list of names in
code, held equal to the adapter's `tiers` table only by a test. Work that makes model, effort and budgets
follow the `cost` stance needed one reader to extend.
[Source: https://github.com/JakeSelby/agent-harness/issues/243]

## Acceptance criteria

1. **Given** any policy hook or the lifecycle coordinator, **when** it needs the selected stance,
   **then** it reads it from one file that hooks can load as a standalone sibling script.
2. **Given** the spawn hook, **when** it needs the model ladder, **then** it reads the adapter's `tiers`
   table, and no model name is written in hook code.
3. **Given** the resolver cannot be loaded or raises, **when** the command-grading hook runs, **then** it
   grades under the strictest autonomy variant and says so in the prompt.
4. **Given** the existing hook tests, **when** the suite runs, **then** they pass unchanged.

## Design

### Approach

`policy/hooks/posture.py` is the only reader. Its precedence runs from the built-in defaults, through
the user configuration under `HARNESS_HOME` or `$HOME`, then the file named by `HARNESS_PROJECT_CONFIG`
(stances only), to `HARNESS_STANCE_*` for the session. Hooks load it as a sibling file and
`lib/harness_core/lifecycle.py` loads the same file by path. A `strict` flag decides what an unusable
file means: a configuration that exists but cannot be read raises in strict mode, as the coordinator
always did; an absent one is still the defaults.

### Decisions and alternatives

- **One deliberate behaviour change:** the policy hooks now honour `HARNESS_HOME` and
  `HARNESS_PROJECT_CONFIG`, as the coordinator already did. Both are variables the user sets, the same
  trust level as `HARNESS_STANCE_*`.
- **Fail strict for grading:** when the resolver fails, the command-grading hook assumes the strictest
  autonomy variant rather than the default.
- **Sibling-file loading:** hooks are standalone subprocess scripts, so shared code is loaded as a
  sibling file rather than imported as a package.

### Do not implement

Not recorded in the issue or pull request. At `origin/main`, `bin/harness` still resolves on its own;
AD-2 records that migration as in progress under #294 and #554.
