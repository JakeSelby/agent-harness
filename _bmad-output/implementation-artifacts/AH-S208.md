## Story

As a maintainer running BMad's sprint and build workflows, I want `sprint-status.yaml` rendered
from the issue map and the story files, so that those workflows have a status surface and nobody
keeps a second copy of GitHub's state up to date by hand.

## Context and value

BMad's `bmad-sprint-planning` and `bmad-build` workflows read and write
`implementation-artifacts/sprint-status.yaml`, and this repository had none, so they had no status
surface. A hand-maintained file would drift from GitHub, which owns delivery state. FR-65 requires
sprint status to be derived, with `audit` reporting zero drift. The 2026-09-19 readiness report is
also stale; re-running the readiness check is the second half of this issue.

## Acceptance criteria

1. **Given** the committed map and story files, **when** `bmad_issue_sync.py sprint-status` runs,
   **then** it writes `sprint-status.yaml` in BMad's format with the header keys `generated`,
   `project`, `project_key`, `tracking_system` and `story_location`, a comment saying the file is
   derived and naming the command, each epic followed by its children in BMad ID order, and a final
   block for items with no epic.
2. **Given** an item, **then** one the map records as completed is `done`, an active one whose
   story is typed and passes the depth check is `ready-for-dev`, and any other active one is
   `backlog`; an epic is `done` only when its own lifecycle is completed, and an open epic is
   `in-progress` when any child is done, ready or in progress, else `backlog`.
3. **Given** an unchanged corpus, **when** the command runs again, **then** the file is
   byte-identical and is not rewritten.
4. **Given** a file that is missing or differs from a fresh render, **when** `audit` runs,
   **then** it fails with a finding naming the command; `sprint-status --check` fails the same way.
5. **Given** `new`, `reserve`, `refresh`, `bootstrap` or `upgrade` writes the map or a story,
   **then** the file is regenerated in the same run.
6. **Given** the `bmad-build` or `bmad-sprint-planning` workflow, **then** its activation steps say
   the file is derived, to record progress in the story file and to run the command instead.
7. **Given** the re-baselined corpus, **then** a new dated implementation-readiness report records
   the verdict.

## Design

### Approach

`render_sprint_status(manifest)` in `scripts/bmad_issue_sync.py` reads each item's story file for
its `updated` date and its layout, and a typed file is read a second time by the depth check, which
it reuses through a new `item_depth_findings(item)` split out of `depth_findings`. `write_sprint_status` writes only when
the render differs. `write_manifest` calls it last, which covers `new`, `reserve`, `refresh` and
`bootstrap`; `upgrade` calls it after a successful batch. `sprint_status_findings` backs both
`audit` and `sprint-status --check`.

### Decisions and alternatives

- **`generated` is the newest `YYYY-MM-DD` among the map's `generated_at` and every story's
  `updated`, quoted**, not the clock; a malformed value is ignored, so a rerun is byte-identical and `audit` can compare exactly. A wall-clock stamp would make
  every render drift.
- **Drift is opt-in: `audit_manifest(sprint_status=True)`, passed only by the `audit` command.**
  `reserve` and `new` run `audit_manifest` as a precondition; checking drift there would block the
  very commands that regenerate the file. `audit --delivery` stays a single-story check.
- **Grouping follows the nearest epic ancestor.** The map has tasks whose parent is a story and
  epics whose parent is an epic; a task sits in its story's epic block, and a child epic gets its
  own block and counts toward its parent epic's status. An epic's `done` follows its own
  lifecycle, like every other item's, so the file never contradicts the map; its children only
  decide `in-progress` against `backlog` while it is open.
- **Drift is compared in LF**, as `refresh` compares legacy stubs, so a CRLF checkout is not drift;
  an unreadable file or a directory at the path is a finding, not a traceback.
- **Keys are `<id>-<slug>`, slug cut at a hyphen within 48 characters**, so keys stay unique by ID
  and readable. BMad's `epic-N` / `N-M` numbering was rejected: it encodes hierarchy, which the ID
  scheme forbids.
- **No `in-progress` or `review` for stories.** Neither is derivable from the map without asking
  GitHub about pull requests; that would put the network in a local render.

### Do not implement

- No hand-edited status, no retrospective or `action_items` sections.
- No GitHub calls from the render; it is local and deterministic.
- The readiness report is written in a separate session.

## Review findings

A fresh-context review of the first commit raised these; each is resolved in the follow-up commit.

1. The header said `done` meant the issue is closed, but status comes from the map. The header and
   `docs/bmad.md` now say the map's lifecycle decides and `refresh` copies GitHub's state into it.
2. Epic status mixed a child-derived `done` with the item rule. An epic is now `done` if and only
   if its own lifecycle is completed; tests cover an open epic with every child done
   (`in-progress`) and a completed epic with an open child (`done`).
3. The drift check compared raw bytes with an LF render. Both the check and the rewrite now compare
   in LF; a CRLF copy of a correct file is tested as clean and left as it is.
4. `generated` accepted any string. Only `YYYY-MM-DD` values count, and the value is quoted; tested
   with malformed dates.
5. A non-UTF-8 file or a directory at the path raised. Both are now an audit finding; tested.
6. The Approach claimed each story is read once. Corrected: a typed story is read again by the
   depth check.
7. Test gaps closed: a parent cycle, a parent missing from the map, an epic decided only by a child
   epic, an empty slug from a non-ASCII title with every key unique, and `upgrade --check` and a
   refused `upgrade` leaving the file untouched.
