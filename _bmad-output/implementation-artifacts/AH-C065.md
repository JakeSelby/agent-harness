## Goal

Take the maintainer's own sites out of the release instructions
([#719](https://github.com/JakeSelby/agent-harness/issues/719)).

At HEAD the release instructions tell any agent working in this repository to verify two sites that
only the maintainer can act on. Surface 4 checks the reference site's repin and deployment, and
surface 5 checks a card on the maintainer's personal site
[Source: AGENTS.md#A release is not done at the tag]. `docs/releasing.md` repeats both as steps 8 and
9, and adds site steps to its rollback and status sections
[Source: docs/releasing.md#Reference and personal site]. `docs/compatibility-policy.md` puts a
reference-site pin into the release transaction
[Source: docs/compatibility-policy.md#Failed and partial releases]. That is personal, project-specific
process inside shared instructions. Its premise that a release never needs a card change is also
false. Both sites follow releases from their own repositories.

The release surfaces drop from seven to five. Every instruction to deploy, repin, verify or roll back
either site goes, along with the preflight's opt-in reference-checkout check. The links that only say
the reference site exists stay.

## Acceptance criteria

From the issue's Acceptance section ([#719](https://github.com/JakeSelby/agent-harness/issues/719)):

1. **Given** `AGENTS.md`, **when** an agent reads "A release is not done at the tag", **then** it
   lists five surfaces: source and evidence, release metadata, tag and GitHub release, GitHub About,
   and development resumes. None of them names either site.
2. **Given** `docs/releasing.md` and `docs/compatibility-policy.md`, **when** the procedure,
   rollback, status and release transaction are read, **then** no step deploys, repins, verifies or
   rolls back either site. One informational line says the reference site follows releases from its
   own repository.
3. **Given** `scripts/release_preflight.py`, **when** it is run with `--reference-repo`, **then**
   argument parsing refuses the option. Its remaining checks are unchanged: catalog, `VERSION`, a
   dirty checkout, projection drift, About and on-the-way.
4. **Given** the PRD (UJ path, glossary, FR-12, FR-53 and the addendum), the UX specification and
   the v1 release plan, **when** they describe release surfaces or the publish order, **then** they
   say five surfaces and name no site pin. The PRD and UX folders each carry a memlog entry for the
   change.
5. **Given** the README badge and reference link, the plugin homepage and the About homepage, **when**
   the change lands, **then** they are unchanged.
6. **Given** the branch, **when** `bin/harness lint`, `python3 -m unittest discover -s tests` and
   `bin/harness generate --check` run, **then** all three pass.
