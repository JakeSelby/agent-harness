# AH-E007 — Graduate editor and desktop clients beyond preview

This work item was authored as part of the repository's committed BMad planning system.

## Goal

Give the editor and desktop integrations (Claude Code in VS Code, Codex in VS Code, and the Codex desktop
app) an evidence-based path from preview to stable support, without widening the v1.0.0 release floor.
Completion is observable when each client has either graduated on its own evidence and support promise,
or has a recorded reason why it has not.

The issue says that current qualification evidence is still useful, but stable graduation needs three
more things: an explicit support promise, lifecycle coverage, and repeated evidence from the native
client.

## Scope and requirement coverage

**In scope:** graduation criteria for the three editor and desktop clients, and an independent evaluation
of each against them (#217).

**Out of scope:** the issue says the program is post-v1 and does not block the stable CLI release. PRD
§9.3 lists stable editor and desktop client support among the items out of scope for 1.0.

**Requirement coverage.** `epics.md` lists this epic against FR-7 and FR-70. Checked against the 2026-09-23
PRD:

- **FR-7 Evidence-backed compatibility** (implemented, 0.9): claims reference versioned native evidence
  for an exact runtime, client surface, operating system and source revision. #217's acceptance, that
  each client has independent immutable evidence on every claimed operating system, applies this
  requirement to the editor clients.
- **FR-70 Machine setup, editor settings and templates** (implemented, 0.9, preview): the PRD labels the
  editor surfaces preview. This epic is the path that would lift that label.

## Children

- AH-S098 #217: Define and execute stable client graduation gates (open, no milestone)

#217 names #187 (Claude Code clients) and #188 (Codex VS Code and desktop) as the existing evidence
authority. Both are delivered stories under AH-E001, qualified for 0.9.0.

**Current state at `origin/main`:** `compatibility/catalog.json` is a 0.13.0 candidate. It lists
`claude-code-vscode-macos`, `codex-vscode-macos` and `codex-desktop-macos` as `unqualified` and not
required for release. No graduation criteria are recorded yet.

## Architecture slice

- **AD-4 Evidence-backed compatibility:** every supported target references passing evidence for the exact
  source revision, and the catalog states are `qualified`, `unqualified`, `planned` and `unsupported`.
  Graduation for a client would be a status change backed by that client's own evidence.
- **AD-1 Shared primitive authority:** a capability a runtime lacks is declared in its `capabilities.json`
  and never emulated. This matches #217's rule that unsupported native capabilities are named rather than
  simulated.

## Sequencing

- The epic follows v1.0.0 (AH-E005), and per the issue it must not block it.
- Inside #217: define the graduation criteria first, then evaluate each client independently. #217's
  acceptance says one client cannot stand in for another.
- **Milestones:** the issue has no milestone field, matching `epics.md` ("unscheduled").

## Exit criteria

From #217's acceptance section, all open:

- [ ] Graduation criteria cover install, update, runtime discovery, hooks or equivalent lifecycle
  behaviour, conflict handling, recovery and support ownership.
- [ ] Each client has independent immutable evidence on every operating system it claims.
- [ ] Unsupported native capabilities are named rather than simulated.
- [ ] A client graduates only when its own evidence and support promise pass.
- [ ] Compatibility docs and release notes change status only after acceptance.
