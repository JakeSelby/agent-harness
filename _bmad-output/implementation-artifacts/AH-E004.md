# AH-E004 — Commit BMad as the repository’s public planning system

## Goal

Commit a reproducible, public BMad planning system to agent-harness, without vendoring installer-owned
runtime files or generated skill projections. The issue states four outcomes:

- repository-owned BMad customizations and public artifacts live in this repository;
- the generated runtime and projections stay reproducible and ignored;
- existing GitHub issues gain durable BMad traceability;
- a defensible v1.0.0 release plan is represented in both systems.

The issue notes that this commits the planning system already used to shape the project, rather than
onboarding an unmanaged project. The closing comment (2026-09-21) records all four outcomes delivered.

## Scope and requirement coverage

**In scope:** the installation boundary, the reconstructed product corpus, bidirectional issue
traceability, the v1.0.0 release program, and the traceability fixes and backfill that followed.

**Out of scope:** the closing comment says further BMad tooling work is filed on its own, not under this
epic. The story-file work of 2026-09-23 sits under AH-E012 and the concurrency hardening under AH-E016.

**Requirement coverage.** `epics.md` lists this epic against FR-9. Checked against the 2026-09-23 PRD:

- **FR-9 Traceable work items** (implemented, 0.9): every managed work item has an immutable BMad ID, a
  GitHub issue and links both ways before implementation begins. Its first consequence, that
  `issue-ownership` fails a pull request whose delivery issue is unmapped, is AH-S142 (#378). Its second,
  the worktree-aware `reserve`, is #441, which is outside this epic.

The v1.0.0 program (#193) is a planning deliverable. Its requirements (FR-12, FR-66) are delivered under
AH-E005, not here.

## Architecture slice

- **AD-5 Public planning with the design in the story file:** GitHub owns delivery state, discussion, the
  summary and acceptance evidence; the repository owns the planning corpus. This epic established the
  public-planning half of that rule: the committed corpus, typed IDs, and links both ways. The story-file
  half came later, under AH-E012.

What this epic delivered, as the closing comment records:

- The installation boundary. The pinned install command and the version-control boundary are in
  `docs/bmad.md`.
- The issue map, `_bmad-output/issue-map.json`, maintained by `scripts/bmad_issue_sync.py`.
- The `issue-ownership` check (#378).
- `audit --live`, run daily (#218).
- Parent adoption (#388): a parent GitHub records is adopted rather than overwritten.
