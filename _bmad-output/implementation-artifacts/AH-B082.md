# AH-B082 — hook-composition proves composition from configuration, never from a turn that fires the hooks

The issue carries the summary, discussion and acceptance evidence; this file carries the design.

This work item was authored as part of the repository's committed BMad planning system.
<!-- bmad-sync:end -->

## Reproduction

Round 4 of the 0.13.0 native qualification (`claude-code-cli-macos` and `claude-code-cli-linux`,
client 2.1.280) recorded `hook-composition` as passed, but its observation said the user-owned
`PostToolUse` Write hook survived the sync "though no Write turn was run to fire it". The assessor
ruled it short of step 4 of the procedure in `docs/compatibility.md`, which says "Configuration
defaults are insufficient proof": composition was read from the merged settings table only, and
hook trust and multi-file patches were exercised in no case.

## Root cause

`case_hook_composition` in `scripts/native_acceptance.py` synced a hand-added user hook, read the
merged `PostToolUse` table, and ran one Bash turn for the `grade-bash` deny. No turn used the
client's file-writing tool, so the user hook never fired; the project was not a git repository
with a `## Gate` block, so the stop gate had nothing to judge and logged no trust verdict; and the
deny could pass on the marker text alone with no permission denial recorded.

## Acceptance criteria

1. **Given** a user-owned `PostToolUse` hook for `Write|Edit|MultiEdit` merged by a sync, **when**
   a headless turn writes a file with the client's file tool, **then** the case reads the user
   hook's own log line for that session, tool and file, beside the stop gate's decision row for
   the same session.
2. **Given** the same turn, **when** it writes two files, **then** the user hook's log names each
   file; a file the tool wrote with no hook line fails the case.
3. **Given** an acknowledged bypass and `autonomy=ask`, **when** a turn asks for a Bash write,
   **then** the write is absent, the turn's own `permission_denials` holds the refusal, and the
   decision log or the transcript attributes it to `grade-bash`.
4. **Given** a git workspace with a `## Gate` block that `harness trust` never listed, **when** the
   headless turn stops, **then** the stop gate's logged verdict for that session is `untrusted`
   and its gate did not run, and the client's recorded folder-trust flag is reported as read.
5. **Given** a turn that never calls the file tool, writes one file only, or records no denial,
   **when** the case judges it, **then** it is unverified, never passed.

## Design

The case seeds the project with the gate repository files the `gate-invalidation` case uses and
commits them, registers the user hook for every file-writing tool, and has the hook log the
`session_id`, event, tool and `file_path` from the payload the client gave it. One `Write` turn
creates `alpha.txt` and `beta.txt`; `file_tool_calls` reads its transcript, `patch_verdict` judges
the calls against the files and the hook log, and `gate_verdicts` joins the stop gate's decision
and outcome rows for that session. The deny turn now requires a recorded permission denial and
reads `grade_denied` from the decision log. Rejected: a third turn for trust alone, since the
write turn's Stop already yields the verdict; proving harness `PostToolUse` evidence per write by
making the model write instruction-shaped text the output scanner flags, which would test the
scanner and risk a refusal; driving the Stop coordinator directly, which is a hook call rather
than the native turn step 4 asks for.

## Regression test

`tests/test_native_acceptance_hook_composition.py`.
- **Before the fix:** the driver test fails, since the old case runs one Bash turn and returns an
  observation holding "no Write turn was run", and the reader functions do not exist.
- **After the fix:** all 13 pass, covering the pass path, a silent user hook, no file-tool call, a
  one-file turn, a trusted verdict, a missing denial and an unattributed denial.
