## Story

As the operator of a native qualification round, I want every scripted case to call `bin/harness`
with the arguments and exit codes the CLI actually has, so that a case's verdict is about the
behaviour it names and never about its own driver.

## Context and value

The first live run of the twelve scripted cases in `scripts/native_acceptance.py` (0.13.0 round,
`claude-code-cli-macos` and `claude-code-cli-linux`, runner at `d426d6d`) failed three cases on
the driver, before the behaviour under test was reached:

1. **role-confinement** called `harness role run <name> --workspace … --prompt-file …` with no
   `--runtime`. `cmd_role` requires a role, `--runtime` and `--prompt-file`; the run exited 1
   with "role run requires a role, --runtime and --prompt-file (use - for stdin)", expected 0.
2. **bidirectional-handoff** passed `task_contract()`, the JSON text itself, as `--input`.
   `cmd_task` reads `Path(args.input).read_text()`, so the save raised FileNotFoundError on the
   JSON string. Its argparse help, "JSON task contract; never executed", does not say it is a path.
3. **migration-uninstall** expected `harness uninstall` to exit 2 with "user changes preserved".
   The CLI exits 2 only when it preserves a conflict, and prints that phrase only for a
   harness-owned file or key the user changed; the case made no such change, so it exited 0.

The existing unit tests fed the drivers' values straight into `lib/harness_core`, so none of them
met the CLI's argument parsing. Qualification for 0.13.0 cannot close with these three open.

## Acceptance criteria

1. **Given** a claude-code or codex home, **when** the role-confinement driver calls
   `harness role run`, **then** it passes `--runtime` equal to that home's own runtime and the
   CLI's parser and `cmd_role` accept the argv and reach the worker.
2. **Given** a task repository, **when** the bidirectional-handoff driver saves the task record,
   **then** it writes the contract to a file in the disposable home, outside the repository,
   passes that path as `--input`, and the real CLI writes revision 1, then 2, and refuses a
   stale revision 1 with "task revision changed since --revision 1".
3. **Given** a record saved that way, **when** `harness task show` reads it, **then** its status
   is `current`, because the contract file is not a working-tree change.
4. **Given** `harness task --help`, **when** it is read, **then** `--input` is described as a
   path to a JSON task contract, and what `task save` accepts is unchanged.
5. **Given** a sync with `--adopt` over a user's own files, **when** the user changes the
   harness-owned `outputStyle` setting by hand and `harness uninstall` runs, **then** it exits 2,
   reports "user changes preserved" for that key, keeps the user's value and own settings key,
   and restores every adopted file byte for byte.
6. **Given** the old drivers, **when** the new tests run, **then** each of the three mismatches
   fails the suite.

## Design

### Approach

- `role_run` passes `--runtime home.runtime`; the runtime comes from the client spec the home
  was built from, never a constant.
- A `save_task` helper writes `task_contract()` to `task-contract.json` in the home root and passes
  that path; all three saves in the case use it.
- `case_migration_uninstall` gains a step between the adopting sync and uninstall:
  `hand_edit_owned_setting` confirms the ownership store holds `outputStyle` for the client's
  `settings.json`, then sets it to `Explanatory`. The uninstall assertions then read exit 2, the
  preservation line naming the key, the kept value and the user's own key.
- `bin/harness`: the `task --input` help reads "path to a JSON task contract; never executed" with
  metavar `FILE`.

### Decisions and alternatives

1. **Uninstall: create the conflict, not relax the expectation.** The case exists to prove an
   uninstall is safe to recommend. Expecting exit 0 and the generic "uninstalled; …" line would
   match the CLI but prove nothing about a user's hand edit; creating one exercises the
   preservation path, which is the behaviour at stake. Rejected: expecting exit 0.
2. **Hand edit a harness-owned JSON key, not a linked file.** Harness files under the client
   directory are symlinks into the checkout, so editing one through the link would write into the
   checkout. `outputStyle` is owned, scalar, and `Explanatory` is a built-in Claude Code style, so
   the closing native turn still starts cleanly. The key is read from the store, so the case
   reports unverified instead of passing if the harness stops owning it.
3. **The contract file lives in the home root, outside the task repository**, so it never changes
   the working-tree fingerprint the record's staleness check reads.
4. **Tests go through the CLI.** `role run` is driven through `harness.main` with only
   `workers.run` stubbed, since a real worker launches a client; `task save` and uninstall run the
   real CLI in a disposable home, with only the uninstall case's closing native turn stubbed.

### Do not implement

- No change to what `task save --input` accepts, and no JSON-on-the-command-line mode.
- No change to `cmd_role`, `cmd_uninstall` or the reconcile store's exit codes or messages.
- No live client run; the unit tests and the runner's self-tests are the evidence.
