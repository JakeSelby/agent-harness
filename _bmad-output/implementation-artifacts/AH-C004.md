## Goal

Define and verify exactly which BMad files agent-harness commits, ignores, regenerates and publishes.
Install BMM at the pinned version the workspace is compatible with, add public credit, and enforce the
repository workflow through BMad's supported customizations. This was the first child of #189, which
commits BMad as the repository's public planning system without vendoring installer-owned runtime files
or generated skill projections.
[Source: https://github.com/JakeSelby/agent-harness/issues/190]
[Source: https://github.com/JakeSelby/agent-harness/issues/189]

## Acceptance criteria

1. **Given** the repository, **when** it is inspected, **then** its durable BMad customizations under
   `_bmad/custom/` are tracked and the generated BMad apparatus is not.
2. **Given** the team configuration, **when** a workflow writes a public artifact, **then** it stays inside
   the repository.
3. **Given** every team workflow, **when** it loads, **then** it loads the single governance source.
4. **Given** the installation, **when** it is reproduced, **then** it uses the pinned BMad 6.12.0 release.
5. **Given** the README and notices, **when** they are read, **then** BMad is credited without implying
   endorsement.

The issue records no acceptance section; these criteria are taken from the PR's description and its
tests.
