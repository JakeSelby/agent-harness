# AH-E012 — Re-baseline the BMad corpus and make story files the design record

<!-- bmad-sync:begin -->
- **GitHub issue:** [#616](https://github.com/JakeSelby/agent-harness/issues/616)
- **Primary parent:** None
- **State:** active

The issue carries the summary, discussion and acceptance evidence; this file carries the design.

This work item was authored as part of the repository's committed BMad planning system.
<!-- bmad-sync:end -->

## Goal

Re-baseline the BMad planning corpus from the repository, the research and the design record, and make
each story file the home of the design depth that had been living in issue bodies and uncommitted plan
files. Completion is observable against the issue's three acceptance items:

- the brief, PRD, UX specification and spine describe the product on `main`, and each passes its BMad
  reviewer gate;
- every open issue belongs to an epic, and every story file carries the design sections for its kind;
- `issue-ownership` fails a pull request whose delivery story lacks its design sections.

The issue records the starting point. The corpus had been reconstructed once, on 2026-09-19, and had not
moved since. The brief still described the 0.9 series, and all 330 story files were 26-line stubs
pointing back at their issues.

## Scope and requirement coverage

**In scope,** from the issue's Scope section:

- Promote existing research into BMad research artifacts.
- Re-baseline the brief, PRD, UX specification and architecture spine through BMad's update workflows.
- Make story files design records: typed rich templates, a managed issue block the sync tool preserves, a
  lossless upgrade of the stubs, and a CI depth check on each pull request's own story.
- Add a repository rule that routes every planning and delivery operation through its BMad skill and keeps
  the corpus current.
- Re-derive the epics, enrich every story, run the readiness check and add a derived sprint status.

**Out of scope:** concurrency hardening of the sync tool, which is AH-E016.

**Requirement coverage.** `epics.md` lists this epic against FR-9, FR-64 and FR-65. Checked against the
2026-09-23 PRD:

- **FR-9 Traceable work items** (implemented, 0.9): kept current here through the ID reservations (#617's
  PR) and the reparenting (#622).
- **FR-64 Story files as design records** (planned, v0.14.0, #620): delivered by AH-S206 (PR #629).
  Enriching the corpus runs through AH-T014 to AH-T025.
- **FR-65 A current corpus** (planned, v0.14.0, #621 and #623): the routing rule is AH-S207 (PR #631). The
  derived sprint status, and `audit` reporting zero drift against `sprint-status.yaml`, are AH-S208 (#623),
  which is open.

## Architecture slice

- **AD-5 Public planning with the design in the story file:** GitHub owns delivery state, discussion, the
  summary and acceptance evidence, and the story file owns the design. The sync tool owns only the
  frontmatter, the H1 and the managed block, and a legacy stub is recognised positively. The spine records
  that the tool contract merged in #629.
- **AD-18 Shared-machine concurrency and writes:**
  - Story files and the issue map are among the files a whole-file rewrite must write atomically, and the
    sync tool already does (#629).
  - A batch rewrite such as `upgrade` restores what it already wrote when a later write fails.
  - ID reservation surveys every reachable issue map.

## Sequencing

- Research (#617) came first, so that the re-baselined PRD and spine could cite it. Its PR also carried
  the ID reservations for the epic tree.
- The brief and PRD (#618) came next, then the UX specification and spine (#619). The story-file tooling
  (#620) and the repository rule (#621) ran beside them.
- The epic re-derivation (#622) followed the PRD and spine, and the enrichment batches follow the new
  map.
- The readiness check and the derived sprint status (#623) close the epic.
- Enrichment is applied batch by batch together with `upgrade`, so a skeleton full of placeholders never
  lands on `main` on its own (`docs/bmad.md`, "Story files").
- **Milestones:** the issue's milestone field is v0.14.0, matching `epics.md` and PRD §9.2 ("rich story
  files and a current BMad corpus (#616)").
