# AH-B051 — A plan file reaches no native plan view, so the reviewer is asked to approve a document they cannot open

## Reproduction

1. Run `/plan`. It writes the Review Card to `plansDirectory` (`.agent-harness/plans`) and posts the
   review message with a workspace-relative markdown link.
2. Look for the plan in the desktop app's plan pane: it never appears.
3. The reviewer is asked to reply `build` to a document they cannot see.

[Source: https://github.com/JakeSelby/agent-harness/issues/436]

## Root cause

Two causes, and the issue rules out the path settings: `plansDirectory` was `.agent-harness/plans` in
both the settings template and the live settings, and the file landed there correctly.

1. The plan pane shows only plans registered through plan mode. `primitives/workflows/plan.md` wrote the
   file directly and never entered plan mode, so nothing registered it. A markdown link in chat is a
   path, not a rendering.
2. When a file is opened by path instead, a workspace-relative path is rejected and only an absolute one
   resolves. The rejection is silent, so a single attempt leaves the reviewer with nothing and no error.

## Acceptance criteria

1. **Given** a plan written without plan mode, **when** the review message is about to be posted,
   **then** the chat-message contract requires putting the plan file on screen first, on revision rounds
   too.
2. **Given** a plan opened by path, **when** the contract is followed, **then** it warns that a relative
   path may be rejected silently and prefers an absolute one.
3. **Given** a runtime with no file viewer, **when** the plan is posted, **then** the message says how to
   open the plan instead.
4. **Given** the change, **when** `harness generate --check` runs, **then** `claude/commands/plan.md` is
   the regenerated projection of `primitives/workflows/plan.md`.

## Design

**Approach.** The issue split the fix in two. This issue's PR delivers the fallback: `plan-authoring`
requires opening the file where the reviewer reads before posting, and the `plan` workflow's step 4
opens the plan with the reason inline so it does not read as optional polish. It is runtime-neutral, so
it covers Codex, which has no plan mode, and plans written outside `/plan`.

**Decisions and alternatives.** The primary fix, making `/plan` enter plan mode and finish through
`ExitPlanMode`, was deferred to a follow-up; the issue notes that `ExitPlanMode` already reads the plan
from a file and `useAutoModeDuringPlan` was already set, so the two designs agree. That follow-up was
delivered as #439 (PR #590). In the code at `origin/main`, plan mode is now the primary path and this
fallback survives as the "No plan mode" step of `primitives/workflows/plan.md` and the "Without plan
mode" paragraph of `plan-authoring`.

**Do not implement.** Changing the path settings, which the issue found correct.
