## Story

As a developer evaluating agent harnesses, I want the repository and reference site to state one
accurate, differentiated category position, so that I can tell what Agent Harness is and what it does
not claim to be.

## Context and value

The issue asked to align the repository and reference site on "a user-owned, stance-driven agent
harness whose switchable personal stances project a developer working style across supported runtimes".
Its parent is recorded as #212. An amendment comment dated 2026-09-21 (for #457) revised two acceptance
lines on the evidence in `docs/field-scan.md` (#459): other projects ship switchable behavioural
variants, so switchable stances became a supporting mechanism and measured rules the signature one; and
`model-provider-agnostic` left the headline in favour of naming Claude Code and Codex. The issue was
closed on 2026-09-23 with a comment saying it was superseded by #468, which repositioned the front door
on measured rules.
[Source: https://github.com/JakeSelby/agent-harness/issues/230]

## Acceptance criteria

As amended on the issue on 2026-09-21:

1. **Given** the product copy, **when** it names the category, **then** it uses `user-owned agent
   harness`.
2. **Given** the copy, **when** it names the signature mechanism, **then** it is measured rules, with
   switchable personal stances as a supporting mechanism (revised from the original, which made stances
   the signature).
3. **Given** the architecture explanation, **when** it is read, **then** it is a cross-runtime
   working-style layer with native runtime projections.
4. **Given** the headline, **when** it names runtimes, **then** it names Claude Code and Codex rather
   than leading with `model-provider-agnostic` (revised from the original, which kept that phrase as a
   supporting qualifier).
5. **Given** any copy, **when** it is read, **then** it makes no multimodal, multi-model or
   first-invention claim.
6. **Given** the README, product metadata, reference-site copy and discoverability metadata, **when**
   they are compared, **then** they are consistent and preserve current capability and compatibility
   boundaries.

## Design

### Approach

No pull request closes this issue. The amendment says the literal copy lands in #458. The closing
comment says #468 led the front door with measured rules ("Find out which of your agent rules actually
fire") and #516 corrected the remaining figures; the user-owned, stance-driven framing lives as the
supporting story under that headline in `product.json`, the README and the reference site, not as the
primary category phrase. At `origin/main`, `product.json`'s description opens "A user-owned agent harness
with a measurement loop", and its `github_description` and the README heading lead with the
measured-rules line.

### Decisions and alternatives

- **Stances demoted to supporting:** three other projects ship switchable behavioural variants, and
  three of this repository's nine axes bind to enforcement.
- **Measured rules as the signature:** a detector per rule file, lint that fails an unmeasured rule, and
  hit rate per rule by repository and by selected variant.
- **Runtimes named instead of `model-provider-agnostic` in the headline.**

### Do not implement

- Any claim that Agent Harness routes or serves models.
- Multimodal, multi-model or first-invention claims.
