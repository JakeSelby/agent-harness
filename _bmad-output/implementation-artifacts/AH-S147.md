# AH-S147 — Write down how Codex and Linux qualification targets are provisioned and where they run

## Story

As a release qualifier, I want the provisioning contract for every Codex and Linux qualification target
written down, with a probe that fails fast when a precondition is missing, so that a release session can
establish the preconditions without discovering them.

## Context and value

Both Codex targets and both Linux targets were qualified for v0.11.1, but nothing in the repository recorded
how or where, and neither could be run from the owner's machine as it stood. The issue records, as found on
2026-09-21: `CLIENTS` in `scripts/native_acceptance.py` held only the two Claude Code targets, so both Codex
targets were driven by hand (#336); no `codex` binary was installed; the v0.11.1 evidence records
`codex-cli-macos` at runtime 0.154.0-alpha.6.2 and `codex-cli-linux` at 0.155.1; and no document named the
Linux host. This blocked the first step of any release. The issue also carries a decision: a release that
cannot qualify the Codex or Linux targets narrows the stable support floor v0.11.1 established, and that
needs a deliberate answer, not a silent skip.
[Source: https://github.com/JakeSelby/agent-harness/issues/408]

## Acceptance criteria

1. **Given** `docs/compatibility.md`, **when** it is read, **then** it names the binary source, the auth
   method and the host for every required target.
2. **Given** a release session, **when** it starts, **then** it can establish the preconditions without
   discovering them.
3. **Given** a missing precondition, **when** the smoke tier's credential step runs, **then** it fails fast.

## Design

### Approach

- **The contract, in `docs/compatibility.md`:** every round to date ran on the owner's Mac. The Codex binary
  is the one bundled in the ChatGPT desktop app, put on `PATH` and logged in through the ChatGPT session,
  not an API key. The Linux targets run in a Docker container on that same Mac.
- **The container recipe,** `scripts/linux-target.Dockerfile`, rebuilt from the image history the 0.11.x
  rounds used and pinned to the client versions the 0.11.1 Linux records name.
- **The probe:** the smoke tier's credential step takes `--targets` and fails at once on a missing client
  binary, a missing Codex login or a stopped Docker daemon, through the new
  `lib/harness_core/target_preconditions.py`. CI still skips the credential step, which belongs on the
  qualification host.
- **The runbook** gains an ordered "Target hosts" section.

### Decisions and alternatives

- **Unknowns are stated, not guessed:** no evidence record says how the Linux Codex target logged in; the
  doc says so, and the runbook suggests device auth inside the container, labelled as a suggestion.
- **Narrowing is a stated decision:** a release that cannot qualify Codex or Linux narrows the support floor
  as a stated decision, not by omission.
- **Docker check in its own module,** because `credentials.py` is tested to import no subprocess.
- **Host-aware defaults (after review):** with no targets named, the probe checks what this host can run,
  and the other platform's targets are skipped, not failed.

### Do not implement

Not recorded in the issue or pull request. The PR names one follow-up it left open: the runner's disposable
`CODEX_HOME` never receives the session login, so Codex targets stay hand-qualified until the runner can use
it.
