## Story

As the release maintainer, I want a native acceptance runner that runs a client's probes in a
disposable configuration home and writes evidence in the repository's own shape, so that qualification
is repeatable and its evidence comparable across releases.

## Context and value

Each release re-derived the native procedure by hand, which the issue calls slow, unrepeatable and hard
to compare. The first automated native run of the cost posture layer from a clean home confirmed
routing, the budget sentence, per-role telemetry, the pre-existing-session guard and the null variant in
about forty seconds, and exposed a usage-feed defect no unit test had (filed as #272). Part of #268.
[Source: https://github.com/JakeSelby/agent-harness/issues/273]

## Acceptance criteria

1. **Given** a case, **when** the runner records it, **then** it is `passed` only when an assertion on
   natively observed behaviour holds; anything else is `failed` or `unverified` with its reason.
2. **Given** the `cost-posture` case on the Claude Code CLI on macOS, **when** it runs, **then** it is
   automated, and every other case is registered `unverified` until it is automated.
3. **Given** any run, **when** it executes, **then** no credential is read, copied or written: provider
   authentication passes through the environment by name, and output redacts home paths and secret
   shapes.
4. **Given** a dirty checkout, **when** the runner starts, **then** it refuses; `--dry-plan` launches no
   client.
5. **Given** the runner's output, **when** it is validated, **then** it passes the evidence validator.
6. **Given** the change, **when** it lands, **then** no runtime-source path changes and no test launches
   a client.

## Design

### Approach

`scripts/native_acceptance.py` builds a disposable configuration home, runs the client's probes and
writes evidence in the repository's shape. The feed check is strict: the orchestrator's context must
carry the finished worker's line with numbers and the budget clause, and `spend unknown` fails the case
and quotes the line.

### Decisions and alternatives

- **Environment-passed authentication:** a disposable Claude Code home cannot use a keychain login, so
  provider authentication passes through the environment by name.
- **Re-anchored config pointers:** with `HOME` redirected, the provider's config-file pointers are
  re-anchored, or the client hangs on lookup.
- **Unverified, never passed:** a case not yet automated is recorded `unverified`.

### Do not implement

- Any runtime-source change.
- Automation of the other ten cases; they stay `unverified` here. [ASSUMPTION: that automation is the
  "drivers for all eleven native cases" FR-52 lists as unreleased under #336.]
