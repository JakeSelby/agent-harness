## Goal

Prove the Python 3.9 floor on every pull request and in the merge queue, so a 3.9 syntax error cannot
merge and surface only at release.

The issue states the gap: CI runs the suite on the runner's system Python only, and the 3.9 floor is
proved locally and by the release lifecycle runs.

At `origin/main`, `.github/workflows/ci.yml` runs on `push` to `main`, `pull_request` and
`merge_group`. Its comment in the `smoke` job says: "No job in this workflow pins an interpreter, so
this one runs the same Python as `test`; the 3.9 floor is proved by running the suite locally under
it." `AGENTS.md` asks contributors to "keep the code free of syntax newer than 3.9", and says tests run
under the system Python 3.9 and under a current Python.

## Acceptance criteria

From the issue:

1. **Given** a pull request that uses syntax newer than Python 3.9, **when** CI runs, **then** a
   required check fails.
2. **Given** the merge queue, **when** a queued pull request is tested on the merge commit, **then**
   the same 3.9 check runs there. [ASSUMPTION: from the scope line "on every pull request and in the
   merge queue"; the acceptance section names only pull requests.]

## Tasks

- [ ] Add a CI job that runs the suite, or at least a syntax check, under Python 3.9 (AC 1).
- [ ] Trigger it on `pull_request` and `merge_group` (AC 2). The workflow already has both triggers.
- [ ] Add the job to the `main` ruleset's required checks, so a failure blocks the merge (AC 1).
  [ASSUMPTION: the issue says "a required check"; changing the ruleset is a repository-settings action
  outside the diff.]
- [ ] Prove it: a deliberate 3.9-incompatible change fails the job.

Scope from the issue: "Run the suite, or at least a syntax check". Which one is not decided.
