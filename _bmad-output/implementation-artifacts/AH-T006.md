## Goal

Grow the replay task set past the size at which the harness can break even. The issue records that
three of the four tasks in `benchmarks/tasks.json` were far below that size, so the set mostly measured
the harness's standing overhead rather than its working efficiency: observed sizes on the first live set
were `hook-inventory` 11 API calls, `codex-pre-allow` 30, `hook-ids` 44 and `link-alias` 90, and only
`link-alias` was in a range where the harness could win. It also found two reps per cell too few, since
the within-cell spread on `hook-ids` was larger than the effect being measured. The wanted outcome was
tasks at `link-alias` size or larger, drawn from solved issues whose merged PR added tests.
[Source: https://github.com/JakeSelby/agent-harness/issues/431]

## Acceptance criteria

1. **Given** the task set, **when** the bare arm runs, **then** at least two tasks exceed 80 API calls.
2. **Given** each task, **when** its check runs, **then** it fails at the parent sha and passes at the
   good sha, and every fixture passes the repository gate before any arm runs.
3. **Given** the rep count, **when** it is set, **then** it is justified against the measured within-cell
   spread rather than chosen.
4. **Given** the manifest change, **when** history is read, **then** a new series starts in
   `benchmarks/history.jsonl` and the 0.11.1 rows stay readable beside it.

**Undelivered or unverified.** The PR evidences criterion 2 (`--verify-tasks`: `verified 8 task(s),
0 error(s)`) and states that the manifest change starts a new series (criterion 4). It records no bare-arm
call counts for the new tasks (criterion 1) and no rep-count justification (criterion 3); neither is
recorded in the issue or pull request. The issue was closed as completed by the PR.

## Dev notes

- **Design, from the PR.** Tasks were chosen by what their held-back tests touch rather than by commit
  date. Three new tasks have held-back files that, grepped at their good commit, read none of
  `claude_dir`, `CLAUDE_CONFIG_DIR`, `HARNESS_HOME` or `Path.home()`, so they are `clean`. `cost-variants`
  reads `HARNESS_HOME` in `test_posture.py` and is kept as a `control`, so the leak's cost is measured on
  a level field instead of inferred. `link-alias` is labelled `leaks`, because its module leaks even
  though its scored class does not. Prompts are the closing issues' bodies trimmed of implementation
  hints, ending with a profile-independent exit line; no prompt demands the full suite. The runner is
  untouched; it already ignores unknown manifest keys.
- **Owner comment on the issue (2026-09-22):** #524 adds a cache axis to the same replay; if the task set
  grows past break-even, the cache arms should be part of that run rather than a second one.
- **Bound requirements and decisions:** FR-56 (Live replay against a bare arm). AD-12 (Measurement
  invariants), which binds FR-56 and prevents comparisons contaminated by profile leakage.
- **Files touched:** `benchmarks/tasks.json`, `tests/test_cost_bench.py`, the issue map and this story file.
- **Testing:** `ManifestTests` widened to six issue and two synthetic tasks, and
  `test_every_task_declares_a_known_leak_class_the_loader_ignores` asserts every entry's `leak_class` and
  that only `link-alias` and `cost-variants` are non-clean.
