## Story

As a developer receiving review findings, I want a bounded check that one finding names a concrete
problem, its consequence and enough detail to investigate, so that vague feedback in a valid review
format is caught. Closed as not planned on 2026-09-21; this file records the proposal as history.

## Context and value

Vague review feedback burdens users even when it appears in a valid review format. The issue proposed a
self-contained experiment, called its effectiveness on this workload unverified, and said it was neither
a first-release dependency nor an implementation authorization. It was one of seven additional bounded
experiments (#156 to #162); the 2026-09-21 epic re-scope closed it with the other prose-level checks,
because nothing consumed those answers and nothing could score them.
[Source: https://github.com/JakeSelby/agent-harness/issues/160]
[Source: https://github.com/JakeSelby/agent-harness/issues/135]

## Acceptance criteria

As proposed, not delivered:
1. **Given** the shared provider and versioned pack contracts, **when** an input is judged, **then**
   each criterion returns a typed decision with explicit abstention and unavailable handling.
2. **Given** a pack's declared input limit, **when** an input is oversized or missing, **then** it stays
   unverified rather than being silently truncated, and no transcript or repository is uploaded.
3. **Given** formatting, counts and schema, **when** they are checked, **then** deterministic code
   checks them.
4. **Given** fixtures of actionable concise findings, generic advice, style preferences mislabelled as
   defects, and findings useful without a proposed fix, **when** they are judged, **then** each
   criterion is scored separately.
5. **Given** labels fixed before evaluation and a held-out split, **when** the pack is evaluated,
   **then** misses, false alarms, abstentions, errors, latency and available cost are reported, and
   ordinary tests stay offline with live tests opt-in and budgeted.
6. **Given** public or synthetic fixtures first and #137's outbound controls, **when** the provider
   fails, **then** current behaviour is preserved, and no enforcement is on by default before
   workload-specific validation.

## Design

### Approach

Input is one short review finding and a rubric for problem specificity and stated consequence. The pack
judges whether the finding describes a concrete problem, its consequence, and enough detail to
investigate.

### Decisions and alternatives

- **Closed as not planned (2026-09-21)** in the epic re-scope.
- Dependencies as proposed: #136, #137 and #138, with #140 only for later automatic runtime delivery.

### Do not implement

Deciding that a bug exists, inspecting a codebase, assigning factual severity, or requiring a fix when
diagnosis alone is enough. No generic quality score, inferred permissions, model training or live
configuration changes; publishing the provider's performance results stays subject to its terms.
