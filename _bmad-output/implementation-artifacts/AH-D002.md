## Context

`harness stances --json` resolves the full ladder: the defaults, the user configuration, the file named by `HARNESS_PROJECT_CONFIG`, then `HARNESS_STANCE_*`. `harness sync` projects only the user-level selection into the client's instruction files. A project file or a session variable therefore changes what the hooks decide, because they resolve the ladder at run time, but not the stance text the model reads, because that text is a link written at sync. The two halves of a stance, the prose the model follows and the switches the hooks read, can disagree within one session ([#276](https://github.com/JakeSelby/agent-harness/issues/276)).

The gap was found while automating the `stance-switch` qualification case, which could not observe a project override natively ([#276](https://github.com/JakeSelby/agent-harness/issues/276)).

The 2026-09-23 PRD lists it as open question 4, "Selections a native client cannot read", blocking FR-2 and needed by v0.14.0, and its UJ-2 edge case says "The linked stance text stays user-level until #276 is decided" [Source: _bmad-output/planning-artifacts/prds/prd-agent-harness-2026-09-23/prd.md]. FR-2's status records the related defect that `sync` ignores `HARNESS_STANCE_*` variables that `harness stances` honours (#294).

What exists on `main`: when a session override or `HARNESS_PROJECT_CONFIG` is present, the session-start hook runs `harness stances --json` and adds an "Effective session stance" line, with the variant's behaviour text, for each dimension that differs from the user configuration [Source: policy/hooks/harness-session.py#resolved_overrides]. The "Effective session stance" text first appears in commit ca5547f, titled with PR #106, which merged on 2026-09-19 and whose file list includes `policy/hooks/harness-session.py` ([PR #106](https://github.com/JakeSelby/agent-harness/pull/106)); this issue was created on 2026-09-21 ([#276](https://github.com/JakeSelby/agent-harness/issues/276)). [ASSUMPTION: this partly implements option 2 below for the environment-driven case; neither the issue nor any later record says whether it satisfies the decision.]

## Options

1. **Document it as the contract.** Prose is user-scoped and sync-time; project and session selections affect hooks only. The issue calls it the cheapest, and says it leaves a real gap for stances that are mostly prose.
2. **Inject the resolved stance text at session start** when the project or session stance differs from the synced one. It keeps sync simple, costs context each session, and must stay within the spirit of the always-loaded budget.
3. **Project a per-project instruction file at sync** for directories that carry a project config. The issue calls it closest to native, and notes it needs ownership rules for files inside repositories the user does not control.

[Source: [#276](https://github.com/JakeSelby/agent-harness/issues/276)]

## Decision

Open: one option is chosen and documented in `docs/sync-model.md` and `docs/primitive-authoring.md`, and the `stance-switch` and `custom-stance` qualification cases either observe a project and a session selection natively or state precisely why that scope is verified another way ([#276](https://github.com/JakeSelby/agent-harness/issues/276)).

## Consequences

- Until decided, a project or session selection can leave the model reading user-level stance text while the hooks act on another variant ([#276](https://github.com/JakeSelby/agent-harness/issues/276)).
- The decision unblocks FR-2 per the PRD's open question 4.
- AD-6, One effective policy for every consumer, requires every consumer to ask `posture.py` for the effective policy; linked stance text read by the model is a consumer that does not today. [ASSUMPTION: the spine does not name #276; the fit is inferred from AD-6's rule.]
- Option 3 would need ownership rules under AD-3, Reversible configuration ownership. [ASSUMPTION: inferred from the issue's own caveat about repositories the user does not control.]
