## Story

As a developer depending on the harness after 1.0, I want a public contract that says which interfaces
SemVer protects and how deprecations, migrations, exceptions and failed releases are handled, so that I
know what a later release may change and what I must do when it does.

## Context and value

Step 2 of the v1.0.0 release program, under epic #206; existing authority is #94, #95 and the compatibility
catalog. v1 needs a promise a maintainer can defend, and that promise has to distinguish source
compatibility, generated-file shape, CLI behaviour, support status and evidence validity rather than
freezing every internal file.
[Source: https://github.com/JakeSelby/agent-harness/issues/208]
[Source: _bmad-output/planning-artifacts/v1-release-plan.md#Step 2 — Publish the compatibility contract]

## Acceptance criteria

1. **Given** the public SemVer scope, **when** it is read, **then** it names each protected interface and
   the interfaces deliberately left internal.
2. **Given** a deprecation, **when** it is announced, **then** it names notice, migration guidance and
   removal timing.
3. **Given** a configuration or generated-file migration, **when** it is defined, **then** it states
   ownership, conflict, rollback and uninstall behaviour.
4. **Given** a breaking change or a security fix, **when** it needs an exception, **then** the exception
   rule is explicit.
5. **Given** a failed or partially published release, **when** it is recovered, **then** a versioning and
   recovery rule applies and immutable tags are never moved.
6. **Given** release notes, **when** they are generated, **then** they link to the policy and include the
   required migration actions.
7. **Given** the frozen candidate, **when** it goes to audit, **then** it includes the final policy bytes.

## Design

### Approach

`docs/compatibility-policy.md` holds the contract, in sections for stable public interfaces, versioning
rules, deprecation and removal, configuration and generated-file migration, security and external-runtime
exceptions, and failed and partial releases. Versioned migration metadata lives in
`compatibility/migration.json`, and `scripts/release_notes.py` generates migration guidance from it, so
each candidate carries explicit actions and recovery steps.
[Source: https://github.com/JakeSelby/agent-harness/pull/221] [Source: docs/compatibility-policy.md]

### Decisions and alternatives

- **Generate migration guidance from versioned metadata** rather than write it by hand per release.
- **Never move a tag:** a failed release is marked and a corrective release follows the SemVer policy.

### Do not implement

- The candidate freeze, lifecycle proof, audit and publication (#207, #209, #210, #211).
