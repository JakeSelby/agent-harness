## Story

As a developer whose repository relies on CI or live integration tests, I want a verification policy that is separate from the test-writing stance, so that I can choose local-first, CI-authoritative or hybrid verification without contradicting the rules that tell the agent which tests to write.

## Context and value

The fixed rules require local gates before any pull request, the exact CI commands run locally, and no new live-service tests, even where another workflow suits the repository ([#118](https://github.com/JakeSelby/agent-harness/issues/118)). These still sit in the always-loaded `primitives/rules/verification.md` as fixed prose, and the `testing` stance covers only test-writing (`off`, `pragmatic`, `required`) [Source: primitives/rules/verification.md] [Source: primitives/stances/testing/].

The epic's 2026-09-21 assessment rated the story Not delivered: there is no `verification` dimension in `STANCE_NAMES` ([#116 comment](https://github.com/JakeSelby/agent-harness/issues/116)). That still holds on `main`: `STANCE_NAMES` in `bin/harness` and the directories under `primitives/stances/` carry no `verification` dimension.

## Acceptance criteria

1. **Given** each verification variant, **when** its guidance is rendered, **then** it states draft pull-request readiness and merge readiness separately, and `ci-authoritative` never reports an unrun check as passed.
2. **Given** a selected variant, **when** build, review and commit guidance and the gate integration are rendered, **then** none of them contradicts the selected alternative.
3. **Given** a local failure, absent CI, pending or failed CI, an explicit-live opt-in, or missing credentials, **when** verification is reported, **then** each case is tested and an unknown result is reported separately from a pass or a failure.

## Design

### Approach

The issue proposes a `verification` dimension with the variants `local-first`, `ci-authoritative` and `hybrid`, `local-first` being the migration default. `testing` stays the test-writing policy. A separate integration-test selection offers `fixtures-only`, `explicit-live` and `repo-native`; live execution requires authorized endpoints and credentials. Repository merge requirements stay authoritative ([#118](https://github.com/JakeSelby/agent-harness/issues/118)).

The plan lists the same variants and adds that the integration-test choice carries "no implied endpoint authorization" [Source: docs/plans/stance-completeness.md#Step 3 — Existing opinions].

### Decisions and alternatives

- `local-first` is the default, so existing behaviour is the migration path ([#118](https://github.com/JakeSelby/agent-harness/issues/118)).
- `fixtures-only` is the default integration-test choice [Source: docs/plans/stance-completeness.md#Step 3 — Existing opinions].
- No other alternative is recorded in the issue or pull request.

### Do not implement

- Do not let a variant override a repository's merge requirements or a native restriction ([#118](https://github.com/JakeSelby/agent-harness/issues/118) Boundaries).
- Do not treat a live-test opt-in as authority to reach an endpoint that was not authorized.
- Do not sync an unmerged candidate into the live installation.
