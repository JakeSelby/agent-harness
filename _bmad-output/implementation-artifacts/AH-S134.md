## Story

As a developer who wants usage data in an observability backend, I want the harness to export ledger
rows as OTLP log records, with replay, so that I get dashboards, SQL or a team view without parsing the
local file, and can rebuild or backfill the backend at any time.

## Context and value

The usage ledger is a local file, so getting its rows into a backend meant parsing it yourself. Native
runtime telemetry does not fill the gap: it is a live stream with no replay, it knows nothing of rule
hits, stances, reroutes or budgets, and it cannot backfill history.
[Source: https://github.com/JakeSelby/agent-harness/issues/353]

## Acceptance criteria

1. **Given** a `telemetry` block in `config.json`, **when** it is absent or off, **then** nothing
   changes and no network code runs.
2. **Given** export on, **when** a row is written, **then** it is sent as one OTLP/HTTP JSON log record,
   standard library only, with the row's scalar fields, a stable `harness.row_key`, the harness version
   and one `harness.<stance>` per recorded stance.
3. **Given** request headers, **when** configured, **then** they come only from a named environment
   variable or a private file outside any work tree, and a literal value in config is rejected.
4. **Given** a closed, hanging or rejecting endpoint, **when** export runs, **then** it neither fails
   nor delays the hook beyond its budget, and the failure is recorded without any header value.
5. **Given** `harness usage export --since <date>`, **when** run, **then** it replays rows, delivery is
   at-least-once, and the docs show de-duplication on `harness.row_key`.
6. **Given** the docs, **when** read, **then** they state that the ledger is the record and a backend
   is a rebuildable copy.

## Design

### Approach

A new `policy/hooks/telemetry.py` builds and sends records from the hook's detached worker after the
row is written; `bin/harness` adds `usage export --since [--until] [--dry-run]`; `docs/telemetry.md`
documents the model and the query.
[Source: https://github.com/JakeSelby/agent-harness/pull/354]

### Decisions and alternatives

- 2-second timeout, no retry; failures record the error class and the endpoint's host only.
- Nested maps stay in the record body; scalars become attributes.
- The module lives beside the hook rather than in `lib/harness_core`, because the hook runs through
  the `~/.claude/hooks` symlink where `lib/` does not resolve.
- Replay is the recovery path, since most backends expire data by default.

### Do not implement

Any retry or blocking delivery; any header value in config.

## Dev notes

### Bound decisions and requirements

- FR-25: OTLP export with replay — off by default, standard library only, never blocks a hook,
  replayable; readers deduplicate on `harness.row_key`; settings live in `telemetry`, secrets from the
  environment or a headers file.
- AD-11: Local ledgers are the system of record — a backend is a replica rebuilt by replay; export is
  OTLP only, off by default, and never blocks a hook.
