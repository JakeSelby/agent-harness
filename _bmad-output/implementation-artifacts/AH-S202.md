## Story

As the harness maintainer, I want the replay runner to build each arm as a profile and refuse a pair
that differs by anything but the variable under test, so that a four-arm comparison measures the
harness and the library rather than drift in the profiles.

## Context and value

Epic #552 measures the `superpowers` mode against superpowers alone, which needs four arms rather than
two. Two earlier issues feed this one. #482 recorded a 1,700-token drift in the harness arm's standing
prefix between two runs on the same profile, caught by the transcript's `init` event and invisible to the
size-hash fingerprint. #428 recorded that the harness arm charged the user's personal layer to the
harness. This issue folds #482 and closes #428.

On `main`, `ARMS` in `scripts/cost_bench.py` is `("bare", "harness")`. The harness arm uses the profile
`--harness-config` names, or with none named inherits the live home through `HOME`. There is no plugin
parity check, no `--arms` and no `--allow-plugin-drift`.
[Source: https://github.com/JakeSelby/agent-harness/issues/559]

## Acceptance criteria

1. **Given** four arms and the release task set, **when** `replay --dry-run` runs, **then** it prints a
   32-run schedule with the lead arm rotating across the four.
2. **Given** a fake launcher and fake plugin-list output, **when** the unit tests run, **then** they
   cover profile build, parity refusal, the drift stamp, rotation and the per-arm summary.
3. **Given** a finished set, **when** it is summarised, **then** it reports per-arm cost per passed task
   and passes, and a history row carries one entry per arm as a ratio to bare plus
   `harness_superpowers_over_superpowers`.
4. **Given** #482's acceptance list, **when** it is checked, **then** it passes as written; #428 closes
   because the harness arm no longer reads the real home.
5. **Given** the docs, **when** `docs/benchmarks.md` is read, **then** it describes the four arms and the
   parity rule.

## Design

### Approach

- **Four profile specs:** `bare` (seed only), `superpowers` (seed plus plugin), `harness` (seed plus
  `bin/harness sync` under `CLAUDE_CONFIG_DIR`), `harness-superpowers` (seed plus sync plus plugin plus
  `HARNESS_MODE=superpowers`).
- The runner builds each from the signed-in seed per run day, installs the plugin from
  `claude-plugins-official` at user scope, and records its version. `--arms` selects a subset.
- **Pair parity before launch:** `bare`/`superpowers` and `harness`/`harness-superpowers` may differ only
  by the plugin listing, and the two harness arms must resolve the same harness commit. Any other
  difference refuses the launch and prints it; `--allow-plugin-drift` launches and stamps every row.
- **Every row records** the `init` event's `skills`, `agents`, `slash_commands`, `tools`,
  `mcp_servers`, the `memory_paths` length, the plugin version and `harness_mode`.
- The task prompt gains a one-sentence no-user preamble, sent to every arm.

### Decisions and alternatives

- **The preamble goes to every arm**, so it is not a difference between arms.
- **Drift is refused by default** and allowed only with a stamp on every row (from #482).

### Do not implement

- The live set itself (#560).
- Any change to the publish threshold.

### Recorded contradiction

The issue has the runner build each arm "from the signed-in seed". The `arm_env` docstring in
`scripts/cost_bench.py` on `main` records that the CLI keys a profile's credential to its absolute
path, so "a copied directory is not signed in and cannot be made so by copying files", and that the
harness profile is therefore one the owner signed into once. The issue does not say how a built profile
authenticates. This must be settled before build; the issue was not changed.
