## Story

As the operator running native qualification, I want `spawn-confinement` to observe the harness's refusal from the harness's own decision log, so that a refusal that happened is not reported `unverified` just because a headless client did not repeat it.

## Context and value

In the first live 0.13.0 qualification round (`claude-code-cli-macos`, runner at `d426d6d`) the case ended `unverified`: "the unnamed framework spawn wrote no subagent transcript, but the constrained-role refusal was not in what the client reported, so the classification itself was not observed". No subagent transcript was written, so the harness did refuse; the case searched only the client's final answer and the orchestrator transcript text for the refusal, and `claude -p` does not necessarily surface a PreToolUse deny's reason in its result. The required case cannot pass on a client that behaves that way, which blocks qualification.

## Acceptance criteria

1. **Given** a refused spawn that wrote no subagent transcript and a `framework-spawn` `deny` row for its session in the disposable home's `decisions.jsonl`, **when** the client's text carries no refusal, **then** the case passes and says the refusal's wording was not observed.
2. **Given** no such row for the refused session (a row for another session does not count) and no refusal in the client's text, **when** the case runs, **then** it raises `Unverified`.
3. **Given** the client's text carries the refusal, **when** either wording clause is missing, **then** the case still fails as before.
4. The transcript-absence check and the ordinary-spawn false-positive check are unchanged.

## Design

### Approach

`logged_refusals(home, session_id)` in `scripts/native_acceptance.py` reads `<home>/.local/state/agent-harness/decisions.jsonl` (the disposable home is the hooks' `HOME`, so `policy/hooks/decisions.py` writes there) and returns the `kind: decision`, `point: framework-spawn`, `deterministic_answer: deny` rows for the refused session. `case_spawn_confinement` treats either that row or the refusal in the client's text as the observation; the wording clauses are checked only when the text carries the refusal.

### Decisions and alternatives

- Join on `session_id`, not a tool-use id: `framework_deny` in `lib/harness_core/lifecycle.py` logs only the session id, and `match_key` in `policy/hooks/decisions.py` notes neither adapter's payload carries a tool-use id today.
- The `framework-spawn` point is the evidence of classification: `framework_deny` is its only writer and writes it on the path that returns the refusal. The row carries no reason text, so a log-only observation cannot check the wording; the unit tests in `tests/test_framework_spawn_confinement.py` hold that, and the verdict says so rather than claiming it.
- Rejected: making log-only an `Unverified`, which would leave the case unable to pass on the observed client behaviour.

### Do not implement

No change to hook behaviour or to what `framework_deny` records (adding the reason or a tool-use id to the row is a separate decision). No change to other cases.

## Dev notes

### Bound decisions and requirements

Native qualification evidence comes from what the harness and client write, never from the model's say-so (`docs/compatibility.md`); a case reports `unverified` rather than pass when it cannot observe the thing it checks.

### Testing

`tests/test_native_acceptance_spawn_refusal.py`: the decision log is written by `lifecycle.dispatch` with the temporary home as `HOME`, so its rows are the hook's own shape. Log-only passes (AC 1); another session's row plus no text is `Unverified` (AC 2); reported text missing a clause still fails (AC 3); a non-deny or unparsable row is not read as a refusal.
