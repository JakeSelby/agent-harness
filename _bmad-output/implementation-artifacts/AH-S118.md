## Story

As the maintainer, I want the issue, milestone and release-cadence rules written where agents read
them, and GitHub About and the `on_the_way` list checked at release preflight, so that labels,
milestones, releases and landing copy stay current without an instruction each time.

## Context and value

Milestones, release cadence and landing-copy upkeep were uncodified, and nothing compared
`product.json` with GitHub About. The issue depended on the capability-data issue (#318). A comment
from the release-cost analysis (#340) asked that the cadence rule be written once, here: do not cut a
release that changes no runtime source, and include a carve-out for corrective and security releases,
because a cadence rule without one "turns a cost argument into a reason to leave a false claim
standing".
[Source: https://github.com/JakeSelby/agent-harness/issues/320]

## Acceptance criteria

1. **Given** `AGENTS.md` and `docs/releasing.md`, **when** read, **then** they state one `type::*`
   label and the next-release milestone per issue, that a pull request changing a user-visible
   capability updates `product.json` in the same change, that releases are cut by milestone with a
   regression fix released at once as a patch, and the bump rules.
2. **Given** `scripts/sync_about.py --check`, **when** GitHub About differs from `product.json` in
   description, topics or homepage, **then** it fails and names each field; `--apply` edits only the
   differing fields.
3. **Given** `release_preflight.py`, **when** About has drifted or an `on_the_way` issue has closed,
   **then** it blocks and says to promote or remove.
4. **Given** an unauthenticated `gh`, **when** preflight runs, **then** both checks are skipped with a
   named warning, never silently.
5. **Given** the tests, **when** they run, **then** they use recorded `gh` JSON fixtures and no live
   service, and the always-loaded context total is unchanged.

## Design

### Approach

Rules in `AGENTS.md` and `docs/releasing.md`; a new `scripts/sync_about.py`; two checks in
`scripts/release_preflight.py`.

### Decisions and alternatives

- A release is proposed when the milestone empties or a user-visible unreleased change is seven days
  old; the bump rule is worded by what changed, not by changelog section.
- Release surfaces 4 and 5 become verify only: the reference site repins itself, and the personal-site
  card names no version. Surface 6 names the script. Closing and opening the milestone is a
  documented hand-run step.
- Both network checks run behind one `gh auth status` probe. An unauthenticated `gh` warns and does
  not fail, which the tag workflow does by design; a `gh` call that fails after a good probe blocks.
[Source: https://github.com/JakeSelby/agent-harness/pull/383]

### Do not implement

Merge mechanics or changelog format (#337), and how a release is qualified (#332 to #336, #338, #339).
