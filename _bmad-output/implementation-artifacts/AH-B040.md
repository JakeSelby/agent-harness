# AH-B040 — new files an issue the list endpoint does not yet return, so reserve fails

## Reproduction

Run `python3 scripts/bmad_issue_sync.py new` to file an issue. The issue records the first real use,
filing #388:

```
bmad issue sync: issue #388 was filed but not reserved; fix the cause and run
reserve --issue 388: RuntimeError('issue #388 was not found')
```

The issue exists on GitHub when the error is printed. The printed recovery worked.

## Root cause

Traced in `scripts/bmad_issue_sync.py` at `origin/main`:

- `create_issue` posts the issue, reads its number from the create response, checks the label, and
  calls `reserve(manifest, repo, number, kind, parent_number, advance)`.
- `reserve` discards the payload `create_issue` already holds. It calls `fetch_issues(repo)`, builds a
  map by number, and raises `issue #N was not found` when the new number is absent.
- The issue states that GitHub's list endpoint does not always return an issue it has just created.
  Nothing retries the lookup.

## Acceptance criteria

From the issue's Acceptance section:

1. **Given** the list endpoint omits a just-created issue on its first read, **when** `new` runs,
   **then** it files the issue and reserves its ID in the same invocation.
2. **Given** an issue that genuinely does not exist, **when** `reserve` looks it up, **then** it still
   fails with the not-found error.
3. **Given** `reserve --issue N` run on its own, **when** it succeeds or fails, **then** its behaviour
   is unchanged.
4. Unit tests cover both the omitted-on-first-read case and the genuinely absent case.

## Design

From the issue's Scope section:

- `reserve` accepts the issue payload the caller already holds, so `new` does not re-fetch an issue it
  has just created.
- Where a fetch is still needed, it retries a small number of times, with a short delay, before
  reporting the issue as missing.

The two can ship together: the payload removes the fetch from `new`'s happy path, and the retry covers
`reserve` on its own. [ASSUMPTION: the issue lists both without saying whether one alone suffices.]

Do not implement: a change to `reserve --issue N`'s behaviour when the issue exists (AC 3).

**Duplicates recorded.** The same failure is filed three times, and all three are open:

- this issue, #392;
- #433, which adds a second defect: the printed recovery `reserve --issue N` omits the required
  `--kind`, so it fails as written;
- #537 (AH-B069), filed after three more failures during the 0.12.0 release.

PR #441's body assigns "the `new` read-after-write failure and its `--kind`-less recovery hint" to #433.
The three need one delivery issue, with the others closed as duplicates. That triage is not recorded.

## Regression test

Not written. A test would stub `gh_json` so the first issue-list read omits the new number, and assert
that `create_issue` returns a reserved item. A second test would assert that a genuinely absent number
still raises.
