## Story

As a developer who treats local collection as a preference, I want switches to disable usage collection, drop repository and branch metadata, and expire old records, so that the harness records only what I agree to keep, for as long as I choose.

## Context and value

Local usage collection and repository and branch metadata are always installed, and local-only storage is still a preference ([#128](https://github.com/JakeSelby/agent-harness/issues/128)). The epic's 2026-09-21 assessment rated the story Partial: collection and metadata exist, with no enable or retention keys and no pruning code ([#116 comment](https://github.com/JakeSelby/agent-harness/issues/116)).

On `main` today:
- The `telemetry` block accepts `export`, `endpoint`, `headers_env`, `headers_file`, `labels`, `native`, `decisions`, `completion_claim` and `allow_sample_rate`, and rejects any other key [Source: policy/hooks/telemetry.py#KNOWN_KEYS]. None of the four keys this story proposes exists.
- `telemetry.decisions: false` already stops the decision log from writing anything [Source: policy/hooks/decisions.py#enabled]. That covers the decision log only, not the usage ledger.
- The usage ledger records `repo` and `branch` for each row [Source: policy/hooks/usage-log.py].
- No retention or pruning code was found in `usage-log.py` or `decisions.py`.

The issue carries the v0.15.0 milestone.

## Acceptance criteria

1. **Given** collection disabled, **when** a session runs, **then** no worker launches and no record is written, and a rescan cannot bypass the setting.
2. **Given** a metadata opt-out, **when** new records are written, **then** they omit the selected fields, and deletion of existing records is documented as a separate operation.
3. **Given** a retention period, **when** pruning runs, **then** it removes only harness-owned records by a defined UTC timestamp, and concurrency, invalid configuration, expiry boundaries and disabled hooks are tested.

## Design

### Approach

The issue proposes `observability.enabled`, `retention_days`, `include_repo` and `include_branch`. Collection and metadata stay on by default, and `retention_days=0` means no automatic expiry, for migration compatibility. The controls apply to both native collectors, detached workers, rescans and reports. Commands and message bodies are never collected ([#128](https://github.com/JakeSelby/agent-harness/issues/128)).

The plan adds that opting out of metadata affects new records only, that purging existing records is a separate explicit operation, and that disabled telemetry must stop detached workers and rescans as well as hook installation [Source: docs/plans/stance-completeness.md#Step 5 — Settings and runtime behavior].

### Decisions and alternatives

- `retention_days=0` preserves current stored history by default ([#128](https://github.com/JakeSelby/agent-harness/issues/128)).
- The issue names the block `observability`; the shipped settings live under `telemetry`, and AD-11 says export settings "live in the `telemetry` block, never in a stance". [ASSUMPTION: the four keys would land in `telemetry` too; no record decides it.]

### Recorded contradiction

This issue says "Do not collect commands or message bodies." #543, the session archive, proposes `telemetry.sessions_bodies`, which stores message and tool-result text when on, and applies this story's `retention_days` to it ([#543](https://github.com/JakeSelby/agent-harness/issues/543)). The two issues disagree on whether message bodies may be collected at all; neither issue has been changed.

### Do not implement

- Do not collect command text or message bodies.
- Do not delete existing records as a side effect of a metadata opt-out.
- Do not sync an unmerged candidate into the live installation.
