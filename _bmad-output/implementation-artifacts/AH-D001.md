## Context

#48 left a follow-up open: should `bmad-build`'s implementation handoff launch the harness's `builder` agent? The issue records the state at the time. The handoff override launched a bare subagent pinned to `opus`, the builder's tier, working in the tree the framework runs in. `builder` implements in its own worktree, commits once and never pushes. The framework's review step diffs the tree it ran in against `baseline_commit`, so routing to `builder` would also have to bring the branch back (`--ff-only`, else cherry-pick) before step 04, and the worktree's base would differ from the checkout's branch whenever that branch was ahead of `main`.

## Options

1. **Route the handoff to `builder`.** For: isolation, one commit and the repository gate. Against: the framework's review step needs the change in the tree it ran in, so the branch must be brought back before step 04, and the bases can diverge.
2. **Keep the in-tree handoff pinned to the builder's tier (won't-do).** For: in-tree implementation is what the review step needs, the pin already carries the tier, and the framework's step 04 runs the spec's verification section. Against: Not recorded in the issue or pull request.

## Decision

Option 2, recorded in the issue comment as: "Decided won't-do and recorded in docs/bmad.md by #53 (384c691): the framework's review step diffs the tree it ran in against baseline_commit, so the implementer works in place; the pinned handoff already carries the builder's tier; isolation, one commit and the repo gate are what the framework does itself later in the run."

The issue's state reason is `completed`, not `not planned`, although the decision was won't-do.

## Consequences

- PR #53 added a paragraph to `docs/bmad.md` saying routing to `builder` "was considered and rejected", with the reasons above, so the question is not re-litigated.
- **Superseded at `origin/main`.** `templates/bmad/custom/bmad-build.user.toml` and `bmad-build-auto.user.toml` now say "Launch harness role `builder` through the active runtime adapter with fresh context, in the assigned implementation worktree", and `docs/bmad.md` no longer carries the rejection paragraph. `[ASSUMPTION: reversed by PR #104 (commit 0752250), the last change to the `baseline_commit` text in docs/bmad.md; this decision record has no amendment saying so]` This is a contradiction between the recorded decision and the current templates, left for the owners to settle.
- No code changed under this item; it was delivered as documentation inside PR #53, merged 2026-09-17, milestone v0.5.0.
