## Reproduction

As filed on 2026-09-21: in this repository, run `harness task save`, then `bin/harness lint`. The save
writes the absolute repository path into `.agent-harness/task.json`, and the lint rejects a
home-directory path in any file under the checkout, tracked or not. The issue records that three
consecutive handoff sessions skipped the shared task contract for this reason.

**The reproduction no longer holds at `origin/main`.** Two later changes stopped the lint seeing the
file, without changing what the file holds:

- PR #490 (merged 2026-09-22, closing #432) added `.agent-harness/task.json`, `sync.lock` and
  `evidence/` to `.gitignore`. Its comment calls the task record "keyed to an absolute repository path".
- Commit 9a7fabf (#614, 2026-09-23) made the lint skip untracked files under `.agent-harness/`.

## Root cause

`save` in `lib/harness_core/tasks.py` writes `repository=str(root)`, where `root` is the resolved
top-level path from `git rev-parse --show-toplevel`. `read` refuses a record whose `repository` differs
from `str(root)`. The lint's `home-directory path` pattern in `bin/harness` matches `/Users/<name>/` and
`/home/<name>/`.

So the path is still absolute. The lint conflict is gone because the file is no longer linted.

## Acceptance criteria

From the issue's "Done when" section, with the state at `origin/main`:

1. **Given** this repository, **when** `harness task save` runs, **then** `bin/harness lint` stays
   clean. Met at `origin/main` by the ignore rule and the lint exception, not by the proposed change.
2. **Given** a saved task, **when** `harness task show` runs, **then** it returns the same objective,
   next steps, decisions and artifacts as before.
3. **Given** a save and a read back, **when** the file is inspected, **then** it holds no absolute
   path, and a test covers it. Not delivered: `repository` is still absolute.

## Design

The issue's proposal: store the path relative to the repository root, or omit it and resolve the root
at read time, because "the consumer already knows which checkout it is reading from".

`read` uses the stored path to refuse a record from another checkout. Omitting it needs another way to
make that check, for example the fingerprint the record already carries. [ASSUMPTION: the issue does
not discuss the `read` check; it is read from the code.]

Open question, recorded here: with AC 1 met by other means, whether AC 3 is still wanted is not
recorded. The issue is still open.

Do not implement: any change to the fields `harness task show` returns (AC 2).
