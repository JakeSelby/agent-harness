# AH-B052 — claude_dir() lets CLAUDE_CONFIG_DIR override a set HARNESS_HOME, so the test suite writes into the real profile

- **Primary parent:** None
- **State:** completed

The issue carries the summary, discussion and acceptance evidence; this file carries the design.

This work item was authored as part of the repository's committed BMad planning system.
<!-- bmad-sync:end -->

## Reproduction

1. Set `CLAUDE_CONFIG_DIR` to an empty signed-in profile.
2. Run `python3 -m unittest discover -s tests`.
3. The sync tests write the harness into that profile (`CLAUDE.md`, `rules/`, `agents/`, `hooks/`,
   `commands/`, `output-styles/`, `plans/`, skill symlinks and a rewritten `settings.json`), and
   `test_sync_links_*` fails. With the variable unset, the suite passes and touches nothing outside its
   temporary home. The skill symlinks point at the suite's temporary clone and dangle once it is cleaned
   up.

The issue notes that anyone who keeps a second profile and runs the suite from a shell that names it gets
that profile rewritten; under the CLI's sandbox the writes are refused and the suite errors instead,
which is how it was noticed.
[Source: https://github.com/JakeSelby/agent-harness/issues/498]

## Root cause

`claude_dir()` in `bin/harness` returns `CLAUDE_CONFIG_DIR` whenever it is set, before considering
`HARNESS_HOME`. The suite isolates itself by pointing `HARNESS_HOME` at a temporary directory, and the
environment variable silently overrides that isolation.

## Acceptance criteria

1. **Given** `HARNESS_HOME` set to a temporary directory and `CLAUDE_CONFIG_DIR` set to another,
   **when** `claude_dir()` resolves, **then** it resolves under `HARNESS_HOME`.
2. **Given** `CLAUDE_CONFIG_DIR` pointed at an empty directory, **when** the full suite runs, **then** it
   passes and leaves that directory empty.
3. **Given** the change, **when** the gate runs, **then** lint is clean and the suite is green under both
   `python3` and `/usr/bin/python3`.

**Criterion 1 was superseded.** The repository owner's 2026-09-22 comment on the issue withdrew the
precedence change: do not make `HARNESS_HOME` win over `CLAUDE_CONFIG_DIR` in `claude_dir()`, because
"that runtime precedence is correct". The recorded rationale is that this precedence is how a harness is
synced into a non-default profile (`HARNESS_HOME=<config> CLAUDE_CONFIG_DIR=<profile> harness sync`), and
reversing it "would send that sync to `<config>/.claude`" instead. The same comment places the defect
entirely in the test suite's isolation and keeps criterion 2 as written. At `origin/main`, `claude_dir()`
still returns `CLAUDE_CONFIG_DIR` when set, as intended.
[Source: https://github.com/JakeSelby/agent-harness/issues/498]

## Design

**Approach.** A shared test helper, `tests/isolation.py`, provides `isolate_home()`,
`without_config_dir()`, `without_harness_vars()` and `drop_inherited_config_dir()`; importing it drops the
variable from the test process. Every temporary-home `setUp` and every inherited-environment builder in
the suite goes through it, replacing copied isolation blocks in 35 modules.

**Decisions and alternatives.** The issue body proposed both a runtime precedence change and clearing
`CLAUDE_CONFIG_DIR` in the suite as belt and braces. The owner's comment on the issue withdrew the
precedence change, for the reason given under the criteria, and moved the fix to the shared helper that
builds the suite's environment. The PR follows that comment.

**Do not implement.** Do not change `claude_dir()` precedence: `CLAUDE_CONFIG_DIR` keeps winning over
`HARNESS_HOME`, per the owner's comment on the issue.

## Regression test

`tests/test_env_isolation.py` (new), including
`test_the_subprocess_environment_does_not_carry_an_inherited_config_dir` and
`test_a_sync_test_writes_nothing_into_an_inherited_config_dir`. The PR reports that disabling the drop
makes both new tests fail, and that a full run with `CLAUDE_CONFIG_DIR` at an empty temporary directory
left it empty.
