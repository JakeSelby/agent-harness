## Story

As an orchestrating agent's operator, I want a bounded check that a worker brief names concrete
deliverables, explicit scope boundaries and an observable stopping condition, so that a brief that has
the right headings and a word cap but no actionable assignment is caught, measured first in `shadow`.

## Context and value

A brief can carry required headings and a return cap while still failing to describe an actionable
assignment. The 2026-09-21 re-scope kept this follow-on because it has a consumer:
`policy/hooks/brief-guard.py`. The issue describes it as standing in for "is this brief bounded" with a
word-cap regex; on `main` the hook appends a return bound and the posture's soft budget to a brief that
states neither, using the cap pattern the `model-wrote-no-cap` detector defines (the hook's docstring).
It stays shadow-only until the decision log (#370) holds labelled briefs, and it is not a release
dependency of the epic.
[Source: https://github.com/JakeSelby/agent-harness/issues/156]

## Acceptance criteria

1. **Given** the shared provider and versioned pack contracts, **when** a brief is judged, **then** each
   criterion returns a typed decision with explicit abstention and unavailable handling.
2. **Given** a pack's declared input limit, **when** an input is oversized or missing, **then** it stays
   unverified rather than being silently truncated, and no transcript or repository is uploaded.
3. **Given** formatting, counts and schema, **when** they are checked, **then** deterministic code
   checks them.
4. **Given** concise valid briefs, vague but well-formatted briefs, and briefs bounded by an explicit
   read-only file list, **when** they are judged, **then** results are compared with the brief-guard
   structural baseline.
5. **Given** labels fixed before evaluation and a held-out split, **when** the pack is evaluated,
   **then** misses, false alarms, abstentions, errors, latency and available cost are reported; ordinary
   tests stay offline and live tests are opt-in and budgeted.
6. **Given** a provider failure, **when** it occurs, **then** current behaviour is preserved, and
   nothing is enforced by default before workload-specific validation.

## Design

### Approach

One short worker brief and an explicit brief-quality rubric go to separate questions on deliverables,
scope boundaries and stopping conditions. Per-criterion judgments are returned beside brief-guard's
structural answer, in `shadow`; the brief is never rewritten.

### Decisions and alternatives

- **Kept at re-scope** because brief-guard is a consumer; the other bounded experiments (#158 to #162)
  were closed.
- **Shadow until labelled briefs exist** in the decision log.

### Do not implement

Judging whether a task is feasible, authorized or a sound decomposition of a larger task; a generic
quality score; inferred permissions; model training; live configuration changes. Publishing the
provider's performance results stays subject to its terms.
