## Story

As a developer who moves a task between Claude Code and Codex, I want one versioned task handoff and
BMad routed through semantic roles, so that work continues in either runtime without transferring an
approval or trusting a verification claim the handoff made about itself.

## Context and value

This is a delivery slice of #97 (BMad integration and task context across Claude and Codex), under epic
#93. It records ownership of the already open PR #104 and adds no release scope.
[Source: https://github.com/JakeSelby/agent-harness/issues/166]

## Acceptance criteria

Taken from the issue's own acceptance section. The outcomes listed under AC 1 restate the
issue's "Proposed design", which AC 1 requires the PR to satisfy.

1. **Given** PR #104, **when** it is reviewed, **then** its implementation and documentation satisfy the
   issue's proposed design and preserve the single shared primitive authority. The design outcomes:
   1. **Given** a task started in one runtime, **when** it is handed off, **then** the other runtime reads one
      versioned handoff carrying repository identity and revision.
   2. **Given** a handoff whose repository or working tree has changed, **when** it is resumed, **then** the
      revision check or stale-tree detection reports it.
   3. **Given** a handoff, **when** it is resumed, **then** no approval transfers and its own verification
      claims are not certified.
   4. **Given** BMad workflows, **when** they run in either runtime, **then** they route through semantic roles
      and either skill projection, and conflicting mirrors are rejected.
   5. **Given** BMad customization files, **when** they are read, **then** they are parsed structurally.
   6. **Given** session start, **when** it runs, **then** it stays read-only (as of PR #104; at `origin/main`,
      `policy/hooks/harness-session.py` also writes a session record).
2. **Given** the final integrated commit, **when** the gate runs, **then** applicable regression tests,
   repository lint, generated projections and the existing CI commands pass.
3. **Given** the pull request, **when** it is reviewed, **then** it owns only this delivery issue, and
   broader tracking issues remain contextual references.
4. **Given** native evidence, **when** it is reported, **then** it names its exact tested source and
   versions, and this delivery alone makes no complete client-support or publication claim.

## Design

### Approach

`lib/harness_core/tasks.py` stores the neutral task state and handoff. The `handoff` and `plan` workflow
primitives and their Claude command projections read and write it. BMad customization templates under
`templates/bmad/custom/` bind BMad's build and review workflows to the harness's semantic roles, and
`docs/bmad.md` documents the routing. As of PR #104, the session-start hook read task state without writing it; at `origin/main` it also writes a
session record through `record_session`. [Source: policy/hooks/harness-session.py]
[Source: https://github.com/JakeSelby/agent-harness/pull/104]

### Decisions and alternatives

- **Handoffs are not authoritative:** approvals never transfer and verification claims are not
  self-certified.
- Alternatives considered are not recorded in the issue or pull request.

### Do not implement

- Native qualification and publication (#98, #100).
