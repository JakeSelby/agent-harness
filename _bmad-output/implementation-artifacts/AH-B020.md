## Reproduction

1. Start an isolated role worker with `harness role run <role>`.
2. Kill the launching session or process before the worker reports.
3. Run `harness role status`.

Observed: the worker stays `status: running` in its `status.json` forever, with no `result.md` and no
error, indistinguishable from live work. Found by native qualification of `claude-code-cli-linux`.
[Source: https://github.com/JakeSelby/agent-harness/issues/286]

## Root cause

The worker's status recorded no supervising process identity, so a status read had no way to tell a
dead worker from a live one.

## Acceptance criteria

1. **Given** a live recorded pid, **when** status is read, **then** it is `running`.
2. **Given** a dead pid and no result, **when** status is read, **then** it is the terminal state
   `orphaned`, with one line saying the worker process ended without reporting.
3. **Given** a dead pid with a result, **when** status is read, **then** it is the finished state.
4. **Given** no recorded pid (an older release, or a platform that reports no start time), **when**
   status is read, **then** it stays `running` as before.
5. **Given** a start-token mismatch, **when** status is read, **then** it is `orphaned`, guarding against
   pid reuse.
6. **Given** the change, **when** it lands, **then** only `status.json` is rewritten and the state is
   documented.

## Design

Record the supervising process id and a start-time token at launch in `lib/harness_core/workers.py`. A
live-status run with no result whose recorded process is gone reads as `orphaned`. "Cannot tell" stays
`running`. The recorded process is the harness runner; the issue records the known limit that a status
read from a different pid namespace (a host reading a containerised worker's state directory) cannot see
that process, and says no supported flow does this.

## Regression test

`tests/test_worker_orphans.py` (new) pins each of the five cases.
