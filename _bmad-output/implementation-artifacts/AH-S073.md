## Story

As a developer evaluating the harness, I want the README, docs, CLI and templates to lead with
user-controlled behaviour, custom primitives and switchable personal stances, so that I understand what
the product is for before I read which runtimes it supports.

## Context and value

This is a delivery slice of #99 (reposition product messaging around personal stances and shared
primitives), under epic #93. It records ownership of the already open PR #107 and adds no release scope.
Runtime support statements stay tied to the compatibility catalog, so the messaging change claims
nothing the catalog does not.
[Source: https://github.com/JakeSelby/agent-harness/issues/169]

## Design

### Approach

`product.json` becomes the one product metadata source for release and site ingestion.
`docs/stance-demo.md` demonstrates switching a stance and authoring a custom one. The README, getting
started, how-it-works, preferences, settings-ownership, sync-model and usage docs, CLI help, issue
templates and the repository template are rewritten around stances and primitives, and
`tests/test_docs.py` checks the documentation. [Source: https://github.com/JakeSelby/agent-harness/pull/107]

### Decisions and alternatives

- **One product metadata source:** release and site copy read `product.json` rather than restating it.
- **Support stays with the catalog:** messaging does not assert runtime support on its own.
- Alternatives considered are not recorded in the issue or pull request.

### Do not implement

- Changes to historical release records.
- Native qualification and publication (#98, #100).
