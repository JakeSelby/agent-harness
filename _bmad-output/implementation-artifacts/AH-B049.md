# AH-B049 — harness worktree remove cannot finish a checkout that holds a submodule

This work item was authored as part of the repository's committed BMad planning system.
<!-- bmad-sync:end -->

## Reproduction

Create a task worktree whose checkout holds an initialised submodule, leave it clean, and run
`harness worktree remove NAME [REPO] --merged`. The command refuses, because `git worktree remove`
refuses: `working trees containing submodules cannot be moved or removed`.

The issue records it against a throwaway repository, and against four worktrees of a repository that
vendors the harness as a submodule at a tag, each left after its pull request merged. The only way to
clean up is a hand-typed recursive delete, which the shell-grading hook denies.

## Root cause

In `bin/harness` at `origin/main`, the remove path runs its own cleanliness check through
`classify_worktree_status`, which refuses tracked changes, untracked files and any ignored entry that
is not a known regenerable cache or an `--also-clear` name. It then calls
`git worktree remove <dest>` without `--force`. Git refuses any worktree that holds a submodule,
whatever its state, so a checkout that passed the harness's own check still cannot be removed.

The issue notes that the removal fix for #363 (delivered in commit fdfaa9a, #384) made the cache case
work; the submodule case is what remains.

## Acceptance criteria

From the issue's Acceptance section:

1. **Given** a clean worktree that holds an initialised submodule, **when** `harness worktree remove
   --merged` runs, **then** it succeeds, deletes the branch as before, and names the forced removal in
   its output.
2. **Given** a worktree whose submodule carries changes, **when** removal runs, **then** it is refused,
   with the reason and the path.
3. **Given** a worktree holding a real untracked file, **when** removal runs, **then** it is refused,
   submodule or not.
4. No test reaches a live service.

## Design

From the issue's Proposal:

- When the command's own cleanliness check has passed, and the only thing `git worktree remove`
  objects to is a submodule, pass `--force` to git and say in the output that it was used and why. A
  submodule at its recorded commit holds no work.
- Refuse as now, without `--force`, when a submodule is dirty or at a commit the superproject does not
  record. Git reports a dirty submodule as a modified path, so the existing check already sees it; a
  test proves it.
- Nothing else gains `--force`, and no flag exposes it to the caller.

Also in scope, as a decision: `--also-clear NAME` takes one top-level directory name, so it cannot cover
a nested `infra/dist`. The issue asks whether a second form is worth it. The narrow form was chosen on
purpose: matching every path component would let `--also-clear build` delete `src/build/`. No answer is
recorded.

Do not implement: a caller-visible force flag, or `--force` on any path other than the submodule case.
