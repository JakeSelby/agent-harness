# AH-S133 — Decouple the harness from BMad: generic layering, BMad as an optional integration test

## Story

As the release maintainer, I want the harness decoupled from BMad, with generic layering qualified by
a synthetic case and BMad run as an optional integration suite, so that a release does not spend an
hour running one third-party framework's own workflow.

## Context and value

One of eleven `required_cases`, `bmad-workflow`, held a release for an hour or more: every release ran
a third-party framework's four-layer code review natively on all four required targets. The issue
records it blocked both 0.11.0 and 0.11.1, and that on the Claude Code CLI on Linux one confined run
took five attempts, because confinement was requested in recipe text rather than enforced at the spawn
hook (#291). It inventories the couplings (A 4, B 7, C 3, D 4) and finds none in the engine: `lib/`,
`adapters/`, `codex/` and every policy hook had zero BMad references. What was missing was a generic
channel keyed on something the model cannot edit, plus a descriptor. It depends on #291 and
complements #340, #335, #336 and #304.
[Source: https://github.com/JakeSelby/agent-harness/issues/349]

## Acceptance criteria

The issue has no acceptance section; these are taken from its recommendations and the PR:
1. **Given** `harness integration check|apply <name>`, **when** run, **then** the template directory,
   install destination, presence probe and skill surface come from `policy/integrations/<name>.json`,
   and `harness bmad` remains an alias.
2. **Given** the session hook, **when** it probes for a framework, **then** it reads the descriptor's
   `detect` path, not a directory literal.
3. **Given** the catalog, **when** read, **then** `framework-spawn-routing` replaces `bmad-workflow` in
   `required_cases`, and the case builds a fixture recipe from the descriptor, drives the real spawn
   hook, and is `unverified` when no valid descriptor exists.
4. **Given** the confinement limitation, **when** rewritten, **then** two limitations replace one and
   no observation is dropped.
5. **Given** the offline template and surface tests, **when** CI runs, **then** they still run.

## Design

### Approach

`lib/harness_core/frameworks.py` and `policy/integrations/bmad.json` carry the descriptor;
`bin/harness` gains the `integration` surface; `scripts/native_acceptance.py` gains the
`framework-spawn-routing` case. The native BMad run becomes an optional, non-gating suite, once per
minor release on one target (`docs/bmad.md`, `docs/releasing.md`). Generic task continuation moves to
`docs/task-continuation.md`, and the D-class framework-named asides are removed.
[Source: https://github.com/JakeSelby/agent-harness/pull/591]

### Decisions and alternatives

The issue's five decisions were taken as it recommended, per the PR:
1. Descriptor plus `harness bmad` alias, rather than a separate product surface.
2. `bmad-workflow` leaves `required_cases` now, since #291 enforces confinement.
3. The optional suite runs once per minor release, on one target.
4. Offline template and surface tests stay in CI.
5. Two limitation entries; the second is narrowed as the issue anticipated, since #291's own entry
   covers that ground.
Also: one path in `compatibility/migration.json` changed, because a wrong pointer is a defect, though
the issue said to keep migration notes as written.

### Do not implement

Anything in C-class (this repository's own planning corpus, issue-sync tool and conventions); the
issue says it costs a release nothing. Claims the new case cannot prove: that a real framework's text
survives an upstream rename, that a multi-layer review completes end to end, or that a client
preserves the marker.
