## Reproduction

In Claude Code plan mode, the PreToolUse coordinator answered `allow` only for Bash commands the
read-only grammar proves (grade 0). Grades 1 and 2 returned no decision, so the native plan-mode flow
prompted for them: `python3 script.py`, `python3 -c …`, `curl -s …`, a redirect into a scratch
directory, `npm test`. `useAutoModeDuringPlan` covers this only where auto mode is available, so a
`bypass` posture still prompted on every investigative command while planning. MCP read tools
prompted in plan mode as well.
[Source: https://github.com/JakeSelby/agent-harness/issues/310]

## Root cause

`dispatch()` in `lib/harness_core/lifecycle.py` gave no decision for grades 1 and 2 in plan mode, and
native plan mode asks whenever no decision is given. Plan mode should force a plan, questions and a
wait, not drop investigation below the permission posture the user selected.
[Source: https://github.com/JakeSelby/agent-harness/issues/310]
[Source: https://github.com/JakeSelby/agent-harness/pull/317]

## Acceptance criteria

1. **Given** Claude Code plan mode and a `bypass` or `auto` posture, **when** a Bash command of grade
   0 or 1 runs, **then** the coordinator answers `allow`.
2. **Given** the same, **when** a grade 2 (remote-mutating) command runs, **then** it answers `ask`,
   with a reason that it is execution rather than planning.
3. **Given** grade 3, a `manual` or `inherit` posture, the Codex runtime, or a non-plan mode, **when**
   a command runs, **then** behaviour is unchanged.
4. **Given** the `plan_allow_tools` glob list, **when** a tool name matches under the same posture
   gate, **then** it is allowed in plan mode; a miss, an empty list and a failed gate allow nothing.
5. **Given** the docs and changelog, **when** read, **then** they describe the behaviour and the key.

## Design

- **Approach:** in plan mode under `bypass` or `auto`, `dispatch()` allows grades 0–1 and asks on
  grade 2. Grade 3, the confirm marker and a stricter autonomy stance are unchanged.
- **Decisions:**
  - New config key `plan_allow_tools`: `fnmatch` globs of tool names, empty by default, because a
    hook payload carries no read-only hint for an MCP tool, so nothing is inferred.
    `harness config set plan_allow_tools '[…]'` validates it.
  - Posture and globs are read non-strict through the existing posture resolver, so an unreadable
    config widens nothing.
  - Codex is unchanged, because its client rejects `allow`.
[Source: https://github.com/JakeSelby/agent-harness/pull/317]

## Regression test

`tests/test_plan_mode_posture.py` (new, 180 lines): every grade against each posture, both runtimes,
non-plan modes, the confirm marker, a stricter stance, the glob list (match, miss, empty, gate, junk
entries), unreadable config, and `config set` validation. The PR records `Ran 1166 tests`, `OK`.
