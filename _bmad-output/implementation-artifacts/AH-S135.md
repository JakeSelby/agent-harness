## Story

As a developer who already collects runtime telemetry, I want `harness sync` to switch on each
runtime's native OpenTelemetry output, stamped with the harness version and stance labels, so that I
can tell which harness version or stance variant produced the data without configuring it by hand.

## Context and value

Both runtimes can export their own telemetry; the issue notes Claude Code's includes a dollar figure,
tokens by type, model, effort and subagent type. Turning it on was manual, and the data arrived with no
way to tell which harness version or stance variant produced it. Codex had a trap: with only
`exporter` set, its default metrics sink suppresses token metrics.
[Source: https://github.com/JakeSelby/agent-harness/issues/355]

## Acceptance criteria

1. **Given** `telemetry.native: true`, **when** `harness sync` runs, **then** it writes the runtime's
   own telemetry settings pointed at the exporter's endpoint; off by default, and with it off `sync`
   writes nothing new.
2. **Given** Claude Code, **when** synced, **then** its `env` block carries the telemetry switch,
   exporters, protocol, endpoint and `OTEL_RESOURCE_ATTRIBUTES` with `harness.version` and one
   `harness.<stance>` per resolved stance, and `otelHeadersHelper` points at a harness-owned helper;
   user-set variables are preserved and ownership of managed keys is recorded.
3. **Given** Codex, **when** synced, **then** its `[otel]` table carries `exporter` and an explicit
   `metrics_exporter`.
4. **Given** any settings, config or command output, **when** written, **then** no header value appears.
5. **Given** `doctor`, **when** run, **then** it reports whether native export is on, the endpoint host,
   and whether labels match the current version and stances.
6. **Given** the docs, **when** read, **then** they say what the runtimes attach on their own,
   including user and organization identifiers.
7. **Given** native export turned off, **when** `sync` runs, **then** it removes exactly what was added.

## Design

### Approach

`bin/harness` writes the settings during `sync`; `policy/hooks/otel-headers.py` is the helper that
reads the configured headers file and prints a JSON object, or nothing on failure;
`claude/OWNERSHIP.json` records the managed keys.
[Source: https://github.com/JakeSelby/agent-harness/pull/357]

### Decisions and alternatives

- Ownership is per variable, never the whole `env` map. A differing pre-existing value is reported in
  `sync` and `doctor` and left alone; an identical one is adopted.
- Codex takes header values only as literals in `config.toml`, so none are written, and `sync` and
  `doctor` say so.
- Labels are refreshed on every sync.

### Do not implement

Writing any header value to a file.
