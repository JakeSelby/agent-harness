## Story

As a developer with a large skill catalog, I want a decision provider to rank a small, code-retrieved
shortlist of skills against a short request, measured in `shadow`, so that the harness learns whether
ranked selection would load the right skill before any recommendation reaches the agent.

## Context and value

A large skill and context catalog makes relevance selection costly and can load unrelated material or
force an inappropriate workflow. The original epic put skill selection in the first release. The
2026-09-21 re-scope made the point shadow-only in 0.13.0: the closest published analogue, a prompt-time
skill router, was right on scripted prompts and wrong on about half of real ones, so this point ships no
`advise` mode until it beats that on the harness's own sessions. The label is observable: whether the
shortlisted skill was the one actually invoked.
[Source: https://github.com/JakeSelby/agent-harness/issues/143]

## Acceptance criteria

1. **Given** a request and a code-retrieved candidate set, **when** the point runs, **then** it ranks
   candidates rather than thresholding them, and returns only supplied IDs or a none-applies outcome.
2. **Given** candidate-count and payload-size limits, **when** an input is oversized or insufficient,
   **then** it falls back without silently truncating required evidence.
3. **Given** an explicit skill invocation or mandatory repository instruction, **when** a ranking
   exists, **then** the invocation and instruction take precedence.
4. **Given** an uncertain result, **when** it is returned, **then** ordinary retrieval and access to the
   full candidate set are preserved.
5. **Given** the test suite, **when** it runs, **then** it covers relevance precision and
   missed-required-context cases, including an impossible-match fixture.
6. **Given** a session, **when** rankings are produced, **then** the installed tool set and parent model
   stay stable and cached global instructions are not rewritten.
7. **Given** a ranking, **when** it is recorded, **then** it writes no persistent memory and changes no
   canonical planning authority.
8. **Given** the harness's own sessions, **when** the point is evaluated, **then** its label is whether
   the shortlisted skill was the one invoked, and it stays in `shadow` in 0.13.0.

## Design

### Approach

Retrieve a small candidate set in code, then rank skill descriptions against a short, self-contained
request. Ambiguous references are resolved before inference, and mandatory context stays independent of
rankings. Claude Code only, since Codex has no prompt-submit event. A later follow-on would rank short
documentation excerpts or handoff candidates the same way.

### Decisions and alternatives

- **Rank, do not threshold.**
- **Shadow only in 0.13.0,** because the published analogue failed on real prompts.
- **Claude Code only;** the Codex gap is named, not emulated.
- **An external repository demonstrating the same pattern is a design reference only:** it declares no
  licence, so its code is not copied, vendored or ported unless a qualifying licence is added and
  reviewed.

### Do not implement

- Whole-session compaction (#373), unrestricted context pruning, or whole-repository retrieval.
- An `advise` mode in 0.13.0.
- A separate provider path outside the shared contracts.
