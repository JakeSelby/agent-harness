## Story

As a developer who wants the latest release rather than the trunk, I want a `stable` branch that
always points at the latest release tag, so that I can clone or browse the released version by
branch name.

## Context and value

`main` is the trunk and carries unreleased work, so nothing in the repository named "the latest
release" as a branch a person could clone or browse.
[Source: https://github.com/JakeSelby/agent-harness/issues/341]

## Acceptance criteria

1. **Given** a published GitHub release, **when** the release workflow finishes, **then** `stable`
   has been fast-forwarded to the tag's commit.
2. **Given** a refused push, **when** the job fails, **then** the release run is not turned red, and
   a warning annotation is left.
3. **Given** `scripts/advance_stable.py --check`, **when** `stable` is not at the tag, **then** it
   fails; run without `--check`, it repairs the branch by hand, creates it on first use, and never
   moves it backward.
4. **Given** the release procedure and the release-surfaces list, **when** read, **then** they name the
   check.

## Design

### Approach

A new `advance-stable` job in `.github/workflows/release.yml`, after the release is published, calling
`scripts/advance_stable.py`.
[Source: https://github.com/JakeSelby/agent-harness/pull/342]

### Decisions and alternatives

- The job is `continue-on-error`, so a refused push cannot fail a published release; the `--check`
  step in the release procedure is what catches a stale branch.

### Do not implement

Changing the repository's default branch. GitHub creates closing-issue links only for pull requests
that target the default branch, and the required `issue-ownership` check depends on those links.
[Source: https://github.com/JakeSelby/agent-harness/issues/341]
