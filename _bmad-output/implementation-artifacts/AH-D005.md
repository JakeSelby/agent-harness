# AH-D005 — Decide how map lifecycle stays current without a pull request after every merge

## Context

`_bmad-output/issue-map.json` records each item's `lifecycle`, and GitHub is the authority for it. So
every merge that resolves an issue leaves the map stale. Clearing that needs a pull request, which
resolves its own issue, which drifts the map again.

The issue records the cost on 2026-09-21: four map-maintenance pull requests in one day (#376, #403,
#419 and the one carrying this issue), none of which changed behaviour, each needing a delivery issue,
an ID reservation, a full gate run and CI.

It is a cost, not an outage. The daily `bmad traceability` workflow runs with `--ignore-lifecycle`, so
it never blocks. But the strict `audit --live`, the form a release is supposed to use, is red almost
always, which the issue says "trains people to ignore it".

At `origin/main`, `docs/bmad.md` ("Live verification") still describes that arrangement: the workflow
runs the live audit "daily, on issue events and when the map changes, with `--ignore-lifecycle` and
`--grace-days 2`", because "an issue closes before its map entry can follow it through a pull request".
`refresh` copies GitHub's title and state into the map and its story files, and never touches GitHub.

The 2026-09-23 PRD lists this as open question 2: "How does the issue map's lifecycle stay current
without a pull request after every merge (#420)? Does the derived sprint status (FR-65) change the
answer?" It blocks FR-65 and is needed by v0.14.0.

## Options

From the issue:

1. **Drop `lifecycle` from the map**, and read state from GitHub when it is needed. The map would record
   only what GitHub cannot: the ID, the artifact path and the primary parent. The issue's case: it
   "removes the treadmill entirely" and "loses the ability to read state from a checkout alone".
2. **Keep `lifecycle`, and have the workflow open a refresh pull request when it drifts**, so no one
   composes one by hand. The issue states no case against it. [ASSUMPTION: a refresh pull request
   would still need a delivery issue and a gate run, per the one-issue-per-PR rule in `AGENTS.md`.]
3. **Keep it, and fold `refresh` into the release checklist** in `docs/releasing.md`, accepting drift
   between releases. [ASSUMPTION: the strict audit would then stay red between releases; inferred from
   the issue's acceptance item, not stated as an argument.]

## Decision

Open: the maintainer chooses among the three options. The PRD records it as open question 2, owned by
the maintainer and needed by v0.14.0, together with whether the derived sprint status in FR-65 changes
the answer.

## Consequences

From the issue's Acceptance section, whichever option is chosen:

- a decision is recorded with its reasoning;
- the strict `audit --live` is green in normal operation, not only the `--ignore-lifecycle` form;
- `docs/bmad.md` states when a human is expected to run `refresh`, or that they never are.

Option 1 changes the map's schema, so `load_manifest` and every reader of `lifecycle` change with it.
