## Story

As a developer with my own agent rules, I want to write a detector for one of them as data rather than
Python, so that I can measure my own rules within the sixty-second test.

## Context and value

The release plan records that its first draft of the carve-out "did not work": a stranger running the
standalone tool would have got hits for the six generic detectors only, and a Python entry-point
registry asks a first-time user to write code before the tool says anything about their configuration.
Declarative detectors were the fix, and the epic (#443) names them as how the sixty-second test is met.
[Source: https://github.com/JakeSelby/agent-harness/issues/452]
[Source: _bmad-output/planning-artifacts/v0.13-adoption-release-plan.md#Step 5 — Carve out the measurement engine]

## Acceptance criteria

1. **Given** the six generic detectors re-expressed in the format, **when** both forms run over the
   corpus and fixture transcripts, **then** they produce identical hits, and the Python versions stay
   as the reference.
2. **Given** a rule file with a short declarative detector, **when** the report runs, **then** it
   reports that rule's hits with no code.
3. **Given** a directory of rule files passed with `--rules`, **when** the report runs, **then** a rule
   with a `detector:` block is measured, one with `opt_out: <reason>` is dark, and one with neither is
   listed as unmeasured.
4. **Given** a malformed detector entry, **when** it is loaded, **then** it is reported with file, line
   and reason, skipped, and every other detector still runs.
5. **Given** the format's documentation, **when** a reader reads it, **then** it states the limits and
   names the Python registry as the escape hatch.

## Design

### Approach

One entry is `id`, `rule`, `event` (`tool_use`, `assistant_text`, `session`), `when` and an optional
`gate`, compiled by `ruleprobe/matchers.py` into the same `Detector` a Python detector builds.
Matchers cover a tool name, an argument, a Bash command through the shared shell parse, a `git` call,
an environment assignment, a text body, an assistant message and a raw event kind, composed with
`any`, `all` and `not`, plus the session-level `order`, `absent` and `change`. Discovery reads
`.ruleprobe/detectors.yaml` at the repository root and a user-level file without a flag.
[Source: https://github.com/JakeSelby/ruleprobe/pull/1]

### Decisions and alternatives

- **A YAML subset with no dependency:** `ruleprobe/declarative.py` parses mappings, sequences, scalars
  and comments, and refuses anchors, aliases, tags, block scalars, directives and multi-document files
  by name and line. A `.json` file reads to the same objects.
- **Equivalence as proof:** `detectors/common.yaml` must match `common.py` hit for hit, so the format
  is a re-expression of the engine rather than a second engine.
- **Binding mirrors the harness lint gate without failing anything:** unmeasured rules are listed, not
  refused.
[Source: https://github.com/JakeSelby/ruleprobe/pull/1]

### Do not implement

- Detector generation from rule prose: the plan defers it to a later version that depends on a model.
  [Source: _bmad-output/planning-artifacts/v0.13-adoption-release-plan.md#Step 5 — Carve out the measurement engine]
