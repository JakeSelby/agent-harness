# AH-B044 — the issue number is keyed github_number in the map and issue in planned actions

## Reproduction

Read the issue number from both structures `scripts/bmad_issue_sync.py` produces:

- an entry in `_bmad-output/issue-map.json` keys it as `github_number`;
- an action returned by `planned_actions` keys it as `issue`.

Code that reads the map with `issue`, or an action with `github_number`, gets `None` rather than an
error, so a lookup silently finds nothing and the issue looks unmapped. The issue records that this
cost another session a watcher that could never have fired.

## Root cause

Confirmed at `origin/main` in `scripts/bmad_issue_sync.py`:

- `planned_actions` appends `{"issue": item["github_number"], "action": "missing"}` and
  `{"issue": item["github_number"], "changes": changes}`;
- the live audit reads `action["issue"]`;
- map entries and `reserve` use `github_number`, and the map carries `schema_version: 2`.

## Acceptance criteria

From the issue's Acceptance section:

1. **Given** any structure the script produces, **when** it names an issue number, **then** it uses
   the same key.
2. **Given** a map written by the previous version, **when** it is loaded, **then** it loads and
   `audit` reports no findings on it.
3. Unit tests cover the old map loading and the consistent key.

## Design

From the issue's Scope section:

- One name for the issue number across the map, the planned actions and the live findings.
- Readers of the map keep working: if the stored key changes, `load_manifest` accepts the old name, and
  the schema version records the change.

Renaming the actions' `issue` to `github_number` leaves the stored map untouched, so AC 2 holds without
a migration. [ASSUMPTION: the issue allows either direction; this option is inferred, not recorded.]

Do not implement, from the issue's "Out of scope" section: renaming `bmad_id`, `parent_bmad_id` or
`parent_github_number`. Only the issue-number key is inconsistent.

## Regression test

Not written. A test in `tests/test_bmad_issue_sync.py` would assert that every action from
`planned_actions` and every map entry carries the same issue-number key, and that a map in the previous
format still loads and audits clean.

- [ ] If the stored key changes, accept the old name in `load_manifest` and bump `schema_version`

- [ ] Tests for the old map and the consistent key (AC 3).
