## Story

As someone reading the replay benchmark's history, I want each run's cache-miss ratio recorded beside
its normalised cost, so that a candidate that buys fewer tokens with more cache misses is visible.

## Context and value

Split from #415, whose usage-ledger half landed in #496; this is the replay-benchmark half. The issue
asks for the per-run cache-miss ratio, computed the way `lib/harness_core/cache_prefix.py` computes it for
the ledger, beside `normalised_cost` on each results row and rendered in `history.md`.
[Source: https://github.com/JakeSelby/agent-harness/issues/497]

## Acceptance criteria

1. **Given** a replay run, **when** its results row is written, **then** it carries the cache-miss ratio
   beside the cache-normalised cost, and `history.md` renders it.
2. **Given** the change, **when** history is upserted, **then** the key (date, series, version, sha,
   bucket) is unchanged and older rows still render.
3. **Given** CLI output with no per-turn cache figures, **when** the ratio is computed, **then** it is
   unknown, never zero.
4. **Given** an errored run, **when** the arm mean is taken, **then** the run carries no ratio and is left
   out of the mean.

Criteria 1 to 3 are the issue's wanted outcome and constraints; criterion 4 is from the PR's test summary.

## Design

### Approach

Each row records `cache_miss_ratio`: cache writes over cache reads plus writes, summed over the run's
turns. The arithmetic is imported from `harness_core.cache_prefix`, the module `harness usage --by prefix`
(#496) uses for the ledger. `history.jsonl` and `history.md` carry each arm's mean beside the
cache-normalised ratio, and older rows render `n/a`. The field joins `STREAM_FIELDS`, so `cost_bench
backfill` derives it for rows whose raw output was kept.

### Decisions and alternatives

- **Every thread counts.** The replay figure counts every thread including subagents, where the ledger
  subtracts them, because in a replay a fan-out's fresh prefix is part of what the run cost. The two
  figures therefore legitimately differ for a fan-out run; this is documented in `docs/benchmarks.md`.
- **Per-turn usage, not `modelUsage`.** The figure is summed from per-turn assistant usage, because the
  unknown rule keys on per-turn figures being present.
- **What counts as unknown.** A run with any turn whose usage omits a cache field, or whose turns report
  neither reads nor writes, is `null`. Zero means a run that served its whole prefix.

### Do not implement

A change to the history upsert key (the issue's "Additive" constraint).
