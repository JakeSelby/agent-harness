## Story

As a developer under the `testing: required` stance, I want a skill that names instruments measuring test quality (branch coverage, mutation score, complexity, duplication), so that the stance can measure whether tests are any good rather than only asking for them.

## Context and value

The issue records that `testing: required` is "an instruction about effort, not a measurement": a suite with full line coverage and no assertions passes it. It adapts the discipline from `unclebob/swarm-forge`, whose engineering article pins mutation, CRAP and DRY instruments per language, and notes that his tools (Clojure, Go and Java, all his own) do not transfer while the concept does.

## Acceptance criteria

1. **Given** the skill, **when** it is read, **then** it has frontmatter whose description says when to use it.
2. **Given** each language the project works in (Python, TypeScript, Rust, Go), **when** the skill is read, **then** it names an instrument for it, including a mutation tool.
3. **Given** a tool the skill names, **when** it would be adopted, **then** the skill routes it through the licensing stance.
4. **Given** the operating rules, **when** they are read, **then** they say to mutate the diff rather than the tree and to run one instrument at a time.
5. **Given** the `required` variant, **when** it is read, **then** it carries one pointer to the skill, the always-loaded total stays within the 196-line test budget, and the reasoning stays out of the always-loaded layer.

## Design

### Approach

A new `claude/skills/code-quality-instruments/SKILL.md`: branch coverage over line coverage, mutation score as the instrument that measures assertions rather than execution, complexity joined to coverage, and duplication as a refactor signal rather than a gate. One pointer line in `claude/stances/testing/required.md`. The pull request reports the always-loaded total at 193.

### Decisions and alternatives

- **A skill, not a rule.** Always-loaded context was 192 of a 200-line cap with a tighter 196 test budget, and a per-language table is only needed when someone works on test quality; that is the placement ladder in `harness-authoring` (from the issue and the pull request).
- **Own instruments, borrowed discipline.** The source's tools are not adopted.
