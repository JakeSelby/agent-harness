# AH-B105 — grade-bash's confirm marker is refused as a bypass in auto mode, so an approved irreversible command can never run

<!-- bmad-sync:begin -->
- **GitHub issue:** [#859](https://github.com/JakeSelby/agent-harness/issues/859)
- **Primary parent:** None
- **State:** active

The issue carries the summary, discussion and acceptance evidence; this file carries the design.

This work item was authored as part of the repository's committed BMad planning system.
<!-- bmad-sync:end -->

## Reproduction

Claude Code in auto mode, autonomy stance `execute`:

1. The agent runs a grade-3 command, for example `gh api -X DELETE repos/<owner>/<fork>/git/refs/heads/<branch>`. `grade-bash` denies it and tells the agent to rerun it with `HARNESS_CONFIRMED=1` once the user agrees.
2. The user replies "Run it".
3. The agent runs `HARNESS_CONFIRMED=1 gh api -X DELETE ...`. The auto-mode classifier refuses it: `Permission for this action was denied by the Claude Code auto mode classifier. Reason: [Auto-Mode Bypass].`

Result: in auto mode no command the hook gates can ever run, whatever the user says. The governance binding that follows this story would hit the same wall for every level-1 or level-2 action.

## Root cause

In `auto` and `bypassPermissions` the hooks reference says an `ask` decision is ignored, so `grade-bash` has to deny, and its only confirmation channel is a marker the agent adds to its own command (`policy/hooks/grade-bash.py`, module docstring and `MARKER`). The auto-mode classifier judges each call on its own. It reads a prefix that switches off a safety hook as an attempt to bypass it, so the channel is closed by design. `bypassPermissions` has no classifier, so the marker still works there.

## Acceptance criteria

1. **Given** auto mode and a gated command denied with approval code `C`, **when** the user's next prompt contains `approve C`, **then** that exact command, with no marker, passes `grade-bash` once.
2. **Given** that approval has been used, **when** the same command runs again, **then** it is denied again.
3. **Given** an approval for `C`, **when** a different command runs, or the same command runs in another session, **then** it is denied.
4. **Given** an approval older than thirty minutes, **when** its command runs, **then** it is denied.
5. **Given** a prompt that contains a code without the `approve` keyword, **when** it is submitted, **then** nothing is recorded.
6. **Given** a Bash command that writes to the approval store, **then** it grades 3; **given** a file-tool write to the store, **then** it is denied. Only a user prompt can create an approval.
7. **Given** `bypassPermissions`, **then** `HARNESS_CONFIRMED=1` works as before; **given** a prompting mode, **then** the hook still asks natively and nothing about grading changes.

## Design

**Fix.** Give the auto-mode deny a user-typed approval channel, and make it reusable by the governance binding that follows.

- **The code binds a session to an exact command.** It is the first six base32 characters of `sha256(session_id + "\n" + command)`, over the raw command text. The same command in the same session always gets the same code, and no pending store is needed.
- **The auto-mode deny reason** tells the agent to stop and ask the user to reply `approve <code>`. It replaces the marker instruction in that mode only.
- **A `UserPromptSubmit` module records approvals.** It scans the user's prompt for `approve <code>` tokens (case-insensitive, several allowed) and writes them to a per-session file under the harness state directory (`approvals/<session_id>.json`), each with its creation time.
- **`grade-bash` consumes an approval** at the point it would deny. It computes the code, looks for an unused approval younger than thirty minutes in this session's file, marks it used and lets the command through with no output.
- **One small module** holds `code_for`, `record` and `consume`, so the governance binding can reuse the channel unchanged.
- **The store is protected.** A Bash write to the approvals directory grades 3. A file-tool write to it is denied, in whichever PreToolUse module already handles file tools once hook manifests land.

**Rejected alternatives:**
- Reading the transcript for the user's "yes": fragile, and text the agent quoted could forge it.
- A random nonce kept in a pending store: that is a second store the agent must not write, and the hash needs none.
- Approving the command for the rest of the session: the issue asks for one use.

**Must not change:** grading, the native `ask` in prompting modes, and the marker in `bypassPermissions`.

**Unverified until checked by hand:** whether a prompt sent through Remote Control reaches `UserPromptSubmit`. The completion notes must record the result.
