# AH-B069 — Reserve a BMad ID in the same invocation that files the issue

## Reproduction

Run `python3 scripts/bmad_issue_sync.py new` against the live repository. The issue records three
failures out of three during the 0.12.0 release, for example:

```
bmad issue sync: issue #532 was filed but not reserved; fix the cause and run reserve --issue 532: RuntimeError('issue #532 was not found')
```

`gh issue view` returns the issue immediately afterwards, and `reserve --issue <n> --kind <kind>` then
succeeds.

## Root cause

Traced in `scripts/bmad_issue_sync.py` at `origin/main`:

- `create_issue` reads the new number from the create response, then calls `reserve`.
- `reserve` re-reads the whole issue list through `fetch_issues(repo)`. It raises `issue #N was not
  found` when the new number is not in that list yet. Nothing retries.

The issue's diagnosis is that "the lookup runs before the freshly created issue is visible to whatever
read it uses". The code confirms the lookup is a fresh list read; the visibility delay itself is the
issue's observation.

## Acceptance criteria

From the issue's Acceptance section:

1. **Given** a live repository, **when** `new` runs, **then** it returns a reserved ID in one
   invocation.
2. **Given** a lookup that misses on the first read, **when** it is retried, **then** the retry
   succeeds, and a test covers it.

## Design

From the issue's Solution section: retry the lookup that follows the create, or read the number from
the create response instead of searching for it.

`create_issue` already reads the number from the create response. What it does not pass on is the rest
of the payload `reserve` needs (`html_url`, `title`, `state`), so `reserve` fetches it again. Passing
the payload through is the second option in practice. [ASSUMPTION: which fields `reserve` needs is read
from the code; the issue does not list them.]

Do not implement: the issue records no out-of-scope item.

**Duplicates recorded.** This is the same defect as #392 (AH-B040), filed on 2026-09-21 with a fuller
scope, and #433, which adds that the printed recovery omits `--kind`. All three are open. PR #441's body
assigns the read-after-write failure to #433. One of them should deliver the fix and the others close
as duplicates. That triage is not recorded.

## Regression test

Not written. A test would stub the issue-list read to miss the new number once, then return it, and
assert that `new` returns a reserved ID.
