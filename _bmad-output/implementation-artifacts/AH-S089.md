## Story

As a developer on Claude Code or Codex, I want architecture viewing to be one shared harness capability behind a versioned adapter contract, so that I can select a viewer implementation without runtime-specific skills, duplicated policy or a bundled renderer.

## Context and value

v0.9.0 deliberately deferred UML viewer integration. The evaluated `unclebob/uml-viewer` had useful rendering and document behaviour but was not yet a licensed, versioned, standalone dependency with a stable consumer contract. The harness needed a generic boundary that could use that project once upstream work landed and could also support user-selected implementations ([#199](https://github.com/JakeSelby/agent-harness/issues/199)).

The issue carries the v0.10.0 milestone and was closed as completed on 2026-09-19 by PR #204.

## Acceptance criteria

1. **Given** both runtimes, **when** the catalog is projected, **then** one shared skill and capability serve Claude Code and Codex.
2. **Given** the adapter contract, **when** its documentation is read, **then** describe, validate, open, replace-document, status and close each have documented request and response semantics.
3. **Given** an invalid descriptor, an incompatible version, malformed, non-finite or oversized data, a timeout, a stale revision, failed persistence, a missing executable or a path escape, **when** the adapter is called, **then** it fails explicitly.
4. **Given** a custom selection or a temporary invocation override, **when** it is applied, **then** user-owned configuration is preserved and no implicit fallback is created.
5. **Given** an opened session, **when** its state is recorded, **then** it holds adapter identity and version, protocol version, epoch, revision, digest and the last structured result, and no document contents.
6. **Given** the test suite, **when** it runs, **then** it covers configuration preservation, idempotency, adapter pinning, concurrent sessions, cleanup and the upstream adapter's translation.
7. **Given** the documentation, **when** a reader checks support, **then** it distinguishes implemented harness support, locally available adapters, native qualification and upstream licensing and release status.

## Design

### Approach

As built in PR #204:
- The harness owns implementation selection, path authorization, session pinning, diagnostics and the neutral architecture profile. A viewer owns rendering, document validation, revisioned lifecycle, concurrency, structured errors and distribution ([PR #204](https://github.com/JakeSelby/agent-harness/pull/204)).
- An adapter is a registered JSON descriptor with an id, capability, `contract_version`, `argv` and optional settings. It reads one bounded JSON object on stdin and writes one JSON result on stdout; inputs and outputs are capped at 1 MiB and calls have a deadline [Source: docs/viewer-integrations.md#Adapter contract 1].
- Each live session is pinned to its original adapter, so a later configuration change cannot redirect it ([PR #204](https://github.com/JakeSelby/agent-harness/pull/204)).
- The upstream adapter calls only the installed public client and imports no viewer code [Source: docs/viewer-integrations.md#Adapter contract 1].

### Decisions and alternatives

- The builtin adapter is the default and a custom adapter is an explicit selection; the selector never substitutes one for the other. The distribution ships no builtin adapter today, and inspection reports it unavailable [Source: docs/viewer-integrations.md].
- Upstream code is neither vendored nor bundled; an upstream release, licence clearance and native qualification are separate gates ([#199](https://github.com/JakeSelby/agent-harness/issues/199)).

### Do not implement

From the issue's boundaries: no Claude-only or Codex-only viewer catalog, no Grok dependency, no browser embedding, no vendored renderer, and no claim that upstream is distributable before its licence and release work is complete ([#199](https://github.com/JakeSelby/agent-harness/issues/199)).
