## Goal

Open 0.13.1 as a release candidate so the landing-copy change in #764 can ship as a patch. The
reference site renders `product.json` from the harness release it pins, so its hero changes only
with a release. Native evidence is bound to the harness version and `VERSION` sits inside the
invalidation scope, so the patch needs its own qualification round on the two required Claude Code
CLI targets; this candidate is what that round runs against.

## Acceptance criteria

1. **Given** `VERSION` and `compatibility/catalog.json`, **when** they are read, **then** both say
   0.13.1, `release_state` is `candidate`, no `qualification_source_commit` is pinned, and
   `claude-code-cli-macos` and `claude-code-cli-linux` stay required, read `unqualified` and link
   no evidence; every limitation is unchanged.
2. **Given** `compatibility/migration.json`, **when** it is read, **then** it describes the upgrade
   from 0.13.0 as a landing-copy-only patch with no runtime, configuration or projection change.
3. **Given** `README.md`, `docs/compatibility.md` and `docs/releasing.md`, **when** they are read,
   **then** each states 0.13.1 as a candidate and 0.13.0 as the current qualified release, with
   0.11.1 still the Codex CLI floor, and `tests/test_docs.py` and `tests/test_compatibility.py`
   pin that state.
4. **Given** `benchmarks/static.json`, **when** `cost_bench.py static --check` runs, **then** it
   passes for 0.13.1.
