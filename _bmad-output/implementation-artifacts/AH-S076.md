## Story

As the maintainer cutting a release, I want publication gated on versioned native-client evidence and the
release notes and support displays generated from the shared authority, so that no release or support
statement can go out ahead of the qualification behind it.

## Context and value

This is a delivery slice of #100 (coordinate the verified release, metadata and website deployments),
referencing #98 and tracked by epic #93. It records ownership of the already open PR #110, the final layer
of the stacked implementation, and prepares the 0.9.0 candidate. At merge, publication remained blocked:
all seven required native combinations were unqualified.
[Source: https://github.com/JakeSelby/agent-harness/issues/172]

## Acceptance criteria

Taken from the issue's own acceptance section. The outcomes listed under AC 1 restate the
issue's "Proposed design", which AC 1 requires the PR to satisfy.

1. **Given** PR #110, **when** it is reviewed, **then** its implementation and documentation satisfy the
   issue's proposed design and preserve the single shared primitive authority. The design outcomes:
   1. **Given** a release candidate, **when** release preflight runs, **then** it refuses publication while any
      required native combination lacks versioned evidence.
   2. **Given** the shared authority, **when** release notes and support displays are produced, **then** they

   repository lint, generated projections and the existing CI commands pass.
3. **Given** the pull request, **when** it is reviewed, **then** it owns only this delivery issue, and
   broader tracking issues remain contextual references.
4. **Given** native evidence, **when** it is reported, **then** it names its exact tested source and
   versions, and this delivery alone makes no complete client-support or publication claim.

## Design

### Approach

`scripts/release_preflight.py` checks the compatibility catalog and its evidence against `VERSION` and
fails on an unqualified required combination. `scripts/release_notes.py` generates the notes, and
`.github/workflows/release.yml` runs the release. `docs/releasing.md` documents the coordinated site
pinning, deployment, verification and rollback. [Source: https://github.com/JakeSelby/agent-harness/pull/110]

### Decisions and alternatives

- **Block rather than waive:** preflight rejected all seven unqualified combinations as intended.
- **Generate from shared authority:** notes and support displays are derived, not restated.
- Alternatives considered are not recorded in the issue or pull request.

### Do not implement

- The release itself, any deployment, or a GitHub About update.
- The qualification rounds (#185, #187, #188). [ASSUMPTION: the issue does not name this sibling; the link is drawn from the issue map and epic.]
