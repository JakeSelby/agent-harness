# AH-B078 — A round without --model runs the runner default while its record declares the routed execution model

## Reproduction

1. Provision a round and run `python3 scripts/qualification_round.py --round <dir> --targets
   claude-code-cli-macos` with no `--model`.
2. The round prints and records `execution standard (sonnet), assessment strong (opus)` and
   launches `scripts/native_acceptance.py` with `--execution-class standard` and no `--model`.
3. The runner's `--model` defaults to `DEFAULT_MODEL`, `haiku`, so every case runs on `haiku`.

Observed in the 0.13.0 round 3 on `claude-code-cli-macos`: the cases ran on `haiku` while
`round.json` and each evidence record said `tier_routing.execution_model: sonnet`, and neither
record held a field naming the model actually run.

## Root cause

The routing work in #598 resolves an execution model per target through the adapter bindings and
records it, but the model a client runs was never tied to it. `target_argv` adds `--model` only
when the operator gave one, and the runner resolves its own routing from the classes alone, so the
routed model and the model passed to the client were two independent values that agree only by
accident. [Source: scripts/qualification_round.py#target_argv]
[Source: scripts/native_acceptance.py#main] [Source: lib/harness_core/qualification.py#resolve]

## Acceptance criteria

1. **Given** a round with no `--model`, **when** a target whose execution class is mapped is
   launched, **then** the runner is passed `--model <routed execution model>` and the round's
   routing for it says `model_source: routing`.
2. **Given** a round with `--model X` where X is not the routed model, **when** a target is
   launched, **then** the runner is passed `--model X`, and the routing says `execution_model: X`,
   `model_source: operator` and `routed_model: <routed model>`.
3. **Given** an execution class the adapter does not map, **when** the round launches it, **then**
   no `--model` is passed and the routing says `execution_model: haiku` (the runner default) and
   `model_source: runner default`.
4. **Given** any of the above, **then** the round record's routing and the runner's record routing
   for that target are identical.
5. **Given** a runner run, **then** the evidence record header and every per-case row carry
   `model_run`, the model passed to the client.
6. **Given** a durable log written on one model, **when** it is rebuilt with `--from-progress`
   under another, **then** the rebuild is refused rather than relabelled.

## Design

`native_acceptance.executed_by(routing, model)` is the one rule: the model run is `model` or
`DEFAULT_MODEL`, `execution_model` is restated to it, `model_source` is `routing`, `operator` or
`runner default`, and `routed_model` keeps the adapter's model whenever the two differ. The runner
applies it in `main` and `record`; the round applies it once per target in `with_models` before the
round record is first written, passing the routed model (or the operator's) as the argument, and
`target_argv` passes whatever model that routing names unless its source is the runner default.
Because both sides restate the same fresh class routing from the same `--model`, the round record
and the target record agree without the round sending the source across.

Rejected: a new `--model-source` flag on the runner, which adds surface only to carry a label the
comparison already derives; and changing the runner's own default to the routed model, which would
move a standalone run from `haiku` to the standard-class model and its cost without being asked.

Must not change: the class resolution and its refusals, the runner default, or anything the round
does when `--model` is given beyond recording it. The consequence is that an operator who passes
the routed model explicitly is recorded as `routing`, since that is the model the routing names.

## Regression test

`tests/test_qualification_model_run.py`:
`test_without_model_the_runner_is_passed_the_routed_execution_model` and
`test_a_round_without_model_runs_and_records_the_routed_model` fail before the fix (no `--model`
reached the runner) and pass after it; `test_every_case_row_and_the_header_carry_the_model_run`
fails before it (no `model_run` field).

## Dev notes

- Files: `scripts/native_acceptance.py`, `scripts/qualification_round.py`,
  `tests/test_qualification_model_run.py`; `tests/test_native_acceptance.py` and
  `tests/test_native_acceptance_progress.py` pin the record's key set and gain `model_run`.
- `model_run` joins `HEADER_KEYS`, so `progress_lines` drops a line from another model the way
  it drops one from another commit. A `--from-progress` rebuild passes the same `--model` the log
  ran on, as it already passes the same classes; a log written before this change carries no
  `model_source` and is refused rather than merged.
- An operator `--model` that names the assessment model is not refused by the same-model check,
  which compares adapter classes only; that is outside this fix.
