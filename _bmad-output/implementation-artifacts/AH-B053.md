# AH-B053 — Remote Control host gives up after 10 min offline, kills every session, and the launchd relaunch does not re-adopt them

This work item was authored as part of the repository's committed BMad planning system.
<!-- bmad-sync:end -->

## Reproduction

1. Run a Remote Control host under the launchd agent from #239 (`claude remote-control` with
   `--spawn worktree`, `KeepAlive` and `ThrottleInterval 60`), with several active web sessions.
2. Lose network connectivity for longer than ten minutes.
3. The host logs `Persistent errors for 10 minutes, giving up.`, shuts down every active session and
   removes their worktrees, keeping only one with uncommitted changes.
4. launchd relaunches the host with zero sessions. The web client shows every session as waiting to
   reconnect indefinitely, and messages sent from it do nothing.

Expected, per the issue: after the network returns, sessions live before the outage come back without
manual work, and their worktrees are not deleted while the session still exists server-side. The issue
records a manual recovery (recreate each worktree from `main` at its path and branch, then run
`claude remote-control --session-id <id>` once per dead session) and two client quirks: `--session-id`
was not honoured for the worker, and the reattached host was single-session and exited after one turn.
[Source: https://github.com/JakeSelby/agent-harness/issues/483]

## Root cause

From the PR: the host's 10-minute give-up path is destructive (it archives sessions and deletes
worktrees), and the relaunch registered a new environment because the host's `bridge-pointer.json` was
two days stale, so nothing came back. The PR says the evidence and the binary reading are in #483.

The repository owner's corrected root cause on the issue (2026-09-22, Claude Code 2.1.278) goes further
than the hardcoded ten-minute give-up. The client has a re-adopt path: it asks the server to reuse the
environment id in `bridge-pointer.json`, then re-queues the session through `bridge/reconnect`. But it
writes that pointer only after a reuse it requested has succeeded, so a host that starts without one
never writes one. The file then ages past its four-hour TTL, every relaunch registers a fresh
environment, and nothing is adopted. The give-up then archives the sessions and deregisters the
environment, and `POST /v1/environments/<new-env>/bridge/reconnect` answers
`400 Session does not belong to this environment`, so nothing external can recover them afterwards.
[Source: https://github.com/JakeSelby/agent-harness/issues/483]

## Acceptance criteria

1. **Given** an outage longer than ten minutes, **when** the network returns, **then** every session
   live beforehand reconnects in the client within two minutes, with no user action.
2. **Given** the give-up path, **when** it runs, **then** no worktree is deleted by it.
3. **Given** a reattached session, **when** it resumes, **then** it keeps the permission mode and model
   it had before.

**Undelivered or unverified.** The PR delivers criterion 2 by stopping the host before the give-up and
recreating removed worktrees. It does not automate reattachment (criterion 1): `status` lists lost
sessions with the manual command, because a `--session-id` host re-registers the lost environment as a
second one that then captures new chats. Criterion 3 is not addressed in the record. The PR names the
network-cut exit test as unverified, needing a real chat session and a human trust dialog, and calls it
the qualification item. Environment reuse and automatic reconnect came later under #603 (PR #604).

## Design

**Approach.** `harness remote-control install|status|uninstall` keeps one launchd host per configured
folder, plus a `heal` agent on `StartInterval 60` that:
- keeps each host's `bridge-pointer.json` naming its live environment;
- stops the host with SIGTERM at nine minutes unreachable, so launchd's relaunch takes the preserving
  path instead of the destructive 10-minute give-up. The owner's comment on the issue records that this
  SIGTERM-preserves-then-reuses loop was "read from the binary, not observed", because a probe host could
  not be started, and that the guard was then left unarmed until the loop was observed. The PR body,
  merged later that day, describes the nine-minute stop as part of the change;
- recreates worktrees the give-up path removed, WIP-committing dirty session worktrees first.

`install` refuses a folder Claude Code has not trusted and says how to trust it. `harness doctor` reports
pid, environment, pointer freshness, reachability and lost sessions per host.

**Decisions and alternatives.** Reattach was not automated, for the reason under the criteria. System
sleep resets the unreachable budget. The issue's proposal to file the two quirks upstream is not recorded
as done in the issue or pull request.
