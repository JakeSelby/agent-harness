## Story

As a developer who has enabled a decision provider, I want each provider call recorded as a priced
decision row and summarized in `harness usage` and `harness doctor`, so that I can see what a judgment
cost, how long it held up a turn, and which model actually answered, without missing data reading as
zero or as success.

## Context and value

Users need to tell an installed adapter from one that is enabled and producing judgments, and missing
provider data must not look like zero cost or a passed check. The 2026-09-21 re-scope re-pointed the
work at what 0.12.0 ships: provider calls become `kind: decision` rows in the usage ledger, priced
through `policy/prices.json`, and `harness doctor` reports the pinned and last returned model. Before
this, the token and latency cost of a judgment was recorded nowhere.
[Source: https://github.com/JakeSelby/agent-harness/issues/139]

## Acceptance criteria

1. **Given** a Jev call, **when** it completes, **then** one `kind: "decision"` row is written with the
   point, mode, status, requested and returned model ids, pack and request hashes, judgment and severity
   labels, the deterministic outcome and the one `act` would have reached, token counts, latency and the
   parent session.
2. **Given** a context full of outbound state, prompts, file paths and environment values, **when** the
   row is built, **then** it carries none of them; the row's key set is pinned by a test.
3. **Given** decision rows, **when** `harness usage --by provider` runs, **then** calls are grouped by
   point and mode, priced like any other row, latency is reported beside statuses, and a call with no
   reported usage is `partial` and counted as unpriced rather than free.
4. **Given** decision rows in the ledger, **when** any other `--by` grouping runs, **then** its output is
   byte-identical to the output without them, so no session is charged for a provider call.
5. **Given** two identical calls, **when** they are written, **then** both rows survive: the write is an
   append under the ledger lock, not a rewrite.
6. **Given** `harness doctor`, **when** it runs, **then** it reports the model every request pins and
   the one the last call returned.
7. **Given** `telemetry.decisions` off, **when** a call is made, **then** neither ledger receives a row,
   and `harness decide` suppresses both.
8. **Given** a decision row is exported over OTLP, **when** a backend sums session tokens, **then** it
   never counts it, because every field carries the `harness.decision.` prefix.

## Design

### Approach

A new `lib/harness_core/decisions/ledger.py` builds the row key by key from a fixed list and reads
nothing else. `policy/hooks/usage-log.py` gains an append path under the existing lock. `bin/harness`
adds `usage --by provider` and the doctor lines, and `policy/hooks/telemetry.py` prefixes decision
fields on export.

### Decisions and alternatives

- **Append rather than `upsert`:** a call inside a hook's time budget does not re-read and rewrite the
  whole file, and identical calls stay distinct.
- **Abstention and no-answer are separate columns:** a provider that abstained is a different event from
  no answer.
- **Record the returned model,** because a provider may answer on a model the harness did not ask for,
  and pricing at the requested one would use the wrong rate.
- **No provider price in the table,** because none is published; `usd` stays empty until a rate is
  added or overridden. `cache_read` and `cache_write` are 0 rather than null because the vendor's usage
  contract has exactly two fields.
- **Not duplicated from #137:** mode per point, allowlist, kill switch and credential-by-name already in
  `doctor`.

### Do not implement

- Raw request or response bodies, or credentials, in ordinary telemetry.
- A paid probe from `doctor` unless explicitly requested.
- Hook wiring: whoever binds `grade-bash` must pass `session_id`.
